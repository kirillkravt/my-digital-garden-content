## 🤖 **DeepSeek**

### **Нефункциональные требования (НФТ) для процесса СБП переводов в Core**  

#### **1. Требования к архивированию данных**  
1.1 **Ежедневное резервное копирование**  
- Полное резервное копирование данных Шлюза СБП/Core должно выполняться ежедневно.  
- Резервные копии должны храниться в отдельном защищенном хранилище, изолированном от основного контура.  
- Должна быть обеспечена возможность восстановления данных из резервной копии в течение 1 часа.  

1.2 **Долгосрочное хранение архивных данных**  
- Все транзакционные и служебные данные должны архивироваться без возможности удаления в течение **5 лет**.  
- Архивные данные должны храниться в формате, обеспечивающем их неизменность (WORM-хранилище, blockchain-аудит).  
- Доступ к архивным данным должен быть защищен и предоставляться только по запросу аудиторов или регуляторов.  

---  

#### **2. Требования к логированию операций**  
2.1 **Полнота логирования**  
- Логируются **все** автоматические операции и действия пользователей (включая администраторов).  
- Каждая запись в логе должна содержать:  
  - временную метку (timestamp),  
  - идентификатор пользователя/системы,  
  - тип операции,  
  - входные и выходные данные (если применимо),  
  - статус выполнения (успех/ошибка).  

2.2 **Защита и хранение логов**  
- Логи должны храниться **не менее 5 лет**.  
- Доступ к логам должен быть защищен от модификации (аудитируемый доступ, хеширование).  
- Логи должны быть доступны для анализа в реальном времени (SIEM-системы, мониторинг подозрительных действий).  

---  

#### **3. Требования к производительности**  
3.1 **Время отклика**  
- Время обработки запроса от СБП до ответа Шлюза СБП должно соответствовать **Стандарту ОПКЦ СБП** (например, не более **500 мс** для 95% запросов).  

3.2 **Масштабируемость**  
- Система должна обеспечивать обработку:  
  - **20 000 транзакций/день** на старте (2025),  
  - **≥100 000 транзакций/день** через 2-3 года.  
- Пиковая нагрузка: **≥1 000 транзакций/минуту** (с запасом для роста).  
- Возможность горизонтального масштабирования (кластеризация, балансировка нагрузки).  

---  

#### **4. Требования к отказоустойчивости**  
4.1 **Восстановление после сбоев (RTO/RPO)**  
- **RTO (Recovery Time Objective)**: ≤15 минут (включая переключение на резервный контур).  
- **RPO (Recovery Point Objective)**: ≤2 минуты (максимальная потеря данных при аварии).  

4.2 **Высокая доступность (HA)**  
- Реализация **активно-пассивного** или **активно-активного** кластера.  
- Мониторинг работоспособности в реальном времени (health-check, автоматическое переключение при сбое).  
- Геораспределенная отказоустойчивость (минимум 2 ЦОДа).  

---  

### **Дополнительные рекомендации**  
- **Аудит безопасности**: регулярные пентесты и анализ уязвимостей.  
- **Шифрование данных**: TLS 1.2+/1.3 для передачи, AES-256 для хранения.  
- **Мониторинг и алертинг**: интеграция с Prometheus/Grafana, Sentry, ELK.  

Эти НФТ обеспечат надежность, производительность и соответствие регуляторным требованиям СБП.

## 🤖 **DeepSeek**

### **Механизм обработки сетевых проблем и восстановления статуса платежа**  

#### **1. Сообщение о временной недоступности (HTTP 503 + кастомный код)**  
Если шлюз не может получить финальный статус платежа из-за сетевых/интеграционных проблем (не ошибка в платеже), следует возвращать:  
- **HTTP Status**: `503 Service Unavailable` (лучше, чем `500`, так как явно указывает на временную проблему).  
- **Response Body**:  
  ```json
  {
    "code": "NETWORK_UNAVAILABLE",
    "detail": "Temporary network issue. Final payment status cannot be determined at this time. Retry later or wait for callback."
  }
  ```  
  **Пояснение к кодам**:  
  - `NETWORK_UNAVAILABLE` – проблема с подключением к Core/СБП.  
  - `INTEGRATION_FAILURE` – сбой во внутренней интеграции (если отличается от сети).  

#### **2. Механизм восстановления статуса**  
Чтобы избежать кэширования и повторных запросов, можно использовать **один из подходов**:  

##### **2.1. Callback-механизм (предпочтительно)**  
- Шлюз СБП после восстановления связи **сам инициирует запрос** к внешней системе с финальным статусом.  
- Требования:  
  - Внешняя система должна предоставить **эндпоинт для callback** (например, `POST /api/payments/{id}/status-update`).  
  - В исходном запросе (где вернулся `503`) можно указать:  
    ```json
    {
      "code": "NETWORK_UNAVAILABLE",
      "detail": "Awaiting callback to finalize the status. Callback URL: https://client-system/api/callback/payment-status"
    }
    ```  

##### **2.2. Поллинг с экспоненциальным бекоффом**  
Если callback невозможен:  
- Внешняя система периодически запрашивает статус через `GET /api/payments/{id}`, но:  
  - Первый повторный запрос – через **1 секунду**.  
  - С каждым неудачным запросом интервал увеличивается (2s → 4s → 8s → 16s → …).  
  - Максимальный интервал – **5 минут**.  

##### **2.3. Компенсирующая транзакция (для идемпотентности)**  
- Если платеж был создан, но статус неизвестен, после восстановления:  
  - Шлюз СБП проверяет **в Core/СБП** актуальный статус.  
  - Если платеж был исполнен – шлюз сохраняет статус в своем журнале и уведомляет клиента.  
  - Если платеж не был исполнен – можно автоматически повторить обработку.  

#### **3. Гарантии доставки статуса**  
- **Журнал событий (Event Log)**:  
  Все запросы с временными ошибками (`503`) фиксируются в отдельной таблице с полями:  
  ```plaintext
  payment_id | external_reference | created_at | last_retry_at | callback_url | status (PENDING/RETRY/COMPLETED)
  ```  
  - При восстановлении связи шлюз обрабатывает записи с `PENDING`/`RETRY`.  

- **Таймаут обработки**:  
  Если статус не удалось обновить в течение **24 часов**, платеж помечается как `EXPIRED` и требует ручного разбора.  

#### **4. Рекомендации**  
- **Не использовать кэш**:  
  Вместо кэша – **журнал с флагами** (как выше), чтобы избежать потерь данных.  
- **Idempotency Key**:  
  Для всех запросов использовать `X-Idempotency-Key`, чтобы избежать дублирования.  
- **Мониторинг**:  
  Алёртинг на длительные `PENDING`-статусы (например, в Prometheus/Grafana).  

### **Итог**  
1. **Отвечать `503 + кастомный code`** при временных проблемах.  
2. **Callback или поллинг** для доставки финального статуса.  
3. **Журнал событий + таймауты** для гарантии доставки.  
4. **Идемпотентность** для безопасных повторов.  

Это обеспечит ясность для клиента и надежное восстановление процесса.

### **Предложение по унифицированному коду и описанию для неоднозначных статусов**  

**Формулировка:**  
*"Поскольку процессинг не сможет различить случаи (1) обрыв соединения и (2) внутренняя ошибка при формировании ответа, предлагаем использовать единый код `OPERATION_STATUS_UNKNOWN` с детализацией в поле `detail`. Это явно укажет ТСП, что текущий статус операции не может быть определен до восстановления работы систем и получения финального ответа от Шлюза СБП."*  

#### **Пример ответа (HTTP 500):**  
```json
{
  "code": "OPERATION_STATUS_UNKNOWN",
  "detail": "The operation status cannot be determined at this time due to a temporary processing failure. The final status will be delivered later via callback or retry mechanism."
}
```  

#### **Обоснование:**  
1. **Упрощение обработки на стороне ТСП**:  
   - Единый код исключает необходимость различать типы сбоев (сеть/процессинг), так как действия ТСП одинаковы — ожидание финального статуса.  
   - Поле `detail` объясняет причину и дальнейшие шаги (ожидание callback или повторного запроса).  

2. **Гибкость для будущих кейсов**:  
   - Код `OPERATION_STATUS_UNKNOWN` покрывает не только текущие сценарии (обрыв связи, ошибка процессинга), но и потенциальные аналогичные случаи.  
   - В будущем механизм доставки (callback/поллинг) обеспечит гарантированное получение итогового статуса.  

3. **Совместимость с будущими доработками**:  
   - В следующих итерациях можно добавить:  
     - **Callback-URL** в ответе (если ТСП поддерживает).  
     - **Рекомендуемый интервал повторного запроса** (например, `retry_after_seconds: 60`).  

#### **Дополнительное уточнение для команды:**  
*"Такой подход позволяет:  
- Избежать путаницы у ТСП из-за множества кодов ошибок.  
- Четко разделять «временную неопределенность» (`OPERATION_STATUS_UNKNOWN`) и «окончательные ошибки» (например, `INVALID_ACCOUNT`, `FRAUD_DETECTED`).  
- Заложить основу для механизма доставки статусов (callback/поллинг) без изменения контракта API."*  

**Итог:**  
- **Код**: `OPERATION_STATUS_UNKNOWN` (универсальный для всех кейсов неоднозначности).  
- **Детализация**: Человекочитаемое пояснение + указание на асинхронное завершение.  
- **Будущее развитие**: Добавление callback/поллинга без смены логики обработки `code`.

## 🤖 **DeepSeek**

Here’s the refined version with clearer wording about the final status delivery:  

**Updated `detail` message:**  
```json
{
  "code": "OPERATION_STATUS_UNKNOWN",
  "detail": "The current status of the operation cannot be determined due to a temporary system issue. The final status will be sent as soon as it is received from the processing system, either via callback or in response to a subsequent request."
}
```  

### Key Improvements:  
1. **Clarity on Source of Final Status**:  
   - Explicitly states that the status will come **from the processing system** (not just generically "later").  
2. **Removed Ambiguity in "Delivered"**:  
   - Replaced "delivered later via callback or retry mechanism" with:  
     - **Callback**: Passive delivery (if supported).  
     - **Subsequent request**: Active polling (fallback).  
3. **Neutral Tone**:  
   - Avoids technical jargon ("retry mechanism") in favor of plain terms ("subsequent request").  

### Why This Works Better:  
- **For TSPs**: Makes it clear they can either:  
  - Wait for an automated callback (if implemented).  
  - Periodically retry the request (if no callback arrives).  
- **For Support Teams**: Explains the issue without implying guaranteed delivery via a specific method (e.g., callback might not be configured yet).  

### Пример для документации:  
> *"При возникновении ошибки `OPERATION_STATUS_UNKNOWN` ТСП должен:  
> 1. Запросить статус повторно через некоторое время **или**  
> 2. Ожидать callback (если интеграция поддерживает этот механизм).  
> Финальный статус будет определен, как только обработка операции завершится."*  

This aligns with your goal of avoiding caching while keeping the flow transparent.
