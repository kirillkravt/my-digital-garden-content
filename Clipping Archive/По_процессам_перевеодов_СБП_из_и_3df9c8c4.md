### **Ключевые вопросы по интеграции Core <-> ABS**

**Цель:** Определить протокол взаимодействия, форматы данных, гарантии доставки и механизмы обработки ошибок для прямой интеграции между Core-системой и АБС.

#### **1. Вопросы по протоколу и способу взаимодействия:**

*   **Какой тип интеграции предполагается?** (нужно выбрать или уточнить)
    *   **Синхронный запрос-ответ** (например, REST API, gRPC): Core отправляет запрос и ждет немедленный ответ от АБС со статусом (например, "Успех", "Недостаточно средств", "Отклонено").
    *   **Асинхронное взаимодействие через сообщения** (например, Kafka, RabbitMQ): Core отправляет сообщение о переводе в топик/очередь, АБС потребляет его, обрабатывает и отправляет сообщение-подтверждение/статус в ответный топик.
    *   **Комбинированный подход** (например, отправка через сообщение, но с синхронным подтверждением о приеме).

*   **Какой конкретный протокол/технология будет использоваться?** (REST HTTP/HTTPS, SOAP, WebSocket, специализированный бинарный протокол?)

#### **2. Вопросы по контракту данных (формат и содержание):**

*   **В каком формате будут передаваться данные?** (JSON, XML, Protobuf, Avro, фиксированная ширина, другое?)
*   **Каков минимально необходимый набор полей в запросе от Core к АБС для выполнения перевода?** Например:
    *   Идентификатор операции в Core (уникальный для идемпотентности)
    *   Сумма и валюта перевода
    *   Реквизиты отправителя (номер счета, БИК, ИНН и т.д.)
    *   Реквизиты получателя (номер счета, БИК, ИНН, назначение платежа)
    *   Тип/назначение платежа (СБП, межбанк и т.д.)
    *   Дата и время инициации
*   **Какие данные Core должна ожидать в ответе от АБС?** Например:
    *   Статус обработки ("выполнено", "отклонено", "на проверке")
    *   Уникальный идентификатор операции в АБС/эквайринге СБП
    *   Код и описание ошибки (в случае отказа)
    *   Дата и время обработки в АБС
    *   (Для синхронного сценария) Токен/идентификатор для подтверждения операции (если требуется 3-D Secure или иная дополнительная аутентификация)

#### **3. Вопросы по гарантиям доставки и идемпотентности:**

*   **Как обеспечивается гарантированная доставка сообщения об операции до АБС?** (Повторные отправки при таймауте, устойчивые очереди сообщений?)
*   **Как система обеспечит идемпотентность (единоразовость обработки операции)?** Это критически важно, чтобы повторная отправка одного и того же платежа из-за сетевого сбоя не привела к списанию двух сумм.
    *   Предполагается ли использование уникального идентификатора запроса (Request ID) от Core, который АБС будет проверять на дубликаты?
*   **Каковы таймауты при ожидании ответа от АБС?** Что делать Core, если ответ не пришел в течение заданного времени?

#### **4. Вопросы по обработке ошибок и аварийным сценариям:**

*   **Какие возможны коды ошибок/статусы от АБС?** (Недостаточно средств, отклонено фрод-системой, неверные реквизиты, технический сбой АБС, недоступность эквайринга СБП и т.д.)
*   **Как Core-система должна реагировать на различные типы ошибок?**
    *   Какие ошибки являются финальными (повторять запрос бессмысленно, например "Недостаточно средств")?
    *   Какие ошибки являются временными (запрос можно повторить через некоторое время, например "Техническая ошибка", "Таймаут")?
    *   Сколько повторных попыток и с каким интервалом предпринимать?
*   **Как будет организовано логирование и мониторинг взаимодействия?** Нужен ли единый сквозной идентификатор (trace ID) для отслеживания запроса через все системы?

*   **Как будет обеспечиваться конфиденциальность и целостность передаваемых данных?** (Обязательное использование HTTPS с какими-либо версиями протоколов/шифров?)

    *   Авизо о зачислении: после того как средства стали доступны получателю (после окончательного расчета по системе СБП)?
*   **Каков ожидаемый жизненный цикл перевода с точки зрения авизо?**

#### **2. Вопросы по формату и содержанию авизо:**

*   **Какой набор данных должен содержаться в авизо?** Минимум:
    *   Уникальный идентификатор исходной операции (из Core).
    *   Уникальный идентификатор операции в АБС/СБП.
    *   Фактическая сумма списания/зачисления (она может отличаться от исходной, например, за счет комиссии?).
    *   Дата и время фактического проведения операции по счету в АБС.
    *   Конечный статус операции (`executed`, `cancelled`, `returned`).
*   **Как должны связываться авизо о списании и авизо о зачислении для одной транзакции в Core?** (По общему идентификатору из Core или по идентификатору из АБС?)

    *   **Глобальный уровень:** Полное отключение всего входящего/исходящего трафика СБП.

    *   Должны ли они быть дообработаны до конца?
    *   Или их необходимо откатывать (инициировать возврат)?
*   **Нужно ли уведомлять операторов или другие системы о срабатывании "крана"?** (Например, отправка алертов в Telegram, Email).

### **Ключевые вопросы по настройке параметров ответов для Payers**

**Цель:** Понять степень гибкости, требуемую для кастомизации ответов Core API (POST/PUT) под каждого эквайера (Payer), и механизм управления этими настройками.

---

#### **1. Вопросы о масштабе и объекте настройки:**

*   **Какие именно методы API требуют настройки ответов?**
    *   Только метод инициирования платежа (`POST /api/v1/payments`)?
    *   Только метод подтверждения/отмены платежа (`PUT /api/v1/payments/{id}`)?
    *   Или также и другие методы (запрос статуса, отмена)?
*   **Что конкретно нужно настраивать в ответах?**
    *   **Структура JSON:** Добавление, удаление или переименование полей в JSON-ответе.
    *   **Значения полей:** Изменение формата или статических значений существующих полей (например, другое название кода ошибки `"code"` -> `"error_code"`).
    *   **HTTP-заголовки:** Добавление специфичных HTTP-заголовков в ответ, которые ожидает Payer.
    *   **Коды HTTP-статусов:** Возможность изменить возвращаемый HTTP-статус для определенных сценариев (например, при ошибке валидации возвращать не `400 Bad Request`, а `200 OK` с кодом ошибки в теле, если так требует Payer).

#### **2. Вопросы о механизме настройки и хранения конфигураций:**

*   **Как и кем будут задаваться эти настройки?**
    *   **Через административный интерфейс:** Будет ли в Core реализован раздел "Настройки Payers", где можно в форме или JSON-редакторе задать шаблон ответа для каждого?
    *   **Через конфигурационные файлы:** Настройки будут храниться в файлах (YAML/JSON) на сервере Core, и для их изменения потребуется деплой?
    *   **Через базу данных:** Отдельная таблица `payer_settings`, где конфигурация хранится в виде JSON-объекта.
*   **На основе чего будет определяться, какую конфигурацию применять?** Идентификатор Payer будет передаваться:
    *   В HTTP-заголовке (напр., `X-Payer-Id`)?
    *   В теле запроса от АБС в специальном поле?
    *   Или определяется по другим признакам (например, по URL, если для каждого Payer свой endpoint)?

#### **3. Вопросы о логике применения настроек и данных:**

*   **Из каких источников Core будет брать данные для подстановки в кастомизированный ответ?**
    *   Только из результата своей внутренней логики (сгенерированный `payment_id`, статус, ошибки).
    *   Также из тела исходного запроса от АБС.
    *   Из внешних систем (например, из базы данных клиентов).
*   **Насколько сложной может быть логика преобразования?**
    *   Простая подстановка (маппинг) полей: `"our_internal_id": "{{payment_id}}"`.
    *   Условные конструкции: если статус "успех", то добавить одно поле, если "ошибка" — другое.
    *   Преобразование форматов дат или сумм.
    *   **Нужен ли будет встроенный шаблонизатор** (например, на основе Jinja2, Liquid или подобный) для генерации сложных ответов?

#### **4. Вопросы по обработке ошибок и валидации:**

*   **Как должна вести себя система, если конфигурация для конкретного Payer не найдена?** Использовать ответ по умолчанию?
*   **Кто будет нести ответственность за валидность кастомного шаблона?**
    *   Будет ли в интерфейсе настройки предварительная проверка (валидация) JSON-схемы?
    *   Что, если шаблон с ошибкой (невалидный JSON) приведет к падению метода API? Как это обрабатывать?
*   **Как обеспечить обратную совместимость?** При обновлении Core-системы и добавлении новых полей в ответ по умолчанию, нужно ли будет вручную обновлять шаблоны для всех Payers?

#### **5. Вопросы по безопасности:**

*   **Не открывает ли такой функционал потенциальные уязвимости?** Например, возможность через небезопасный шаблон случайно вернуть в ответе чувствительные данные (номера счетов, персональные данные), которые обычно не возвращаются.
*   **Кто имеет право вносить изменения в эти настройки?** Разграничение прав доступа (роли: администратор, разработчик, оператор).

## 🤖 **DeepSeek**

Отлично, это один из самых сложных и критичных аспектов проектирования надежной системы. Вот ключевые вопросы к заказчику, которые помогут определить требования к механизму автоматического восстановления после сбоев.

### **Ключевые вопросы по автоматическому восстановлению процесса после сбоев**

**Цель:** Понять, какие сбои считаются восстанавливаемыми, определить стратегии повторных попыток, границы автоматического восстановления и требования к мониторингу ручного вмешательства.

---

#### **1. Вопросы по классификации сбоев и стратегиям повторов:**

*   **Как классифицировать сбои?** Необходимо четко разделить:
    *   **Временные сбои (Transient faults):** Таймауты сети, временная недоступность АБС/СБП, блокировки БД. Такие сбои требуют стратегии повторных попыток.
    *   **Постоянные сбои (Permanent faults):** Неверные данные от клиента (неправильный номер телефона), "Недостаточно средств", отклонение фрод-фильтром. Повторные попытки бессмысленны и требуют перехода в статус "Ошибка".
    *   **Как система должна определять тип сбоя?** По HTTP-статусу (5xx vs 4xx), по коду ошибки в ответе от АБС, по типу исключения на своей стороне (сетевое vs бизнес-исключение)?

*   **Какая стратегия повторных попыток (Retry Policy) требуется для временных сбоев?**
    *   **Количество попыток:** Сколько раз пытаться повторить операцию до финальной ошибки? (3, 5, 10?).
    *   **Интервалы между попытками:** С постоянной задержкой (каждые 10 сек)? С экспоненциальной задержкой (backoff: 1 сек, 2 сек, 4 сек, 8 сек...)?
    *   **Таймаут всей операции:** Какое общее максимальное время на все попытки? (Например, не более 10 минут).

#### **2. Вопросы по персистентности и состоянию процесса:**

*   **Где и как будет сохраняться состояние каждого шага длительной операции (сага)?**
    *   **В базе данных Core:** Отдельная таблица `payment_attempts` или `transaction_steps` с полями: `payment_id`, `step_name`, `status` (`in_progress`, `success`, `error`), `attempt_count`, `last_error`, `next_retry_time`.
    *   **Это обязательное требование:** Без сохранения состояния процесса после каждого шага автоматическое восстановление невозможно.

*   **Какой механизм будет инициировать повторную обработку?**
    *   **Пуш-модель:** Немедленная повторная попытка внутри того же процесса, обрабатывающего операцию (с задержкой).
    *   **Пул-модель:** Отложенные задачи. Операция в статусе "retry" ставится в очередь (например, в RabbitMQ, Kafka с отложенными сообщениями или в таблицу БД, которую сканирует шедулер).
    *   **Шедулер:** Отдельный фоновый процесс (cron job), который периодически (каждую минуту) ищет в БД операции с `next_retry_time <= NOW()` и статусом `error` и пытается их обработать.

#### **3. Вопросы по идемпотентности и последствиям повторов:**

*   **Как гарантировать, что повторный вызов одного и того же шага не приведет к дублирующимся списаниям или иным побочным эффектам?**
    *   **Требуется реализация идемпотентности на всех ключевых шагах**, особенно при взаимодействии с АБС. Это должно быть ключевым требованием к интеграции с АБС (см. первый блок вопросов).
    *   **По каким критериям будет определяться, что шаг уже выполнен?** По `payment_id`? По уникальному идентификатору шага?

#### **4. Вопросы по границам автоматического восстановления и эскалации:**

*   **Когда автоматическое восстановление должно прекращаться и требовать ручного вмешательства?**
    *   После исчерпания всех попыток по стратегии.
    *   При получении определенных кодов ошибок от АБС (например, `account_blocked`).
    *   При внутренних ошибках приложения (например, ошибка кода, не связанная с интеграцией).
*   **Куда и как должна эскалировать такая ошибка?**
    *   Переход операции в статус `manual_review_required`.
    *   Отправка уведомления (алерт, email, тикет в Jira) команде поддержки/операторам.
    *   **Что должно быть в уведомлении?** Полный контекст: ID операции, история шагов, код ошибки, количество попыток.

#### **5. Вопросы по мониторингу и ручному вмешательству:**

*   **Какой интерфейс будет у оператора для управления "зависшими" операциями?**
    *   Просмотр списка операций в статусе `error` и `manual_review_required`.
    *   Возможность просмотреть детали ошибки, историю попыток.
    *   **Возможность ручного запуска повторной обработки** (кнопка "Retry") после того, как причина сбоя была устранена.
    *   Возможность принудительно завершить операцию как неуспешную.
*   **Нужны ли дашборды для мониторинга здоровья процесса?** (Графики: количество операций в ошибке, успешных повторов, основных ошибок по типам).

**Рекомендация по обсуждению (на примере):**

**"Давайте разберем на примере. Платеж прошел шаг 'Списание со счета в Core', но на шаге 'Отправка запроса в АБС' произошел таймаут.**
1.  **Как система должна понять, что списание уже прошло?** (Проверить статус в БД).
2.  **Как она должна понять, что в АБС платеж, возможно, *все-таки* дошел?** (Сделать запрос статуса в АБС по `payment_id`).

Ответы на эти вопросы позволят спроектировать отказоустойчивый процесс, основанный на паттернах **Saga** и **Idempotent Receiver**.

### **Ключевые вопросы по реализации идемпотентности**

**Цель:** Уточнить детали реализации, граничные условия и процессы ручного вмешательства для обеспечения корректной идемпотентной обработки.

#### **1. Вопросы по обработке исключительных ситуаций и ручного вмешательства (для PUT C2B):**

*   **Механизм `rpt_flag = 'Y'`:**
    *   **Кто и в каком интерфейсе выставляет этот флаг?** Оператор в панели управления Core? Или этот флаг приходит из Шлюза СБП в самом запросе?
    *   **Где должен проверяться этот флаг?** На входе в Core-метод, до проверки идемпотентности?
    *   **Каков полный сценарий обработки запроса с `rpt_flag = 'Y'`?**
        *   Должен ли он игнорировать существующую успешную операцию и всегда создавать новую проводку в АБС?
        *   Или он должен проверить, было ли отправлено авизо (`camt.054`) в первом случае, и отправить его только если не было?
        *   **Требуется ли для таких "принудительных" повторов отдельный логический путь, чтобы не нарушать стандартную логику идемпотентности?**

#### **2. Вопросы по консистентности данных и состоянию (для всех методов):**

*   **Где и как должны сохраняться ответы на запросы?** Требуется единый механизм (таблица в БД, например `idempotency_cache`), где будут храниться:
    *   Ключ идемпотентности (`uuid` для POST/PUT, `ips_27_operation_id` + `ips_105_clearing_date` для PUT C2B)
    *   Полный ответ, который был отправлен клиенту (ТСП)
    *   HTTP-статус этого ответа
    *   Статус обработки (например, `in_progress`, `completed`)
    *   Ответ, полученный от Шлюза СБП (для POST-запросов, на шаге 2)
*   **Как долго должны храниться эти записи?** Только в течение операционного дня? Или дольше (неделя, месяц)? Это важно для управления размером базы данных.

#### **3. Вопросы по конкурентности (для всех методов):**

*   **Как обрабатывать одновременные запросы с одинаковым `ID`?**
    *   Предполагается ли блокировка (lock) на время обработки первого запроса, чтобы последующие ждали его завершения и затем получили тот же результат?
    *   Или все concurrent-запросы начинают обработку, но только один из них выполняет "тяжелую" работу (вызов Шлюза СБП, антифрода), а остальные ждут ее результата?
    *   **Не приведет ли это к созданию очереди из hanging-запросов и исчерпанию лимитов соединений на веб-сервере?**

#### **4. Вопросы к интеграции с Шлюзом СБП (для POST-методов):**

*   **Является ли Шлюз СБП сам по себе идемпотентным для POST-запросов?**
    *   Если Core отправит два одинаковых POST-запроса в Шлюз (в случае, если ответ от Шлюза в первый раз был потерян), приведет ли это к созданию двух операций в НСПК?
    *   **Если да, то это переводит задачу из области идемпотентности прокси в область обеспечения идемпотентности на стороне Шлюза.** Требуется ли от Шлюза СБП аналогичный механизм по тому же `uuid`?

#### **5. Вопросы по обработке отрицательных ответов:**

*   **Определение "отрицательного ответа":** В требованиях сказано: все, что не 200/201/202 — отрицательный.
    *   **Как обрабатывать ответ `500 Internal Server Error` от Шлюза СБП?** Это временная ошибка (стоит повторить) или постоянная (стоит сразу вернуть ошибку клиенту)?
    *   **Как обрабатывать ответ `400 Bad Request`?** Это ошибка данных, ее повторение бессмысленно. Нужна ли более детальная классификация ошибок от Шлюза СБП?
*   **Если при повторном POST-запросе выясняется, что первый запрос завершился ошибкой на шаге 3 (Антифрод) или 4 (Финмон), нужно ли заново проходить эти шаги?** Или результат их работы тоже нужно кешировать по `uuid`?

#### **6. Вопросы по мониторингу и поддержке:**

*   **Как оператор сможет найти операцию по `ips_27_operation_id` или `uuid`?** Будет ли интерфейс для поиска и просмотра состояния обработки идемпотентных запросов?
*   **Нужно ли предусмотреть механизм принудительной очистки или инвалидации кеша идемпотентности?** Например, если выяснилось, что сохраненный ответ некорректен и его нужно перезаписать.

### 1. Для PUT-методов выгрузки проводок C2B (из Шлюза СБП в Core)

| :--- | :--- |

### 2. Для POST-методов (Инициация операций B2C и возвратов C2B)

**Проблема:** Повторный вызов с одним и тем же `uuid` создает новую операцию в НСПК, а не возвращает результат первой.

| :--- | :--- |
| **Ключ идемпотентности** | Параметр `ID` (uuid) в теле запроса. |
| **Логика обработки** | <ul><li>**Если на запрос с таким `ID` уже был отправлен ответ в ТСП:** <br> — **Вернуть** этот же сохраненный ответ.</li><li>**Если ответ в ТСП не был отправлен (или был ошибка):** <br> — Проверить, есть ли **ответ от Шлюза СБП** на этот `ID`.<br> — **Если ответ от Шлюза есть и он успешный:** <br> &nbsp;&nbsp;→ Пропустить повторный вызов Шлюза (шаг 2). <br> &nbsp;&nbsp;→ Выполнить оставшиеся шаги (Антифрод, Финмон) и отправить ответ в ТСП. <br> — **Если ответа от Шлюза нет или он ошибочный:** <br> &nbsp;&nbsp;→ Выполнить всю цепочку шагов **полностью** (1-5).</li></ul> |

**Итог:** Предложена сложная и умная система многоуровневого кеширования. Сохраняются результаты как промежуточных шагов (интеграции со Шлюзом), так и финальные. Это позволяет не просто избегать дублей, но и доисполнять прерванные цепочки действий.

| Аспект | Предложение по реализации |
| :--- | :--- |
| **Ключ идемпотентности** | Параметр `ID` (uuid) в теле запроса. |

| **Механизм** | Core должен выступать **прослойкой-буфером** между ТСП и Шлюзом СБП. Он абстрагирует ТСП от специфической реализации идемпотентности на стороне Шлюза. Core кеширует финальные ответы для ТСП. |

**Итог:** Предложено классическое кеширование финальных ответов, чтобы изолировать клиента (ТСП) от особенностей работы Шлюза СБП и гарантировать ожидаемое поведение.

## 🤖 **DeepSeek**

### Процесс установки баланса в BO по запросу из Core

#### 1. **Получение запроса**
- **Система:** Back-Office (BO) получает запрос от Core
- **Данные в запросе:** Список счетов с балансами для обновления
- **Формат:** `{ "accounts": [ {"account": "4070281000000001", "balance": "150000.50"}, {"account": "4070281000000002", "balance": "0"}, ... ] }`

#### 2. **Валидация счетов**
- **Проверка существования счетов:** BO проверяет наличие каждого счета из запроса в своей базе
- **Обработка несуществующих счетов:**
  - Если счет отсутствует в BO → возврат ошибки `"Счета"` для конкретного счета
  - Ошибка не прерывает обработку остальных счетов

#### 3. **Обработка балансов**
- **Удаление старых балансов:** Для каждого валидного счета из запроса удаляются все существующие балансы
- **Установка новых балансов:** 
  - Для счетов с переданным балансом устанавливается новое значение
  - **Важно:** Нулевой (`0`) и отрицательный баланс считаются допустимыми значениями

#### 4. **Блокировка счетов без информации**
- **Определение счетов:** Выявляются счета, которые есть в BO, но отсутствуют в запросе от Core
- **Установка запрета:** Для этих счетов устанавливается флаг/статус запрета на проведение операций
- **Логика:** "Нет информации о балансе = запрет операций"

#### 5. **Обработка ошибок записи**
- **Сценарий ошибки:** Если при записи баланса возникает ошибка
- **Действия:**
  1. Баланс удаляется в BO (откат к состоянию "нет информации")
  2. Возвращается ошибка `"Невозможность записи по счету"`
  3. По счету автоматически устанавливается запрет на операции

#### 6. **Формирование ответа**
- **Успешные операции:** Подтверждение обновления баланса
- **Ошибочные операции:** Детализация ошибок по счетам:
  - `"Счета"` - для несуществующих счетов
  - `"Невозможность записи по счету"` - при ошибках записи

#### 7. **Итоговое состояние системы**
- **Счета из запроса:** Имеют актуальные балансы (включая 0 и отрицательные)
- **Счета не из запроса:** Заблокированы для операций
- **Система согласована:** BO отражает точную картину балансов из Core

**Особенности процесса:**
- Идемпотентность: повторный запрос с теми же данными дает идентичный результат
- Атомарность на уровне счета: ошибка по одному счету не влияет на обработку других
- Жесткая привязка к данным Core: отсутствие счета в запросе = запрет операций

- 500 - при критической ошибке системы

#### **6. Требования к мониторингу и аудиту**

**FR-BO-012: Аудит операций**
- Система должна вести детальный аудит всех операций синхронизации:
  - sync_id
  - request_timestamp
  - processing_duration_ms
  - accounts_processed
  - accounts_failed
  - initiator_system (Core)

**FR-BO-013: Мониторинг статусов**
- Система должна предоставлять метрики для мониторинга:
  - Количество успешно обновленных счетов
  - Количество заблокированных счетов
  - Количество ошибок по типам
  - Время обработки запросов

---

#### **7. Требования к производительности**

**FR-BO-014: Производительность обработки**
- Система должна обрабатывать запросы с до 10,000 счетов за время не более 30 секунд
- Поддерживать одновременную обработку до 5 параллельных запросов
- Обеспечивать согласованность данных при параллельных обновлениях

**FR-BO-015: Отказоустойчивость**
- При частичном сбое БД система должна:
  - Обеспечивать целостность данных
  - Блокировать счета при невозможности обновления баланса
  - Возвращать детализированный статус обработки для каждого счета
