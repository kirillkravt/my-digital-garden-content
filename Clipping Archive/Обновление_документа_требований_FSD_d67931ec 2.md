## 🤖 **DeepSeek**

**Доработанный раздел FSD с учетом правок**

---

### **1. Бизнес-операции (BO) в режиме Stand-in**

**Описание процесса:**
- BO функционирует исключительно в режиме stand-in при недоступности АБС
- **Позитивные сценарии:**
  - Автоматическая обработка операций C2B (зачисление)
  - Проведение операций B2C (списание) при достаточном положительном остатке
- **Негативные сценарии:**
  - Блокировка операций B2C при отрицательном остатке
  - Возврат ошибок в Core при недостатке средств

---

### **2. Алгоритм работы с отрицательным остатком**

**Бизнес-правила:**
- Операции списания (B2C) разрешены только при положительном остатке
- Операции зачисления (C2B) разрешены при любом состоянии остатка
- **Процесс обработки отказа:**
  1. BO детектирует недостаточность средств
  2. BO возвращает ошибку в Core
  3. Core завершает операцию
  4. Core отправляет отказ ТСП через маппинг ответов

---

### **3. Процесс передачи счетов в BO**

**Текущее состояние:** Процесс не автоматизирован
**Процедура:** Ручное заведение счетов в BO согласно инструкции [ССЫЛКА НА ИНСТРУКЦИЮ]

---

### **4. Подключение новых клиентов**

**Процесс:**
1. Ручное создание сущности в BO (инструкция [ССЫЛКА])
2. Подключение к Core через API ТСП (Payer)
3. Настройка прав доступа и лимитов

---

### **5. Обработка "Запроса на подтверждение" с отрицательным ответом АБС**

**Поведение системы:** Описано в разделе "5.6 Обработка исключений"
- Core получает отрицательный ответ от АБС
- Операция маркируется как неуспешная
- Инициируется процесс нотификации участников

---

### **6. Переход между режимами онлайн/оффлайн**

**Процесс синхронизации остатков:**
- **Позитивный сценарий:** Успешная передача остатков в BO
- **Негативный сценарий:** Повторные попытки синхронизации при ошибках
- **Валидация:** Контроль целостности данных при смене режима

---

### **7. Логирование в Core**

**Реализация:** Базовая функциональность системы
**Детализация:** Описано в Maintenance Guide [ССЫЛКА]

---

### **8. Статус-коды для негативных сценариев**

**Добавляемые коды:**
- `5001` - Таймаут соединения с АБС
- `5002` - Нарушение идемпотентности
- `5003` - Недостаточность средств
- `5004` - Техническая ошибка BO

---

### **9. Обработка отсутствия ответа на холд от АБС**

**Процедура:**
1. Core детектирует таймаут ожидания ответа
2. Отправляется запрос отмены холда в АБС
3. ТСП получает уведомление об ошибке проведения операции
4. Операция маркируется как "Не выполнена"

---

### **10. Аварийное восстановление операций**

**Механизм:** Повторная обработка неуспешных шагов
- Автоматический ретрай отправки сообщений в АБС
- Контроль целостности данных при повторе
- Лимиты количества повторных попыток

---

### **11. Доработка раздела "5.6 Обработка исключений"**

**Добавляемые элементы:**
- Таблица кодов ошибок и действий системы
- Примеры сценариев обработки различных типов ошибок
- Процедуры финализации операций при технических сбоях
- Форматы уведомлений для ТСП

---

### **12. Взаимодействие с Антифрод (АФ) и Финмон (ФМ)**

**Поведение при технических ошибках:**
- **Повторные запросы:** 3 попытки с интервалами 5-10-30 секунд
- **Таймаут ожидания:** 60 секунд на ответ
- **Эскалация:** Переход в degraded mode при недоступности сервисов

---

### **Примечания:**
- Инструкции по ручным операциям вынесены в отдельные документы
- Детальные сценарии тестирования будут разработаны на основе данных требований
- Коды ошибок подлежат согласованию с техническими командами

Документ готов к использованию разработчиками и тестировщиками.
