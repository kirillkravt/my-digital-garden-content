### **Детализированный алгоритм**

#### **1. Таблица ограничений**
```sql
-- Таца для исключённых счетов
CREATE TABLE account_blacklist (
    account_number VARCHAR(34) PRIMARY KEY,
    reason VARCHAR(255),
    disabled_stages JSON -- ['camtGeneration', 'edoCamtDispatch']
);
```

#### **2. Алгоритм обработки шага с проверкой ограничений**
```python
def process_step(operation_id, stage_code):
    operation = get_operation(operation_id)
    
    # Проверка на чёрный список
    if is_blacklisted(operation.account_number, stage_code):
        update_stage_status(operation_id, stage_code, 'SKIPPED')
        return True  # Пропуск шага
        
    # Выполнение шага
    success = execute_stage(operation_id, stage_code)
    
    if not success:
        update_stage_status(operation_id, stage_code, 'RETRY_PENDING')
        return False
        
    return True

def is_blacklisted(account_number, stage_code):
    blacklist = get_blacklist(account_number)
    return blacklist and stage_code in blacklist.disabled_stages
```

#### **3. Запрос планировщика с учётом ограничений**
```sql
-- Поиск операций для повторной обработки (исключая чёрный список)
SELECT 
    t.operation_id,
    t.account_number,
    s.stage_code,
    s.retry_count
FROM t_sbp_trans t
JOIN t_sbp_stage_result s ON t.operation_id = s.operation_id
LEFT JOIN account_blacklist ab ON t.account_number = ab.account_number
WHERE s.status = 'RETRY_PENDING'
  AND s.retry_count < 3
  AND s.last_retry_time + INTERVAL '5 minutes' < NOW()
  AND (
    ab.account_number IS NULL 
    OR NOT(s.stage_code = ANY(ab.disabled_stages))
  );
```

#### **4. Ручной скрипт для принудительного перезапуска**
```sql
-- Скрипт устанавливает статус для перезапуска
UPDATE t_sbp_stage_result 
SET status = 'RETRY_PENDING',
    retry_count = 0,
    last_retry_time = NULL
WHERE operation_id IN (...)
  AND stage_code IN ('camtGeneration', 'edoCamtDispatch')
  AND status != 'SKIPPED';
```

### **Логика работы**

1. **При нормальном выполнении**: система проверяет каждый счёт перед выполнением `camtGeneration` и `edoCamtDispatch`
2. **При ошибке**: автоматически ставится `RETRY_PENDING` (только для разрешённых счетов)
3. **Планировщик**: обрабатывает только операции, не попадающие под ограничения
4. **Ручное вмешательство**: скрипт может установить `RETRY_PENDING`, который будет обработан планировщиком

### **Структура таблицы «крана»**

```sql
CREATE TABLE avizo_flow_control (
    id SERIAL PRIMARY KEY,
    account_number VARCHAR(34) NOT NULL,          -- конкретный счёт
    -- или scope VARCHAR(50) для групповых правил

    retry_interval INTERVAL DEFAULT '5 minutes',  -- интервал между повторами

    updated_at TIMESTAMP DEFAULT NOW()
);

-- Индексы
CREATE INDEX idx_avizo_flow_account ON avizo_flow_control(account_number);
CREATE INDEX idx_avizo_flow_enabled ON avizo_flow_control(enabled) WHERE enabled = true;
```

### **Алгоритм работы планировщика с «краном»**

```sql
-- Запрос планировщика: какие операции нужно повторить
SELECT 
    t.operation_id,
    t.account_number,
    s.stage_code,
    s.retry_count,
    s.last_retry_time,
    fc.retry_interval,
    fc.max_retries
FROM t_sbp_trans t
JOIN t_sbp_stage_result s ON t.operation_id = s.operation_id
LEFT JOIN avizo_flow_control fc ON t.account_number = fc.account_number
WHERE s.status = 'RETRY_PENDING'
  AND (fc.enabled IS NULL OR fc.enabled = true)  -- «кран» открыт
  AND s.retry_count < COALESCE(fc.max_retries, 3)
  AND (s.last_retry_time + COALESCE(fc.retry_interval, '5 minutes') < NOW())
  AND (
    fc.account_number IS NULL 
    OR NOT(s.stage_code = ANY(fc.disabled_stages))
  );
```

### **Матрица решений с «краном»**

| **Ситуация** | **Состояние крана** | **Действие системы** |
|--------------|---------------------|---------------------|
| Ошибка шага | `enabled = true` | Статус `RETRY_PENDING` → планировщик повторит |
| Ошибка шага | `enabled = false` | Статус `BLOCKED` → пропуск, счётчик blocked_count++ |
| Ручной скрипт | Любое | Меняет `enabled` или принудительно ставит `RETRY_PENDING` |
| Превышение лимита | `retry_count >= max_retries` | Статус `FAILED` → уведомление |

Предварительные требования
На этапе выполнения операции планировщик должен отслеживать неуспешные шаги со статусом выполнения retry_pending, статусом транзакции pending и счетчиком повторных попыток обработки меньше максимального значении (при наличии такого счетчика для шага). Если счетчика нет, то проверять по статусам

В чем особенность процесса сейчас:
есть общий процесс выполнения операции, который выполняется последовательно шаг за шагом.
Есть некие "контрольные точки" которые должны быть выполнены обязательно для установки статуса транзакции "completed" это шаги по отправке результата в том или ином виде (callback клиенту, camt в эдо, уведомление об успешной операции в АБС)

Сейчас планировщим умеет отслеживать статусы и количество попыток перезапуска процесса, но не умеет выполнять конкретные шаги без выполнения остальной бизнес-логики т.е. может вернуться на ошибочный шаг в нужном статусе и перезапустить с него и все последующие шаги.

Это неправильно поведение  т.к. например callback при неуспешной попытке отправки в ТСП начинает обрабатываться механизмом ретраев повторно в асинхронном режиме и процесс считает этот шаг за пройденный и дальше отправляет camt  и уведомление. Но когда сработает планировщик, то нужно чтобы отправился только callback изолированно (без выполнения последующих шагов если они были выполнены ранее)

Еще есть сложность, что при прохождении "контрольных точек" сейчас устанавливается и статус самой операции. Это тоже неправильно т.к. планировщик может пропустить ошибочно завершенные процессы (например, callback не был отправлен и статус шага и транзакции негативные, но последующие шаги были успешные и затерли статус операции на completed

Есть предложение, добавить систему флагов на контрольных точках, чтобы конкретный шаг не мог повлиять на весь статус а только на свой флаг. А уже в конце процесса поставить проверку флагов и положительный статус может быть установлен только при поднятии всех важных флагов.

| Планировщик запускает всю цепочку шагов | Ненужное дублирование операций | Ошибки данных, конфликты, нагрузка |
| Статус операции перезаписывается последним шагом | Потеря информации о неуспешных контрольных точках | Финансовые риски, неотправленные уведомления |
| Отсутствие изоляции шагов | Нельзя перезапустить только callback без camt | Нарушение SLA, дублирование документов |
| Жёсткая последовательность | Нельзя пропустить успешные шаги при ретрае | Нерациональное использование ресурсов |

---

## **2. Требования к функционалу планировщика**

### **2.1. Основная задача планировщика**
**Описание:** Планировщик должен **изолированно перезапускать только неуспешные шаги** без выполнения всей последующей бизнес-логики.

**Требования:**
1. **Селективность ретраев:** Возможность указывать, какие шаги перезапускать (`callbackReceiving`, `camtGeneration`, `edoCamtDispatch`, `successNotification`)
2. **Проверка завершённости:** Перед перезапуском шага проверять, не был ли он уже успешно выполнен
3. **Исключение дублирования:** Не запускать шаги, которые уже в статусе `COMPLETED`

---

### **2.2. Система флагов контрольных точек**
**Описание:** Вместо единого статуса операции — система независимых флагов для ключевых шагов.

**Требования:**
1. **Таблица флагов:**
```sql
CREATE TABLE operation_checkpoints (
    operation_id VARCHAR(50),
    checkpoint_code VARCHAR(50),  -- 'callback_sent', 'camt_generated', 'camt_sent', 'notification_sent'
    status VARCHAR(20),           -- 'PENDING', 'COMPLETED', 'FAILED'
    attempt_count INTEGER,
    last_attempt TIMESTAMP,
    PRIMARY KEY (operation_id, checkpoint_code)
);
```

2. **Логика установки флагов:**
   - Каждый ключевой шаг управляет только своим флагом
   - Флаг `COMPLETED` устанавливается только при успешном выполнении
   - Флаг `FAILED` при исчерпании попыток

3. **Финальная проверка:**
```sql
-- Операция считается успешной только если:
SELECT COUNT(*) = 4 FROM operation_checkpoints 
WHERE operation_id = ? 
  AND status = 'COMPLETED';
-- (4 = все обязательные контрольные точки)
```

---

### **2.3. Ветвление процесса и изоляция**
**Описание:** Процесс должен ветвиться на независимые потоки для разных типов уведомлений.

**Требования:**
1. **Архитектура процессов:**
```
Основной процесс (выполнение операции)
    ├── Поток 1: Callback ТСП
    ├── Поток 2: CAMT в ЭДО
    ├── Поток 3: Уведомление в АБС
    └── Поток 4: Логирование
```

2. **Правила изоляции:**
   - Неуспех в одном потоке не блокирует другие
   - Планировщик работает с каждым потоком независимо
   - Каждый поток имеет свои лимиты попыток

---

### **2.4. Алгоритм работы планировщика**

**Требования к логике:**

```python
def scheduler_tick():
    # 1. Найти операции с неуспешными контрольными точками
    failed_checkpoints = get_failed_checkpoints()
    
    for checkpoint in failed_checkpoints:
        # 2. Проверить лимиты попыток
        if checkpoint.attempt_count >= checkpoint.max_retries:
            set_final_failure(checkpoint)
            continue
            
        # 3. Проверить таймаут
        if not is_time_for_retry(checkpoint):
            continue
            
        # 4. Изолированно выполнить только этот шаг
        if checkpoint.code == 'callback_sent':
            execute_only_callback(checkpoint.operation_id)
        elif checkpoint.code == 'camt_generated':
            execute_only_camt_generation(checkpoint.operation_id)
        # ...
        
        # 5. Обновить статус флага
        update_checkpoint_status(checkpoint)
    
    # 6. Проверить финальные статусы операций
    update_operation_final_statuses()
```

---

### **2.5. Управление статусами операций**

**Требования:**
1. **Статус операции** = агрегация статусов контрольных точек
2. **Возможные статусы операции:**
   - `PENDING` — не все контрольные точки завершены
   - `COMPLETED` — все контрольные точки `COMPLETED`
   - `PARTIALLY_FAILED` — часть контрольных точек `FAILED`, но операция прошла
   - `FAILED` — критическая контрольная точка провалена

3. **Триггеры обновления:**
   - При изменении любого флага → пересчёт статуса операции
   - Автоматическое уведомление при `PARTIALLY_FAILED`

---

### **2.6. Нефункциональные требования**

| **Требование** | **Метрика** | **Цель** |
|----------------|-------------|----------|
| **Изоляция шагов** | 0% дублирования успешных шагов | Качество данных |
| **Полнота контрольных точек** | 100% охват ключевых событий | Контроль рисков |
| **Гибкость конфигурации** | Настройка без перезапуска системы | Оперативность |
| **Мониторинг** | Дашборд статусов контрольных точек | Прозрачность |
| **Производительность** | < 1 сек на обработку очереди | SLA |

### **До:**

### **После:**
- Планировщик → конкретный шаг → изоляция → точные флаги → корректный статус

### **Бизнес-выгоды:**
1. **Снижение рисков** пропуска критичных уведомлений

## **Обновлённые требования к планировщику (поэтапная реализация)**

### **1. Текущий этап: разделение основного процесса и callback**

**Архитектура процессов (первая версия):**
```
Операция
    ├── Основной поток (шаги до callback)
```

**Требования к реализации:**

1. **Две независимые очереди обработки:**

2. **Разделение данных:**
```sql

    operation_id,
    main_status,      -- 'PENDING', 'EXECUTED', 'FAILED'
    callback_status,  -- 'PENDING', 'SENT', 'FAILED'
    final_operation_status -- агрегация (только когда оба потока завершены)
)

-- Детализация шагов callback
```

### **2. Алгоритм работы планировщика (первая версия)**

```python
def scheduler_tick():
    # 1. Проверить callback-очередь (приоритет)
    pending_callbacks = get_pending_callbacks_from_cache_or_db()
    
    for cb in pending_callbacks:
        if should_retry_callback(cb):
            execute_isolated_callback(cb.operation_id)
            # Обновляем только callback-статус
            update_callback_status(cb.operation_id)
    
    # 2. Проверить основной процесс (если callback уже отправлен или не требуется)
    pending_main = get_pending_main_operations()
    
    for op in pending_main:
        if is_callback_sent_or_skipped(op.operation_id):
            execute_main_process(op.operation_id)
            update_main_status(op.operation_id)
    
    # 3. Вычислить финальный статус операции
    update_final_statuses()
```

### **3. Использование кеша (предварительные требования)**

**Что хранить в кеше:**
1. **Статусы callback** (часто обновляются, много чтений)
   - Ключ: `callback:status:{operation_id}`
   - Значение: `{status: 'PENDING', attempts: 2, last_attempt: ts}`

2. **Конфигурация ретраев** (настройки системы)
   - Ключ: `config:retry:callback`
   - Значение: `{max_attempts: 5, interval_sec: 300, timeout_sec: 3600}`

3. **Чёрный список счетов** (для быстрого доступа)
   - Ключ: `blacklist:accounts`
   - Значение: `['ACC001', 'ACC002']`

**Стратегия кеширования:**
- **Write-through**: при обновлении в БД → сразу в кеш
- **TTL**: 5 минут для статусов, 1 час для конфигураций
- **Fallback to DB**: если кеш недоступен → читаем из БД

### **4. Система флагов (упрощённая, под этап 1)**

```sql
-- Таблица контрольных точек (только для этапа 1)
CREATE TABLE operation_flags (
    operation_id VARCHAR(50) PRIMARY KEY,
    -- Основные флаги
    main_process_completed BOOLEAN DEFAULT FALSE,
    callback_sent BOOLEAN DEFAULT FALSE,
    
    -- Дополнительные (заглушки для будущего)
    camt_generated BOOLEAN DEFAULT FALSE,
    notification_sent BOOLEAN DEFAULT FALSE,
    
    -- Статус агрегации
    is_finalized BOOLEAN DEFAULT FALSE,
    final_status VARCHAR(20)
);
```

**Логика агрегации:**
```sql
-- Финальный статус вычисляется только когда is_finalized = TRUE
UPDATE operation_flags 
SET final_status = CASE
    WHEN main_process_completed = TRUE 
      AND callback_sent = TRUE THEN 'COMPLETED'
    WHEN main_process_completed = FALSE THEN 'FAILED'
    ELSE 'PARTIALLY_FAILED'
  END,
  is_finalized = TRUE
WHERE is_finalized = FALSE
  AND (main_process_completed IS NOT NULL 
       AND callback_sent IS NOT NULL);
```

### **5. Правила изоляции (для этапа 1)**

| **Ситуация** | **Действие планировщика** | **Что обновляется** |
|--------------|--------------------------|---------------------|
| Callback не отправлен | Запустить только callback-поток | `callback_sent`, кеш статуса |
| Основной процесс упал | Запустить основной поток | `main_process_completed` |
| Оба упали | Запустить оба (но в разное время) | Оба флага |
| Callback успешен, основной упал | Только основной поток | `main_process_completed` |

**Важно:** Планировщик НЕ запускает callback, если `callback_sent = TRUE` (даже если основной процесс перезапускается).
