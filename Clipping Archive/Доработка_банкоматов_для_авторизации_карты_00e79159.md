## 🤖 **DeepSeek**

**Документ требований к доработке (BRD)**  
**Проект:** Поддержка функционала дополнительной авторизации карты при оплате мобильной связи наличными в банкоматах  
**Версия:** 1.0  
**Дата:** 30.01.2026  

---

### 1. Введение  
#### 1.1. Цель документа  
Формализовать требования к доработке сценариев банкоматов для поддержки дополнительной авторизации карты клиента при оплате мобильной связи наличными.  

#### 1.2. Контекст  
Банк внедрил требование об обязательной идентификации клиента по карте для операций оплаты мобильной связи наличными в банкоматах. На новых банкоматах (парк Tieto) функционал уже реализован. Задача — обеспечить работу этого функционала на банкоматах групп **Luno 101** и **301**, использующих хост-систему Исполнителя.  

---

### 2. Основной бизнес-процесс  
#### 2.1. Текущий процесс (без изменений)  
1. Клиент выбирает оплату мобильной связи.  
2. Если выбран способ оплаты **«наличными»**, система должна выполнить дополнительную авторизацию по карте клиента.  

#### 2.2. Целевой процесс (после доработки)  
1. Клиент выбирает оплату мобильной связи → способ «наличными».  
2. Система запрашивает карту клиента и проводит её авторизацию.  
3. После успешной авторизации клиент вносит наличные.  
4. Система выполняет два шага:  
   - **Первая операция**: зачисление наличных на карту (депозит).  
   - **Вторая операция**: списание суммы с карты для оплаты мобильной связи.  
5. Клиент получает чек и карту.  

---

### 3. Требования к доработкам  
#### 3.1. Изменения в сценарии банкомата  
- Необходимо добавить **новые стейты (states)** в сценарий Luno 101/301 для обработки ветвления:  
  - **Стейт проверки типа идентификации** (ветвление по наличию карты).  
  - **Стейт приёма карты** в рамках текущей транзакции.  
  - **Стейт отображения HTML-страниц** для информирования клиента.  
- Обновить таблицы `STATE_DEF` и `STATE_TRANSITION` в соответствии с логикой Tieto.  

#### 3.2. Логика обработки операций  
- При оплате наличными система должна:  
  1. Создать контекст операции «оплата мобильной связи».  
  2. Выполнить операцию **«пополнение карты наличными»**, сохранив ID операции.  
  3. Передать управление в дополнительный вызов авторизационного модуля (AW).  
  4. В AW проверить контекст:  
     - Если контекст «оплата мобильной связи» — передать сумму в буфер и перейти на ветку оплаты по карте.  
     - Если контекст «пополнение карты» — завершить операцию.  
  5. Выполнить транзакцию «оплата мобильной связи» с карты.  

#### 3.3. Данные для интеграции  
- Необходимо получить от Банка:  
  - Актуальные дампы стейтов с продовых УС Tieto (номера стейтов 690–697, 944–948).  
  - Примеры успешных и проблемных логов STF/NDC с Tieto.  
  - Схему взаимодействия между NDC и AW при обработке двухшаговой операции.  

---

### 4. Описание ограничений и допущений  
#### 4.1. Ограничения  
- Изменения затрагивают только сценарии **Luno 101 и 301**.  
- Функционал должен быть обратно совместим с существующими операциями.  
- Логика обработки наличных должна соответствовать регуляторным требованиям (идентификация клиента).  

#### 4.2. Допущения  
- Банк предоставит корректные данные по стейтам Tieto и форматам взаимодействия.  
- Тестирование будет проводиться на Host PreProd с возможностью отката изменений.  
- Ошибки, выявленные на этапе тестирования (например, синий экран после внесения наличных), будут исправляться в рамках отладки, а не как изменения требований.

### 6. Критерии приемки  
- Оплата мобильной связи наличными с авторизацией карты работает на Luno 101/301 без сбоев.  
- Обе операции (депозит и списание) отражаются в отчётах и чеках корректно.  
- Функционал не влияет на другие операции банкомата.

     - Выполняется переход на ветку **оплаты по карте** (выход 6).
8. **Оплата услуги**:
   - NDC сценарий выполняет транзакцию «оплата мобильной связи».

## 🤖 **DeepSeek**

Лучший способ оформлять простой текстовый документ зависит от контекста, но есть универсальные принципы. Вот пошаговое руководство:

## 📝 **Базовые принципы оформления**

### 1. **Структура документа**
```
[Название документа]                 # Центрирование, жирный, крупный шрифт
[Подзаголовок/версия]               # Меньше шрифтом, обычное начертание

1. ВВЕДЕНИЕ                         # Уровень 1 заголовка
   [Текст раздела...]

1.1. Подраздел                      # Уровень 2 заголовка
   [Текст подраздела...]

1.1.1. Детализация                  # Уровень 3 заголовка
```

### 2. **Использование заголовков**
- **Уровень 1:** Главные разделы (1., 2., 3.)
- **Уровень 2:** Подразделы (1.1., 1.2.)
- **Уровень 3:** Подпункты (1.1.1., 1.1.2.)
- **Визуальное выделение:** жирный шрифт, отступы

### 3. **Форматирование текста**
```
**Жирный текст** — для ключевых терминов, названий
*Курсив* — для акцента, иностранных слов
• Маркированные списки
1. Нумерованные списки (для шагов, этапов)
```

### 4. **Отступы и выравнивание**
- **Абзацы:** отступ первой строки или пустая строка между
- **Выравнивание:** по ширине или по левому краю
- **Межстрочный интервал:** 1.5 или двойной для читаемости

## 📋 **Типовые разделы документа**

### Пример структуры технического/делового документа:
```
ТИТУЛЬНЫЙ ЛИСТ
1. Введение
   1.1. Цель документа
   1.2. Область применения
   1.3. Определения и сокращения
2. Основная часть
   2.1. [Раздел 1]
   2.2. [Раздел 2]
3. Заключение
4. Приложения
5. Список изменений (если документ версионируется)
```

### Пример структуры отчета/анализа:
```
КРАТКОЕ СОДЕРЖАНИЕ (аннотация)
1. Контекст и проблема
2. Методология
3. Результаты
4. Выводы
5. Рекомендации
6. Приложения (данные, графики)
```

## 🎨 **Визуальные элементы**

### Таблицы (в простом тексте):
```
+----------------+------------------+
| Колонка 1      | Колонка 2        |
+----------------+------------------+
| Данные         | Данные           |
| Ещё данные     | Ещё данные       |
+----------------+------------------+
```

### Блоки для важной информации:
```
ВАЖНО: Это критическая информация
────────────────────────────────────
[Текст важного замечания]
────────────────────────────────────
```

```
ПРИМЕЧАНИЕ: Дополнительная информация
```

## 💡 **Практические советы**

### Для разных типов документов:
1. **Техническая документация:**
   - Четкая иерархия
   - Нумерация всех элементов
   - Глоссарий в начале

2. **Деловые документы:**
   - Исполнитель/заказчик в шапке
   - Дата и версия
   - Контактная информация

3. **Отчеты:**
   - Резюме в начале
   - Выводы отдельным разделом
   - Визуализация данных

### Что избегать:
- ❌ Слишком много уровней вложенности (больше 3-4)
- ❌ Разные стили оформления в одном документе
- ❌ Слишком мелкий/крупный шрифт
- ❌ Отсутствие оглавления в длинных документах

## ✅ **Чек-лист перед отправкой**
- [ ] Проверена орфография и пунктуация
- [ ] Единообразие форматирования
- [ ] Все разделы пронумерованы
- [ ] Есть контактная информация автора
- [ ] Указана дата и версия документа
- [ ] Соответствие корпоративному стилю (если требуется)

**Ключевое правило:** Оформление должно помогать чтению, а не мешать ему. Чем сложнее документ, тем важнее четкая структура и визуальная иерархия.

## 💡 **Практические советы для Notepad++**

### Для лучшей читаемости:

- Выделить + `Ctrl+Shift+U` — верхний регистр (для заголовков)
