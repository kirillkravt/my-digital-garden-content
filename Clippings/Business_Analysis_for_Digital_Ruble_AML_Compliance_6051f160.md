## 1. Предварительный анализ и структурирование входных данных

Прежде чем писать FSD, я бы выполнил следующие действия:

### 1.1. Выделил типы требований
В вашем документе явно видны:
- **Нормативные требования** (ссылки на 115-ФЗ, 764-П, 655-П, указания ЦБ) — они обязательны.
- **Функциональные требования** (автоматические проверки по спискам, блокировки, отказы).
- **Открытые вопросы** (выделены как «Вопрос», «Вопросы реализации»).
- **Референсная реализация** (описание того, как сейчас работает АБС — проверки 43, 41, 38, 34, 33, 27, 23).
- **Отчеты пост-контроля** (200998, 10048106 и др.) — их нужно переосмыслить для цифрового рубля.

### 1.2. Составил глоссарий (ключевые сущности)
Чтобы FSD был понятен и разработчикам, и тестировщикам, я бы зафиксировал:
- **СЦР** — счет цифрового рубля (на платформе ЦБ).
- **ПлЦР** — платформа цифрового рубля (оператор — ЦБ).
- **Участник ПлЦР** — банк (вы).
- **Клиент** — физ/юр лицо, открывшее СЦР.
- **Контрагент** — получатель/отправитель по операции в цифровых рублях.
- **Операция в СЦР** — пополнение, перевод, вывод.
- **Модуль Комплаенса** — то, что вы проектируете.

## 2. Методология работы над FSD

Я бы использовал **смешанный подход**:  
- **Use Case-driven** для операционных сценариев (открытие счета, перевод, пост-контроль).  
- **Decision tables** для логики проверок по спискам (включая проверку назначения платежа).  
- **Data mapping** для интеграции с ПлЦР, СМЭВ, ЗСК, Росфинмониторингом.

### 2.1. Применил бы следующие артефакты внутри FSD:
- **Диаграмма контекста** (где модуль ПОД/ФТ внутри банка и его связи с ПлЦР, АБС, справочниками, Росфинмониторингом).
- **Диаграммы активностей** для каждого типа проверки (предварительный контроль, пост-контроль).
- **Таблица правил** для каждого справочника (когда блокировать, когда на ручную проверку, когда только уведомлять).
- **Спецификация интерфейсов** (входящие запросы от ПлЦР, исходящие уведомления, выгрузка в АО Комита).

## 3. План работ по превращению требований в FSD

### Шаг 1. Уточнить открытые вопросы (до написания FSD)

Я бы составил список вопросов к заказчику/эксперту ПОД/ФТ:

| Вопрос из документа | Что нужно уточнить для FSD |
|---------------------|----------------------------|
| Проверка с учетом информации в назначении платежа | Какие именно поля в назначении платежа проверять? Точное совпадение или по маске/регулярному выражению? |
| Настройки алгоритмов по ОПОК (655-П, экспортеры) | Где хранить настройки (БД, конфиг-файл)? Кто и как меняет их без перекомпиляции? |
| Отправка сообщений в Росфинмониторинг | Какие форматы (FO, XML)? Через АО Комиту — нужен API или выгрузка файлов? |
| Формирование уведомления клиенту об отказе | Шаблон уведомления? Каналы (СЦР, e-mail, личный кабинет)? |
| Загрузка заявлений на бумаге | OCR или ручной ввод? Какие поля из бумаги идут в модуль? |

### Шаг 2. Определил границы модуля ПОД/ФТ по СЦР

**Входит в FSD:**
- Проверки при открытии СЦР / доступе без открытия.
- Проверки при пополнении, переводе, выводе.
- Формирование ОПОК и сомнительных операций.
- Приостановка/отказ/заморозка.
- Пост-контроль (отчеты, сверки).
- Интеграция с ПлЦР (получение уведомлений, отправка решений).

**Не входит (но зависит от внешних систем):**
- Сама платформа ЦР (ЦБ).
- АО Комита (шлюз в Росфинмониторинг).
- СМЭВ (проверка паспортов) — но мы вызываем.

### Шаг 3. Построил логику проверок в виде таблицы (пример для FSD)

| Тип проверки | Источник данных | Совпадение с кем/чем | Действие |
|--------------|----------------|----------------------|-----------|
| Террористы/экстремисты | Перечень (ежедневно) | Клиент, Контрагент, поле «назначение» | Отказ + уведомление в РФМ + блокировка |
| 764-П (отказы в открытии) | Реестр | Клиент | Отказ |
| ЗСК (средний риск) | Платформа ЗСК (ежедневно) | Контрагент (исходящий) | Ручная проверка (код 33) |
| ЗСК (высокий риск) | Платформа ЗСК | Клиент или контрагент | Блокировка входящих и исходящих |

| Исполнительные листы | Справочник | Клиент, контрагент, назначение | Приостановка |

> В FSD я бы для каждого справочника указал: **формат импорта, периодичность обновления, поля сравнения, алгоритм (exact match / fuzzy), результат**.

### Шаг 4. Опираясь на АБС, спроектировал аналоги для СЦР

В FSD я бы создал раздел **«Маппинг проверок из АБС в СЦР»**:

| Код проверки в АБС | Назначение | Реализация для СЦР |
|---------------------|------------|--------------------|
| 43 | ОФМ на исходящие | При переводе с СЦР на другой СЦР или банк.счет |
| 34 (условные контроли) | Произвольные правила | Конфигурируемый движок правил (например, сумма > 500 тыс. руб. на физ.лицо) |
| 27 | Нежелательные организации (назначение платежа) | Проверка текста перевода по справочнику иноагентов/экстремистов |
| 33 (ЗСК) | Высокий/средний риск | Ежедневная выгрузка из Платформы ЗСК в модуль |

### Шаг 5. Описал операции, подлежащие обязательному контролю (ОПОК)

Для FSD я бы перевел вашу таблицу в структурированный вид:

- Код 4005 — новые юрлица (<3 мес) — пополнение/списание СЦР.
- Код 4013/4014 — драгметаллы (с 2025) — при переводе на/с ювелиров.
- Код 5020/5021 — физлица с инвестиционными драгметаллами.
- Код 7001/7004 — террористы / заблокированные лица (включая связанные юрлица).

**Для каждого кода в FSD указать:**
- Триггер (вид операции СЦР).
- Условия (сумма, сторона, период).
- Формирование сообщения в РФМ (код вида операции 115-ФЗ).

### Шаг 6. Спроектировал интерфейс с ПлЦР и Росфинмониторингом

**От модуля ПОД/ФТ к ПлЦР:**
- Уведомление об отказе в открытии СЦР.
- Уведомление об отказе в исполнении перевода.
- Расторжение договора.

**От ПлЦР к модулю:**
- Уведомления об операциях (пополнение, перевод, вывод).
- Запросы на расширенную выписку (по запросу РФМ).

**К АО Комита / РФМ:**
- Выгрузка сообщений (ОПОК + сомнительные).
- Формат: по API или S3/сетевые папки.

### Шаг 7. Учел пост-контроль и ручные справочники

В FSD обязателен раздел **«Администрирование модуля»**:
- Возможность сотруднику ОФМ вручную добавить клиента/контрагента в черный список.
- Загрузка реестров (ЗСК, 764-П, экстремисты) через UI или автоматически.
- Формирование отчетов по сверке (например, «Клиенты с высоким риском на дату»).
- Интерфейс ручного просмотра и решения по операциям, попавшим на проверку (коды 33, 34, 27).

## 4. Структура итогового документа FSD (пример оглавления)

1. **Введение**
   - Цель документа
   - Область применения (СЦР, модуль ПОД/ФТ)
   - Нормативные ссылки (115-ФЗ, 764-П, 655-П, указания ЦБ)
2. **Глоссарий и сокращения**
3. **Контекстная диаграмма и роли**
   - Банк-участник, ПлЦР, Клиент, РФМ, АО Комита, СМЭВ
4. **Функциональные требования**
   1. Проверки при открытии СЦР / предоставлении доступа
       - Таблица по каждому справочнику (источник, периодичность, действие)
       - Особое условие: проверка назначения платежа
   2. Проверки при проведении операций (пополнение/перевод/вывод)
       - Предварительный контроль (аналоги кодов 43,41,38,34,33,27,23)
       - Ручная проверка (вкладки, как в АБС)
   3. Выявление ОПОК (таблица по кодам 40,50,60,70,71,80,90)
   4. Выявление сомнительных операций (по МР ЦБ, 655-П, экспортеры)
   5. Взаимодействие с ПлЦР (отказы, приостановки, заморозка)
   6. Взаимодействие с РФМ (формирование сообщений, выгрузка в Комиту)
   7. Пост-контроль (отчеты, сверки, импорт реестров)
5. **Нефункциональные требования**
   - Производительность (проверка < 1 сек)
   - Доступность (24/7)
   - Аудит (логи всех решений)
6. **Требования к интеграции**
   - СМЭВ (паспорта)
   - Платформа ЗСК (ежедневный импорт)
   - ПлЦР (API уведомлений)
   - АО Комита (выгрузка)
7. **Требования к данным**
   - Справочники (форматы, периодичность)
   - Хранение результатов проверок
8. **Пользовательские интерфейсы (если есть)**
   - Рабочее место ОФМ (ручная проверка, загрузка справочников)
9. **Сценарии тестирования (примеры)**
   - Клиент в 764-П → отказ в открытии
   - Перевод с назначением, содержащим иноагента → блокировка
10. **Открытые вопросы (перенесенные из требований)**

## 3. Итоговая оценка готовности исходного документа

| Аспект | Готовность | Комментарий |
|--------|------------|--------------|
| **Перечень того, что нужно проверять** | ✅ 90% | Есть почти все списки |
| **Действия при срабатывании** | ✅ 70% | Отказ/блокировка/ручная проверка — есть, но нет приоритетов |
| **Технические форматы** | ❌ 10% | Нет API, нет XML-схем, нет протоколов |
| **Логика проверки назначения платежа** | ❌ 5% | Только упоминание, без деталей |

## Что остаётся закрыть из внутренних источников

Несмотря на хорошую нормативную базу, следующие вещи **не публикуются ЦБ в открытом доступе**:

1. **Конкретный XML-формат ФЭС для отправки в Росфинмониторинг** — это закрытая документация, которую получают участники информационного обмена.

3. **Логика существующих отчетов в АБС** (200998, 10048023 и др.) — внутренняя разработка банка.
4. **Полные форматы справочников** (ЗСК, 764-П) — частично открыты, частично требуют запроса в ЦБ.
