Функциональные требования к идемпотентности методов Core1. Требования к POST методам1.1. Общие требованияFR-POST-001: Система Core должна обеспечивать обработку повторных POST-запросов как идемпотентных операцийFR-POST-002: Ключом идемпотентности для POST-запросов должен выступать параметр ID (uuid) из тела запроса1.2. Логика обработки повторных запросовFR-POST-010: При получении POST-запроса система должна проверять наличие предыдущего ответа для ТСП с таким же IDFR-POST-011: Если для данного ID существует предыдущий положительный ответ (HTTP 200, 201, 202) → система должна вернуть тот же ответ без выполнения бизнес-логикиFR-POST-012: Если предыдущий ответ был отрицательным или отсутствует → система должна проверить наличие ответа от Шлюза СБП для данного IDFR-POST-013: Если от Шлюза СБП был получен положительный ответ → выполнить только шаги 3-5 (антифрод, финмон, ответ ТСП) без повторного проксирования в ШлюзFR-POST-014: Если от Шлюза СБП ответ отрицательный или отсутствует → выполнить полную обработку запроса (шаги 1-5)1.3. Обработка конкурентных запросовFR-POST-020: При одновременной обработке нескольких запросов с одинаковым ID система должна гарантировать отправку сформированного ответа на все инициированные запросы2. Требования к PUT методам2.1. Общие требованияFR-PUT-001: Система Core должна обеспечивать идемпотентную обработку PUT-запросовFR-PUT-002: Ключом идемпотентности для PUT-запросов должен выступать параметр ID (uuid) из тела запросаFR-PUT-003: Для операций СБП дополнительным ключом должен выступать связка ips_27_operation_id + ips_105_clearing_date2.2. Логика обработки операций СБПFR-PUT-010: При получении PUT-запроса система должна проверять наличие уже обработанного запроса с таким же ips_27_operation_id и ips_105_clearing_dateFR-PUT-011: Если запрос с такими параметрами уже обработан со статусом 200 → вернуть положительный ответ (200) без инициации нового процесса обработкиFR-PUT-012: Если запрос с такими параметрами существует но имеет статус ≠ 200 → инициировать процесс обработки заново2.3. Обработка ручной повторной выгрузкиFR-PUT-020: Система должна поддерживать специальный режим обработки для ручной повторной выгрузки с признаком rpt_flag = YFR-PUT-021: В режиме rpt_flag = Y система должна гарантировать прокидку проводки в АБСFR-PUT-022: В режиме rpt_flag = Y система должна предотвращать дублирование авизо (camt.054) - формировать его только если не было отправлено в первоначальном процессе2.4. Логика проксирования PUT-запросовFR-PUT-030: При получении повторного PUT-запроса система должна проверять наличие предыдущего ответа для ТСП с таким же IDFR-PUT-031: Если существует предыдущий положительный ответ → вернуть тот же ответ повторно в сторону ТСПFR-PUT-032: Если предыдущий ответ отрицательный или отсутствует → выполнить полную обработку запроса (шаги 1-3)3. Общие системные требования3.1. Хранение состоянияFR-COMMON-001: Система должна хранить историю обработки запросов с ключами идемпотентности и результатами обработкиFR-COMMON-002: Время хранения состояния обработки должно покрывать длительность операционного дня3.2. Классификация ответовFR-COMMON-010: Положительными ответами считать HTTP коды: 200, 201, 202FR-COMMON-011: Отрицательными ответами считать все остальные HTTP коды3.3. ПроизводительностьFR-COMMON-020: Механизм проверки идемпотентности не должен существенно влиять на производительность обработки запросовFR-COMMON-021: Система должна обеспечивать атомарность операций проверки и обновления состояния идемпотентности
