# **Бизнес-требования к доработке модуля управления сертификатами в EPG**  
**Документ подготовлен:** Бизнес-аналитик  
**Версия:** 1.0  
**Дата:** [текущая дата]  
**Заинтересованные стороны:** Команда заказчика (AV, MK, VG), Команда исполнителя (SN, GF)  

---

## **1. Введение**

### 1.1. Цель документа
Формализовать требования к доработке веб-интерфейса EPG для управления клиентскими сертификатами, включая их подписание, хранение, контроль срока действия и уведомления.

### 1.2. Контекст и проблема
В текущем процессе выпуска сертификатов для партнёров (мерчантов) используется ручное взаимодействие с OpenSSL, что требует специальных знаний и усложняет регистрацию новых партнёров.  
Требуется упростить и частично автоматизировать процесс выпуска, подписания и контроля сертификатов через веб-интерфейс EPG.

---

## **2. Бизнес-требования**

### 2.1. Цели
- Создать единый интерфейс для управления сертификатами партнёров в рамках EPG.
- Упростить процесс выпуска сертификатов для операторов.
- Обеспечить контроль сроков действия сертификатов и уведомления об истечении.
- Исключить необходимость использования сторонних инструментов (например, OpenSSL вручную).

### 2.2. Ожидаемые результаты
- Оператор может выпустить сертификат для мерчанта в процессе его регистрации.
- Администратор видит список всех сертификатов с информацией о сроке действия.
- Автоматические уведомления отправляются ответственным лицам перед истечением срока действия сертификата.

---

## **3. Функциональные требования**

### 3.1. Страница управления сертификатами
**Экран:** Отдельный раздел в веб-интерфейсе EPG.

**Элементы:**
- Таблица со списком сертификатов, содержащая колонки:
  - Логин пользователя API
  - Логин мерчанта (MID/TID)
  - Subject сертификата
  - Серийный номер сертификата
  - Дата истечения срока действия
  - Визуальное выделение строк:
    - Красный — срок истёк.
    - Жёлтый — осталось менее N дней (N настраивается).
- Фильтры/поиск по:
  - Логину пользователя API
  - Логину мерчанта
  - Subject сертификата

### 3.2. Загрузка CA (центра удостоверения)
**Функционал:**
- Возможность загрузки CA-сертификата и приватного ключа в JKS-хранилище EPG.
- Настройка alias для CA в конфигурации EPG.

### 3.3. Подписание CSR (запрос на подпись сертификата)
**Сценарий 1: Через отдельную форму**
- Кнопка "Подписать сертификат" → открывает модальное окно с полями:
  - Логин пользователя API (с поиском и автоподстановкой мерчанта).
  - Поле для загрузки файла CSR (.csr).
  - Кнопка "Подписать" → выполняет подписание с использованием загруженного CA.
  - После успешного подписания:
    - Запись добавляется в таблицу сертификатов.
    - Показывается ссылка/кнопка для скачивания CRT.
  - При ошибке подписания — отображение понятного сообщения об ошибке.

**Сценарий 2: При создании пользователя API**
- Если у пользователя есть разрешение "Use Merchant API", отображается поле для загрузки CSR.
- При загрузке CSR автоматически подписывается и добавляется в список сертификатов.

### 3.4. Скачивание сертификата
- В таблице сертификатов — кнопка "Скачать CRT" для каждой записи.
- На форме списка пользователей — если у пользователя есть действующие сертификаты, отображается кнопка "Скачать сертификат" (скачивается CRT с самым поздним сроком действия).

### 3.5. Удаление записей
- Кнопка "Удалить" в таблице сертификатов для удаления устаревших или ошибочных записей.

### 3.6. Уведомления об истечении срока действия
**Механизм:**
- Фоновое задание (расписание) проверяет срок действия сертификатов.
- Отправляет email-уведомления, если:
  - Срок действия истекает через N дней (настраиваемо).
  - Срок уже истёк.
- Адреса для уведомлений настраиваются:
  - Глобально (системная настройка) — для ответственных сотрудников банка.
  - На уровне сертификата (при подписании) — для ответственных лиц мерчанта.

---

## **4. Нефункциональные требования**

### 4.1. Безопасность
- Приватный ключ CA хранится в JKS-хранилище с защитой.
- Доступ к разделу управления сертификатами — только для пользователей с соответствующими правами.

### 4.2. Надёжность
- Обработка ошибок подписания CSR с понятными сообщениями в интерфейсе.
- Логирование всех операций с сертификатами.

### 4.3. Производительность
- Таблица сертификатов должна поддерживать пагинацию/фильтрацию при большом количестве записей.

---

## **5. Ограничения и допущения**

### 5.1. Ограничения
- EPG не проверяет клиентские сертификаты при вызовах API — это задача nginx.
- Ключи партнёров не хранятся в EPG (только сертификаты).

### 5.2. Допущения
- CA-сертификат и ключ предоставляются заказчиком.
- Формат CSR — стандартный PEM/DER, совместимый с OpenSSL.

---

## **6. Сценарии использования**

### 6.1. Выпуск сертификата для нового партнёра
1. Оператор создаёт пользователя API с разрешением "Use Merchant API".
2. Загружает CSR от партнёра.
3. Система автоматически подписывает CSR с использованием CA.
4. Сертификат добавляется в список, становится доступным для скачивания.
5. Партнёру отправляется CRT.

### 6.2. Контроль сроков действия
1. Ежедневно система проверяет сроки действия сертификатов.
2. Если до истечения срока осталось менее 30 дней (значение настраивается), отправляется уведомление на email из системных настроек и/или указанные при подписании.
3. В интерфейсе запись подсвечивается жёлтым/красным.

# **Бизнес-требования к доработке модуля управления сертификатами в EPG**

**Документ подготовлен:** Бизнес-аналитик  
**Версия:** 1.0  
**Дата:** [текущая дата]  
**Заинтересованные стороны:** Команда заказчика (AV, MK, VG), Команда исполнителя (SN, GF)

---

### **1. Цель документа**
Формализовать требования к доработке веб-интерфейса EPG для управления клиентскими сертификатами партнеров (мерчантов), включая их подписание, хранение, контроль срока действия и уведомления. Цель — упростить и централизовать процесс выпуска сертификатов, исключив необходимость ручной работы с OpenSSL.

### **2. Бизнес-контекст**
В текущем процессе регистрации нового партнера требуется, чтобы оператор вручную, используя инструменты командной строки (OpenSSL), подписывал сертификат на основе предоставленного партнером CSR. Это создает операционную сложность и требует специальных знаний. Необходим инструмент в интерфейсе EPG, который позволит выполнять выпуск и контроль сертификатов в рамках единого рабочего процесса регистрации мерчанта.

### **3. Общие требования**
Система должна предоставлять администратору/оператору EPG возможность управлять сертификатами партнеров через веб-интерфейс. Необходимо обеспечить безопасное хранение корневого CA, простой механизм подписания запросов (CSR), отображение списка всех выпущенных сертификатов с их статусами и автоматическое оповещение об истечении срока действия.

### **4. Детальные функциональные требования**

**4.1. Страница управления сертификатами**
В интерфейс EPG необходимо добавить отдельный раздел (страницу) "Клиентские сертификаты". На этой странице должен отображаться список всех выпущенных сертификатов в виде таблицы. Для каждой записи нужно предусмотреть отображение:
*   Логина пользователя API и соответствующего ему логина мерчанта (MID/TID).
*   Subject и серийного номера сертификата.
*   Даты истечения срока действия.
Необходимо визуально выделять записи, у которых срок действия истек (например, красным) или истекает менее чем через N дней (например, желтым). Значение N должно быть настраиваемым. Также нужно предусмотреть возможность фильтрации и поиска по логину пользователя, логину мерчанта и полю Subject.

**4.2. Работа с Центром сертификации (CA)**
Система должна предоставлять возможность загрузки корневого CA-сертификата и его приватного ключа в JKS-хранилище EPG. Путь к хранилищу и alias для пары ключей должны задаваться через системные настройки.

**4.3. Подписание запросов на сертификат (CSR)**
Требуется реализовать два сценария подписания CSR:
1.  **Через основную страницу управления:** На странице сертификатов должна быть кнопка "Подписать сертификат", открывающая модальное окно. В окне необходимо предусмотреть поле для выбора пользователя API (с поиском и автоподстановкой мерчанта) и элемент для загрузки файла CSR (.csr). После нажатия кнопки "Подписать" система должна подписать запрос, используя загруженный CA, создать запись в общем списке и предоставить возможность сразу скачать полученный .crt файл.
2.  **При создании пользователя:** На форме создания/редактирования пользователя API, если у пользователя есть право "Use Merchant API", нужно добавить поле для загрузки CSR. Загрузка файла должна инициировать автоматическое подписание и сохранение сертификата в общем списке.

Во всех случаях при ошибке подписания (например, проблемы с OpenSSL, невалидный CSR) система должна отображать понятное сообщение об ошибке в интерфейсе.

**4.4. Скачивание и удаление сертификатов**
Для каждой записи в списке сертификатов должна быть доступна кнопка для скачивания подписанного сертификата в формате .crt. На странице списка пользователей, если у выбранного пользователя есть действующие сертификаты, необходимо предусмотреть кнопку для скачивания сертификата с самым поздним сроком действия.
Для поддержания порядка в базе данных необходимо предусмотреть возможность удаления устаревших или ошибочных записей о сертификатах через кнопку "Удалить" в таблице.

**4.5. Система уведомлений об истечении срока**
Требуется реализовать фоновое задание (расписание), которое будет проверять сроки действия всех сертификатов и отправлять email-уведомления. Уведомления должны отправляться как при приближении даты истечения (за N дней), так и после ее наступления.
Система должна поддерживать гибкую настройку списков рассылки:
*   **Глобальный список:** Настраивается в системных параметрах EPG для получения уведомлений по всем сертификатам (например, для сотрудников банка).
*   **Локальный список:** Должна быть возможность указать один или несколько email-адресов непосредственно при подписании CSR (например, для ответственных лиц партнера-мерчанта). Уведомления отправляются на объединенный список адресов.

### **5. Нефункциональные требования**
*   **Безопасность:** Приватный ключ CA должен храниться в защищенном JKS-хранилище. Доступ к функционалу управления сертификатами должен регулироваться правами пользователей EPG.
*   **Надежность:** Все операции с сертификатами должны логироваться. Необходима корректная обработка и отображение ошибок на всех этапах (загрузка CA, подписание CSR).
*   **Производительность:** Интерфейс списка сертификатов должен эффективно работать при большом количестве записей, поддерживая пагинацию и фильтрацию.

### **6. Ограничения**
*   EPG не выполняет проверку клиентских сертификатов при входящих API-вызовах. Эта задача остается за nginx.
*   Система предназначена для хранения и управления сертификатами (публичными ключами), но не приватными ключами партнеров.

# **Бизнес-требования к доработке интерфейса для работы с 3D Secure**

**Документ подготовлен:** Бизнес-аналитик  
**Версия:** 1.0  
**Дата:** [текущая дата]  
**Заинтересованные стороны:** Команда заказчика (AV), Команда исполнителя (GF, DA)

---

### **1. Цель документа**
Определить требования к доработке интерфейсов EPG (платежного шлюза) и 3DSS (3D Secure Server) для обеспечения сквозной трассировки платежных операций, связанных с 3D Secure аутентификацией. Цель — предоставить специалистам поддержки возможность быстро находить детали аутентификации в системе 3DSS, отталкиваясь от данных об операции в основном интерфейсе EPG.

### **2. Бизнес-контекст**
Специалисты технической поддержки и операторы при разборе инцидентов, связанных с 3D Secure, начинают поиск с операции в платежном шлюзе (EPG) по данным, предоставленным партнером (например, orderNumber, mdOrder, PAN). В текущей реализации для просмотра деталей самой аутентификации 3DS им необходимо переходить в интерфейс 3DSS, но отсутствует прямая связь между этими системами в интерфейсе, что усложняет и замедляет диагностику. Необходимо обеспечить удобную связку между двумя интерфейсами.

### **3. Общие требования**
Требуется реализовать косвенную, но эффективную интеграцию между интерфейсом просмотра операций в EPG и интерфейсом просмотра транзакций в 3DSS. Основной принцип: предоставить в EPG идентификатор транзакции 3DSS, который затем можно использовать для прямого поиска в GUI 3DSS. Это предпочтительнее, чем реализация сложного поиска по PAN в самой базе данных 3DSS.

### **4. Детальные функциональные требования**

**4.1. Отображение идентификатора 3DS-транзакции в EPG**
В графическом интерфейсе EPG, на странице детализации операции платежа, необходимо предусмотреть отображение идентификатора транзакции 3D Secure Server (`threeDSServerTransID` или `threeDSTransId`). Данное поле должно отображаться для всех операций, в рамках которых выполнялась процедура 3D Secure аутентификации.

Важно учесть, что в рамках одной финансовой транзакции в EPG может быть несколько попыток оплаты и, соответственно, несколько уникальных `threeDSServerTransID`. Система должна быть готова отображать несколько таких идентификаторов или последний/актуальный из них, в зависимости от технической реализации логики связывания.

**4.2. Поиск по идентификатору в GUI 3D Secure Server**
В графическом интерфейсе 3D Secure Server (3DSS UI) должна быть сохранена или доработана возможность поиска транзакций по идентификатору `threeDSServerTransID`. Поиск может быть дополнен фильтрацией по дате и времени для повышения точности, но основным и достаточным критерием должен оставаться сам идентификатор транзакции.

Таким образом, рабочий процесс специалиста поддержки будет следующим:
1.  Получив от партнера реквизиты операции (номер заказа, PAN и т.д.), специалист находит операцию в интерфейсе EPG.
2.  В деталях операции он видит `threeDSServerTransID`.
3.  Копируя этот идентификатор, специалист переходит в интерфейс 3DSS, вставляет его в поле поиска и получает полную детализацию сообщений и статусов соответствующей попытки 3D Secure аутентификации.

### **5. Ограничения и допущения**
*   Первичным источником для поиска деталей 3DS-аутентификации остается отдельный интерфейс 3DSS. Прямой просмотр этих деталей внутри интерфейса EPG в рамках данной задачи не требуется.

Изначально проблема формулируется на стороне платежного шлюза (EPG), где оператор ищет операцию по данным от партнера (номер заказа, PAN). Однако детали непосредственно 3D Secure аутентификации хранятся в отдельной системе — 3D Secure Server (3DSS), и переход между интерфейсами этих систем не является очевидным.

Первоначальный запрос заказчика был направлен на добавление в интерфейс 3DSS возможности поиска по номеру карты (PAN), что потребовало бы значительных изменений в архитектуре хранения данных. В ходе обсуждения был предложен и согласован более рациональный альтернативный подход: **отображать в интерфейсе EPG уникальный идентификатор транзакции 3DSS**, чтобы специалист мог скопировать его и выполнить целенаправленный поиск в GUI 3DSS.

Основная цель — **сократить время диагностики проблем с 3D Secure** за счет создания удобной логической связи между интерфейсом платежного шлюза (EPG) и интерфейсом сервера аутентификации (3DSS).

Конкретные цели:
1.  Исключить необходимость для специалистов выполнять сложный или неочевидный поиск в 3DSS.
2.  Предоставить прямой и понятный механизм перехода от просмотра операции в EPG к деталям её 3DS-аутентификации в 3DSS.
3.  Реализовать решение с минимальными архитектурными изменениями, избегая сложной доработки логики хранения и поиска в базе данных 3DSS.

## **3. Основные требования**

### **3.1. Отображение идентификатора транзакции 3DSS в EPG**
Необходимо доработать графический интерфейс EPG. На странице с детальной информацией о платежной операции, для которой выполнялась 3D Secure аутентификация, должно быть добавлено поле **«Идентификатор транзакции 3DS»** (`threeDSServerTransID` / `threeDSTransId`).

### **3.2. Обеспечение поиска в 3DSS по идентификатору**
В графическом интерфейсе 3D Secure Server должна быть сохранена или гарантирована возможность **поиска транзакций по полю `threeDSServerTransID`**. Это является ключевым условием работы всего механизма. Поиск может быть дополнен фильтрами (например, по дате), но идентификатор должен оставаться основным и достаточным критерием.

## **4. Ожидаемый рабочий процесс**

После реализации доработки процесс анализа инцидента специалистом поддержки будет выглядеть следующим образом:
1.  Специалист получает от партнера референс операции (например, `orderNumber`).
2.  Находит эту операцию в интерфейсе EPG через стандартный поиск.
3.  В карточке операции видит поле **«Идентификатор транзакции 3DS»**.
4.  Копирует значение этого идентификатора.
5.  Переходит в интерфейс 3DSS, вставляет скопированный идентификатор в поле поиска.
6.  Получает полную детализацию сообщений и статусов соответствующей попытки 3D Secure аутентификации.

## **1. Контекст и постановка проблемы**

Заказчик испытывает недостаток информации для мониторинга и анализа работы компонентов, ответственных за 3D Secure аутентификацию. В существующих системах (EPG и 3DSS) присутствуют в основном технические метрики (Actuator/JMX), но отсутствуют **бизнес-метрики**, отражающие ключевые показатели процесса аутентификации: количество и статусы сообщений по протоколам 3DS 1.0.2 и 3DS 2.0.

Отсутствие таких данных затрудняет оперативный контроль качества обслуживания, анализ причин отказов и планирование нагрузок. Изначальный запрос включал вопросы по настройке мониторинга, но в ходе обсуждения был сформирован и согласован конкретный перечень необходимых бизнес-метрик, разделенных по системам.

## **2. Цели проекта**

Основная цель — **обеспечить прозрачность и контролируемость процессов 3D Secure** за счет внедрения набора ключевых бизнес-метрик в системах EPG и 3DS Server.

Конкретные цели:
1.  **Для 3DS 2.0:** Реализовать сбор метрик в компоненте **3DS Server**, так как он является центральным узлом обработки для этого протокола.
2.  **Для 3DS 1.0.2:** Реализовать сбор метрик в компоненте **EPG (MPI)**, так как он обрабатывает этот протокол.
3.  **Исключить дублирование:** Не создавать одинаковые метрики в обеих системах, а чётко разделить ответственность в соответствии с архитектурой.
4.  **Обеспечить техническую возможность сбора:** Подтвердить и обеспечить работу сбора метрик через агента Prometheus/JMX по аналогии с системой ACS.

## **3. Требования к метрикам для 3DS Server (3DS 2.0)**

Требуется реализовать в 3DS Server сбор следующих бизнес-метрик по протоколу 3DS 2.0. Метрики должны быть доступны для сбора через Prometheus.

### **3.1. Метрики по потоку аутентификации (AReq/ARes):**
*   **AReq (App Request):** Количество отправленных AReq-сообщений в Directory Server (DS) с разбивкой по HTTP-статусу ответа (уже частично существует как `dsRequestsCounter`).
*   **ARes (App Response):** Количество полученных ARes-сообщений от DS с разбивкой по значениям полей `transStatus` и `transStatusReason` (при наличии).

### **3.2. Метрики по потоку Challenge (CReq/CRes):**
*   **CReq (Challenge Request):** Количество сформированных и отправленных (через браузер клиента) CReq-сообщений.
*   **CRes (Challenge Response):** Количество полученных CRes-сообщений от ACS с разбивкой по значению поля `transStatus`.

### **3.3. Метрики по потоку RReq/RRes:**
*   **RReq (Result Request):** Количество полученных RReq-сообщений от DS с разбивкой по всем возможным значениям полей `transStatus` и `transStatusReason` в соответствии со спецификацией EMV.
*   **RRes (Result Response):** Количество отправленных RRes-сообщений (синхронных ответов на RReq) с разбивкой по значению поля `resultStatus` из самого сообщения RRes.

### **3.4. Метрика доступности инфраструктуры:**
*   **Переключение на Fallback DS:** Метрика, фиксирующая факты переключения запросов на резервный Directory Server (`ds2.mirconnect.ru`) при недоступности основного (`ds1.mirconnect.ru`). Должна учитывать срабатывания при таймаутах или получении кодов ошибок (например, 500).

## **4. Требования к метрикам для EPG (3DS 1.0.2)**

Требуется реализовать в EPG (в компоненте MPI) сбор следующих бизнес-метрик по протоколу 3DS 1.0.2.

### **4.1. Метрики по потоку Verify Enrollment (VeReq/VeRes):**
*   **VeReq (Verify Enrollment Request):** Количество отправленных VeReq-сообщений в DS.
*   **VeRes (Verify Enrollment Response):** Количество полученных VeRes-сообщений от DS с разбивкой по значению поля `status`.

### **4.2. Метрики по потоку Payer Authentication (PaReq/PaRes):**
*   **PaReq (Payer Authentication Request):** Количество сформированных и отправленных (через браузер клиента) PaReq-сообщений.
*   **PaRes (Payer Authentication Response):** Количество полученных PaRes-сообщений от ACS с разбивкой по всем возможным значениям поля `transStatus`.

## **5. Нефункциональные требования и техническая реализация**

1.  **Формат и сбор:** Все новые метрики должны быть доступны в формате, пригодном для сбора **агентом Prometheus** (через JMX или HTTP endpoint), по аналогии с настройкой для ACS.
2.  **Именование и теги:** Метрики должны иметь понятные имена и использовать labels (теги) для детальной разбивки (например, `transStatus="Y"`, `transStatusReason="01"`).
3.  **Производительность:** Внедрение метрик не должно оказывать существенного негативного влияния на производительность и время отклика систем EPG и 3DSS.
4.  **Документация:** По итогам реализации необходимо предоставить обновлённый перечень доступных метрик с описанием.

## **6. Ограничения**

**EPG (E-commerce Payment Gateway)** — платежный шлюз, система эквайера для приёма и обработки онлайн-платежей. Включает компонент MPI для работы с 3DS 1.0.2.

**Fallback DS** — резервный (вторичный) адрес Directory Server, используемый при недоступности основного (primary) DS.

**JMX (Java Management Extensions)** — технология для управления и мониторинга приложений на Java. Используется для сбора метрик.

**MPI (Merchant Plug-In)** — модуль на стороне мерчанта (или эквайера), ответственный за взаимодействие с инфраструктурой 3DS 1.0.2. В контексте задачи является частью EPG.

**PaReq (Payer Authentication Request)** — сообщение 3DS 1.0.2, инициирующее аутентификацию. Формируется MPI и передается через браузер клиента в ACS.

**PaRes (Payer Authentication Response)** — сообщение 3DS 1.0.2 с результатами аутентификации, отправляемое ACS через браузер клиента обратно в MPI.

**Prometheus** — open-source система мониторинга и сбора метрик, использующая модель pull по HTTP.

**RReq (Result Request)** — сообщение 3DS 2.0, отправляемое Directory Server в 3DS Server для финального подтверждения результата аутентификации.

**RRes (Result Response)** — синхронный ответ 3DS Server на RReq, подтверждающий получение финального результата.

**transStatus** — ключевой статус транзакции аутентификации в сообщениях 3DS (например, "Y" – успешно, "N" – не успешно, "U" – недоступно).

**transStatusReason** — код, уточняющий причину того или иного `transStatus` (например, "01" – карта не участвует).

**VeReq (Verify Enrollment Request)** — сообщение 3DS 1.0.2, отправляемое MPI в Directory Server для проверки участия карты в программе 3D Secure.

**VeRes (Verify Enrollment Response)** — ответ Directory Server на VeReq, содержащий информацию об участии карты и адрес ACS.

Из диалога видно, что заказчика интересует не просто "живо ли приложение" (проверка процесса), а **комплексная проверка работоспособности ключевых внутренних зависимостей** каждой системы:

1.  **EPG (Платежный шлюз + MPI):**
    *   Состояние соединения с базой данных (DB).
    *   Состояние кластера Hazelcast (распределенный кэш/блокировки).
    *   Состояние соединения с Front-End (FE) системой (скорее всего, ядро процессинга банка).
    *   Соединения по HTTP (например, с DS) считаются stateless и не требуют мониторинга в рамках health check.

2.  **ACS:**
    *   Аналогично EPG: состояние DB, Hazelcast и соединения с FE.

3.  **3DS Server:**
    *   Состояние DB и Hazelcast. Соединение с FE для него не актуально.

**Важный нюанс (от заказчика):** Если потеряно соединение с FE **по одному из нескольких профилей или эквайеров**, сам экземпляр приложения **не должен считаться полностью неработоспособным**. Однако этот факт должен быть явно отражен в ответе, чтобы его можно было вывести в метрику и настроить на него алерт для экстренного реагирования инженеров банка.

## **Предполагаемый механизм реализации**

1.  **API Endpoint:** Для каждого компонента (EPG, ACS, 3DS Server) будет реализован отдельный HTTP endpoint (например, `/api/health` или `/management/health`).
2.  **Логика проверки:** Endpoint будет выполнять синхронные проверки состояния критических подключений (DB, Hazelcast, FE) и агрегировать результат.
3.  **Формат ответа:** Обсуждается два варианта:
    *   **Для балансировщика нагрузки (HA Proxy):** Возвращать HTTP статус `200 OK` в случае общей работоспособности и `5xx`/`4xx` в случае критической неработоспособности (например, отвалилась БД на всех нодах). Это позволит балансировщику автоматически исключать "больные" ноды из ротации.
    *   **Для детального мониторинга и Grafana:** Предоставить ответ в структурированном формате (JSON), где будет детальный статус каждого проверяемого компонента, или даже **в формате Prometheus** (plain text), чтобы метрики можно было напрямую забирать системой мониторинга.
4.  **Интеграция с Prometheus:** Существует техническая возможность (и уже настроенная для ACS) использовать Java-агент (`jmx_prometheus_javaagent`) для экспорта JMX-метрик приложения (включая, потенциально, новые health-метрики) в формате Prometheus. Это требует:
    *   Добавления новых кастомных метрик в JMX для каждого компонента (статусы подключений).
    *   Настройки агента для их сбора и экспорта.

## **Итог: Суть задачи**

Разработать и внедрить **систему детальной самодиагностики** для трех ключевых платежных систем, результаты которой будут доступны:
1.  **Внешне:** Мерчантам через простой API-запрос для оперативного принятия решений о маршрутизации трафика.
2.  **Внутренне:** Системам мониторинга банка (Prometheus/Grafana) через метрики в формате Prometheus для алертинга и анализа.

## **1. Контекст и описание проблемы**

Мерчанты банка, интегрированные с платежными системами, нуждаются в инструменте для оперативного контроля доступности критически важных сервисов на стороне банка. В текущей архитектуре падение одного из внутренних компонентов (например, 3DS Server) может оставаться незамеченным для мерчанта в течение нескольких минут, что ведет к потере транзакций и сложностям при разборе инцидентов.

Требуется предоставить мерчантам (и внутренним системам мониторинга банка) возможность выполнять проверку не просто факта работы процесса приложения, а **работоспособности ключевых внутренних зависимостей** каждого сервиса.

## **2. Цели проекта**

1.  **Внешняя прозрачность:** Дать мерчантам простой механизм (API) для самостоятельной проверки работоспособности систем ACS, 3DS Server и EPG перед инициированием платежного трафика.
2.  **Внутренний мониторинг:** Обеспечить сбор детализированных метрик о состоянии компонентов для систем мониторинга банка (Prometheus/Grafana) с целью алертинга и оперативного реагирования.
3.  **Интеграция с балансировщиком:** Предоставить endpoint, совместимый с балансировщиками нагрузки (HA Proxy), для автоматического исключения неработоспособных нод из ротации.

## **3. Детальные функциональные требования**

### **3.1. Общий принцип**
Для каждого компонента (**ACS**, **3DS Server**, **EPG**) необходимо реализовать отдельный HTTP **Health Check Endpoint**. Endpoint должен выполнять синхронные проверки состояния критически важных внутренних подключений и возвращать агрегированный результат.

### **3.2. Проверяемые компоненты и их статусы**

| :------------ | :------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **EPG**       | 1. Соединение с базой данных (DB)<br>2. Состояние кластера Hazelcast<br>3. Соединение с Front-End (FE) для **каждого** настроенного эквайера | Экземпляр считается **работоспособным (UP)**, если доступны БД и Hazelcast. ### **3.3. Форматы ответа API**

Система должна поддерживать два режима работы endpoint'а, определяемых, например, HTTP-заголовком `Accept`:

1.  **Режим для балансировщика нагрузки (Balancer Mode):**
    *   **Цель:** Интеграция с HA Proxy, Nginx, Kubernetes для автоматического управления трафиком.
    *   **Формат ответа:** Только HTTP-статус код.
        *   **HTTP 200 OK:** Экземпляр приложения считается **работоспособным** (соответствует критерию UP из п. 3.2).
        *   **HTTP 503 Service Unavailable:** Экземпляр приложения считается **неработоспособным** (не соответствует критерию UP).
    *   **Контент:** Минимальный или пустой.

2.  **Режим детализированного ответа (Detailed/JSON Mode):**
    *   **Цель:** Для внешних мерчантов и внутреннего детального мониторинга.
    *   **Формат ответа:** JSON-объект.
    *   **Структура ответа:**
        ```json
        {
          "status": "UP", // или "DOWN" на основе общего критерия
          "components": {
            "db": { "status": "UP", "details": "..." },
            "hazelcast": { "status": "UP", "details": "..." },
            "feConnections": [
              { "profile": "main", "status": "UP" },
              { "profile": "louis", "status": "DOWN", "error": "Connection timeout" }
            ]
          }
        }
        ```
    *   Для **3DS Server** объект `feConnections` отсутствует.

### **3.4. Интеграция с Prometheus (Ответ на вопрос #4)**

**Да, систему можно реализовать так, чтобы метрики были доступны в формате Prometheus.**

*   **Механизм:** В дополнение к API, в каждый компонент (ACS, EPG, 3DS Server) будут добавлены **JMX-метрики** (Java Management Extensions), отражающие текущий статус каждого проверяемого компонента (db_status, hazelcast_status, fe_connection_status{profile="..."}).
*   **Сбор метрик:** Для сбора этих JMX-метрик в формате Prometheus будет использоваться стандартный **Java-агент** `jmx_prometheus_javaagent`, который уже успешно настроен и работает для системы ACS. Агент запускается вместе с приложением и экспортирует метрики на отдельный HTTP-порт.
*   **Результат:** Система мониторинга Prometheus сможет "скрести" (scrape) этот порт и получать актуальные метрики состояния, которые затем можно визуализировать в Grafana и использовать для настройки алертов (например, "FE connection для профиля Louis = DOWN более 1 минуты").

**Важно:** Это означает, что у мерчантов будет **два независимых способа** получить информацию:
1.  **Прямой запрос** к Health Check API за детальным статусом.
2.  **Через общую систему мониторинга банка** (Grafana), куда данные попадают из Prometheus.

2.  **Интеграция с балансировщиком:** Endpoint должен позволять балансировщику нагрузки (например, HA Proxy) определять, следует ли маршрутизировать трафик на данный экземпляр приложения. Для этого endpoint должен возвращать HTTP-статус `200 OK`, если экземпляр работоспособен (согласно логике из п. 3.2), и статус ошибки (например, `503 Service Unavailable`), если неработоспособен.
3.  **Детализированный ответ:** Endpoint должен возвращать структурированные данные (например, в формате JSON), которые детализируют статус каждого проверяемого компонента (DB, Hazelcast, FE-соединения). Это необходимо для внутреннего мониторинга и настройки алертов.

### **3.4. Поддержка формата Prometheus (Ответ на вопрос #4)**

Требуется обеспечить возможность сбора метрик о состоянии компонентов (статусы проверок из п. 3.1) системой мониторинга **Prometheus**.

*   **Механизм:** Метрики должны быть доступны для сбора в формате Prometheus. В качестве базового метода предлагается добавление соответствующих метрик в **JMX** и использование для их экспорта **Java-агента Prometheus JMX Exporter** (`jmx_prometheus_javaagent`), который уже настроен для системы ACS.
*   **Содержание метрик:** В метриках должны отражаться статусы всех проверяемых компонентов, включая отдельные FE-подключения для разных профилей/эквайеров.

## **4. Ограничения**

1.  **Stateless-подключения:** Проверка состояния stateless HTTP-подключений (например, к Directory Server) не входит в scope данной задачи и не имеет смысла в контексте health check.
2.  **Тестирование интеграции с Prometheus:** Полная настройка и тестирование конвейера сбора метрик (Prometheus -> Grafana) на стороне заказчика не входит в scope работ исполнителя. Исполнитель обеспечивает доступность метрик в формате Prometheus на endpoint'е каждого экземпляра приложения.
3.  **Архитектура FE-подключений:** В текущей архитектуре используется TCP Gate для подключения к FE. В случае его проблем, соединение с FE, скорее всего, будет потеряно одновременно на многих экземплярах приложений, что превращает вопрос в задачу экстренного реагирования, а не балансировки трафика между нодами.

*   **3DS Server** — сервер, обеспечивающий аутентификацию по протоколу 3-D Secure 2.x.
*   **ACS (Access Control Server)** — сервер эмитента, выполняющий аутентификацию держателя карты.
*   **DB (Database)** — база данных приложения.

## **1. Контекст и описание проблемы**

В текущей реализации процесс списания ежемесячной комиссии за услугу SMS-информирования по карте включает механизм повторных попыток списания ("дополнительный цикл") в течение 30 дней в случае недостатка средств на счете клиента. Данная логика является избыточной и не соответствует новым бизнес-требованиям.

Бизнес принимает решение упростить процесс, перейдя к четкой и предсказуемой модели: если в расчетный день на счете клиента достаточно средств — комиссия списывается, и услуга продлевается. Если средств недостаточно — услуга немедленно отключается без создания долга и последующих попыток списания.

## **2. Цели проекта**

1.  **Упрощение логики:** Ликвидировать сложные механизмы повторных попыток списания и обработки долга по комиссии за SMS-сервис.
2.  **Повышение прозрачности:** Обеспечить для клиента четкую связь между оплатой и статусом услуги — неуплата приводит к немедленному отключению.
3.  **Синхронизация статусов:** Гарантировать, что отключение услуги в расчетной системе (BO) актуализируется в карточном фронте (FE).

## **3. Текущая логика (AS-IS)**

Цикл взимания комиссии регулируется событием **CYTP0132** с периодом 30 дней.
1.  В день наступления события система проверяет статус карты и доступный баланс.
2.  При достаточном балансе: комиссия списывается полностью.
3.  При недостаточном балансе: запускается **дополнительный 30-дневный цикл (S)** для ежедневных проверок баланса.
    *   Если в течение этого цикла средства появляются, происходит списание, и основной цикл перезапускается.
    *   Если средства не появляются, долг аннулируется, и цикл S запускается заново для следующего периода.

## **4. Требуемая логика (TO-BE)**

Требуется модифицировать обработку события **CYTP0132** в системе Back-Office (BO). Новая логика должна реализовывать следующий алгоритм:

**В день наступления события CYTP0132 система должна:**
1.  **Проверить статус карты.** Обработка должна происходить только для карт, которые **не заблокированы** и **не находятся в процессе закрытия**.
2.  **Оценить возможность списания:**
    *   **ВАРИАНТ А: Средств ДОСТАТОЧНО.**
        *   **Действие:** Произвести списание комиссии в полном объеме.
        *   **Результат:** Услуга SMS-информирования считается оплаченной и остается активной на следующий расчетный цикл.
    *   **ВАРИАНТ Б: Средств НЕДОСТАТОЧНО.**
        *   **Действие 1:** Немедленно **отключить** услугу SMS-информирования для данной карты в системе BO. **Никакое списание комиссии (в том числе частичное) не производится.**
        *   **Действие 2:** Передать информацию об отключении сервиса в систему **Front-End (FE)** для синхронизации статуса на всех уровнях.
        *   **Результат:** Услуга деактивирована. Дополнительные циклы ожидания или накопление долга **не создаются**.

## **5. Детальные требования к реализации**

### **5.1. Требования к Back-Office (BO)**
1.  **Новые модификаторы (проверяющие условия):**
    *   Создать модификатор **"Денег достаточно для комиссии за SMS-сервис"**. Он должен возвращать `true`, если доступный баланс основного счета карты **больше или равен** размеру комиссии за SMS-сервис.
    *   Создать модификатор **"Денег недостаточно для комиссии за SMS-сервис"**. Он должен возвращать `true`, если доступный баланс основного счета карты **меньше** размера комиссии за SMS-сервис.
2.  **Новый набор правил:**
    *   Создать **набор правил "Отключение SMS-сервиса"**, который будет выполняться при условии срабатывания модификатора "Денег недостаточно...". Действием этого набора должно быть отключение сервиса в BO.
3.  **Конфигурация события CYTP0132:**
    *   К существующему **набору правил "Взимание комиссии"** для события CYTP0132 должен быть прикреплен модификатор **"Денег достаточно для комиссии за SMS-сервис"**. Это гарантирует, что списание произойдет только при достаточном балансе.
    *   К новому **набору правил "Отключение SMS-сервиса"** для события CYTP0132 должен быть прикреплен модификатор **"Денег недостаточно для комиссии за SMS-сервис"**.

### **5.2. Требование к интеграции с Front-End (FE)**
1.  В рамках действия **"Отключение SMS-сервиса"** в BO необходимо инициировать процесс передачи соответствующего статуса в систему **Front-End (FE)**.
2.  Механизм и формат передачи должны соответствовать существующим практикам интеграции между BO и FE.

## **6. Ограничения**

1.  Частичное списание комиссии (списание доступной суммы с последующим досписанием) **не входит в scope** данной задачи.
2.  Архитектурное изменение, при котором проверка баланса и списание комиссии будут происходить в **Front-End (FE)** или **Интеграционной платформе (IP)**, **не рассматривается**. Логика остается в рамках Back-Office (BO).
3.  Все изменения должны быть обратимы: клиент должен иметь возможность повторно подключить услугу SMS-информирования через предусмотренные для этого каналы (например, через мобильное приложение или личный кабинет).

## **7. Термины и сокращения**

*   **BO (Back-Office)** — бэк-офисная система, отвечающая за расчетные операции, ведение карточных продуктов и списание комиссий.
*   **CYTP0132** — код события/цикла в системе BO, отвечающего за периодическое (раз в 30 дней) взимание комиссии за SMS-информирование.
*   **FE (Front-End)** — фронт-эндовая карточная система (ядро), хранящая актуальный статус карт и подключенных к ним сервисов.
*   **Модификатор (в контексте BO)** — правило или условие, которое проверяет определенные параметры (например, баланс счета) и возвращает булево значение (`true`/`false`).
*   **Набор правил (в контексте BO)** — совокупность действий, которые выполняются при наступлении события при соблюдении прикрепленных к нему модификаторов.
*   **SMS-информирование** — платная услуга, при которой клиент получает SMS-уведомления об операциях по своей карте.
