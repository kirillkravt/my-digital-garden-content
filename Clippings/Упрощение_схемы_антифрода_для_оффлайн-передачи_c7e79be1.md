# Упрощение схемы антифрода для оффлайн-передачи

## 👤 **Kirill**

Изменить требования с учетом усеченной схемы реализации:
Оффлайн передача операций для учета в антифроде. Никаких проверок Антифрод не выполняет пока только подключение потока оффлайн транзакций. 
В целевой схеме уже добавится логика обработки (в рамках данного документа не рассматривается)
 
 
Бизнес-инициатива
Интеграция нового источника данных о карточных транзакциях в систему антифрода банка. Это позволит повысить точность выявления мошеннических операций за счет расширения анализируемых 
данных, реализация возможности блокировки карт должно привести к снижению финансовых потерь.

Рисунок 2 Процесс получения и обработки транзакции

1.	Отправитель (клиент) делает запрос на платёж по СКС счету через СДБО. Тип сообщения: 1120 - Authorization Advice
2.	СДБО перенаправляет запрос для авторизации

6.	Синхронный ответ c подтверждением получения запроса HTTP status 200
7.	СДБО отправляет клиенту уведомление о финальном статусе операции.

## 🤖 **DeepSeek**

### Измененные требования с учетом усеченной схемы реализации (оффлайн-передача операций для учета в антифроде)

---

#### **1. Бизнес-инициатива**  
Интеграция нового источника данных о карточных транзакциях в систему антифрода банка для накопления данных.  
**Цель**:  
- Реализация оффлайн-передачи транзакций в антифрод для последующего анализа (без проверок в текущей фазе).  
- В будущем это позволит повысить точность выявления мошеннических операций и реализовать блокировки карт.  

---

#### **2.1.1 Архитектура решения**  
**Рисунок 1. Упрощенная архитектура (оффлайн-режим)**  

| № | Описание | Режим | Протокол |  
|---|----------|-------|----------|  
| 1 | СДБО → Antifraud: Передача транзакций для учета | Оффлайн | RabbitMQ/JSON |  

**Изменения**:  
- Убрана онлайн-проверка антифрода (шаг 5 в процессе обработки).  
- Ответ системы — только подтверждение приема данных (HTTP 200 / ACK).  

---

#### **2.1.2 Процесс передачи транзакции**  
**Рисунок 2. Упрощенный процесс**:  
1. Клиент инициирует операцию через СДБО (тип сообщения `1120 - Authorization Advice`).  
2. СДБО отправляет транзакцию в платежный шлюз → авторизация (**без проверки антифрода**).  
3. Шлюз возвращает статус "Одобрено".  
4. **Antifraud принимает операцию в очередь для учета (без проверки рисков)**.  
5. СДБО получает синхронный ответ `HTTP 200` (подтверждение приема).  
6. Клиенту отправляется финальный статус операции.  

**Ключевые изменения**:  
- Шаг 5 (проверка антифрода) заменен на пассивный учет.  
- Нет блокировок/отказов на этапе авторизации.  

---

#### **2.1.2.1 Параметры запроса (актуальные)**  
Состав полей сохранен (см. исходную таблицу), но:  
- Обязательные поля: `ucid`, `accountNumber`, `operationType`, `timestamp`, `amount`, `payer`, `recipient`.  
- Остальные поля передаются при наличии (не влияют на обработку в усеченной схеме).  

---

#### **2.1.3 Требования к RabbitMQ**  
| № | Очередь | Направление | Описание |  
|---|---------|-------------|----------|  
| 1 | `OPERATIONS_SV_QUEUE` | Входящая | Прием операций по СКС-счетам для учета в антифроде |  

**Настройки**:  
- Формат сообщений: JSON.  
- Подтверждение (ACK) при успешном сохранении в буфере антифрода.  
- Retry-политика: 3 попытки при ошибке доставки.  

---

#### **2.2 Требования к доработкам**  
1. **Интеграция с СДБО**:  
   - Реализовать выгрузку операций в очередь `OPERATIONS_SV_QUEUE` после авторизации.  
   - Отключить логику ожидания ответа от антифрода (только подтверждение приема).  

2. **Настройка RabbitMQ**:  
   - Создать Durable-очередь с сохранением сообщений при перезапуске.  
   - Логирование ошибок доставки.  

---

#### **3. Коды ответов (упрощенные)**  
| Код | Описание |  
|-----|----------|  
| 200 | Успешный прием транзакции |  
| 400 | Ошибка формата сообщения (некорректный JSON) |  
| 500 | Внутренняя ошибка сервера (например, недоступность очереди) |  

**Примечание**: В будущем коды будут расширены для онлайн-проверок.  

---

### **Итоговые изменения**  
- Удалена логика проверок антифрода (только учет данных).  
- Ответы системы сводятся к подтверждению приема.  
- Требования к RabbitMQ упрощены (достаточно одной очереди).  
- Обязательность полей пересмотрена (только ключевые для идентификации транзакции).  

Документ готов для согласования в рамках первой фазы (оффлайн-накопление данных).

### **2.2 Требования к доработкам в системе антифрода**  

#### **1. Прием и учет транзакций**  
- Реализовать **оффлайн-прием** транзакций из СДБО через RabbitMQ (очередь `OPERATIONS_SV_QUEUE`).  
- Обеспечить **сохранение операций** в буфер антифрода без проведения проверок.  
- Подтверждать прием данных ответом `HTTP 200` (без анализа содержимого).  

#### **2. Настройка очереди RabbitMQ**  
- Развернуть **durable-очередь** `OPERATIONS_SV_QUEUE` с гарантией доставки (persistent mode).  
- Реализовать **логирование ошибок** при проблемах с записью в очередь (например, недоступность брокера).  
- Настроить **retry-механизм** (3 попытки) для обработки временных сбоев.  

#### **3. Подготовка к будущей доработке**  
- Обеспечить **структуру хранения данных**, совместимую с будущими проверками (поля `ucid`, `amount`, `timestamp` и др.).  
- Добавить **метку времени получения** транзакции для анализа задержек.  
- Реализовать **мониторинг очереди** (количество сообщений, задержки обработки).  

#### **4. Отказоустойчивость**  
- При недоступности антифрода **сообщения должны накапливаться** в очереди (без потерь).  
- Настроить **оповещения** при критических сбоях (например, заполнение очереди).  

---

**Исключено из требований**:  
- Онлайн-проверки транзакций (это будет в следующих версиях).  
- Блокировки операций по результатам анализа.  
- Интеграция с другими системами (например, AML).  

Текущий фокус — **надежный прием данных** для последующего внедрения фрод-мониторинга.
