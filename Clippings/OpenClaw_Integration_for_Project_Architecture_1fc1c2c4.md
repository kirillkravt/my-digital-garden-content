ТЕКУЩИЕ ПРОБЛЕМЫ (НУЖНО ИСПРАВИТЬ)
🐛 Блокер 1: Версионирование не обновляется при навигации
Описание: При переходе между чатами через боковую панель, информация о версии не обновляется. Кнопка показывает версию предыдущего чата.

Воспроизведение:

Открыть чат А → сохранить (становится v1)

Перейти в чат Б → кнопка все еще показывает "Save v2" (для чата А)

Сохранить чат Б → он сохраняется как v2, хотя должен быть v1

Причина: MutationObserver отслеживает изменение URL, но не отслеживает изменение контента в SPA. При переходе по ссылкам в боковой панели URL может не меняться (используется hash или pushState с тем же URL).

🐛 Блокер 2: Mass Save сохраняет только один чат
Описание: Функция findAllChats() находит только один чат в DOM, хотя в боковой панели их много.

Воспроизведение:

Нажать красную кнопку "📚 Save All"

В диалоге показывает "Found 1 chats"

Сохраняется только текущий чат

Причина: Селекторы не находят все элементы чатов в боковой панели. Нужно исследовать структуру DOM DeepSeek.

⚠️ Блокер 3: Нет Preprocessing Agent
Описание: Файлы сохраняются, но не обрабатываются — нет эмбеддингов, нет графа знаний, нет поиска.

⚠️ Блокер 4: Нет векторной БД
Описание: ChromaDB установлена, но не интегрирована.

⚠️ Блокер 5: Нет графовой БД

function findAllChats() {
    const chats = [];
    const seen = new Set();
    
    // Расширенные селекторы
    const selectors = [
        'a[href*="/chat/"]',
        'a[href*="/c/"]',
        '[role="button"][data-testid*="chat"]',
        '.group\\/conversation-item a',
        '.chat-list-item',
        '[class*="conversation"] a'
    ];
    
    for (const selector of selectors) {
        document.querySelectorAll(selector).forEach(el => {
            const a = el.tagName === 'A' ? el : el.querySelector('a');
            if (!a) return;
            
            const href = a.href;
            const match = href.match(/\/chat\/([^\/]+)/);
            const id = match ? match[1] : null;
            
            if (id && !seen.has(id)) {
                seen.add(id);
                chats.push({
                    id: id,
                    url: href,
                    title: a.textContent?.trim() || el.textContent?.trim() || 'Untitled',
                    element: el
                });
            }
        });
    }
    
    console.log(`Found ${chats.length} unique chats`);
    return chats;
}

## 🤖 **DeepSeek**

Отличный архитектурный вопрос. Пока вы сфокусированы на исправлении багов в пользовательском скрипте, я как **Senior Architect** уже смотрю на два шага вперед — как вписать нашу текущую работу в долгосрочную архитектуру, где OpenClaw играет ключевую роль.

Анализ поисковых результатов показывает, что OpenClaw — это не просто очередной фреймворк, а идеальный "оркестратор" для решения наших проблем (Блокеры 3, 4, 5) и масштабирования проекта [citation:1][citation:4][citation:8].

Вот как OpenClaw радикально усилит наш проект, разделенный по ролям:

### 1. Решение Блокера 3 и 4 (Preprocessing Agent + Vector DB) через "Local-First RAG"
Сейчас мы планируем писать кастомного Preprocessing Agent на FastAPI. OpenClaw предлагает более элегантное решение.
*   **Как это работает (Senior ML/AI Engineer):** OpenClaw уже имеет встроенную **"Persistent Memory"** , которая построена на SQLite + `sqlite-vec` [citation:8]. Это именно то, что нам нужно: локальная векторная база данных без лишнего Docker-контейнера.
*   **Интеграция (Senior Backend Engineer):** Вместо того чтобы писать воркер, слушающий папку `Clippings/`, мы можем настроить OpenClaw на автоматическое потребление этих Markdown-файлов.
    *   **Механизм:** Мы помещаем наши клиппинги в директорию `~/.openclaw/memory/` (или символическую ссылку на `Obsidian/Clippings/`).
    *   **Результат:** OpenClaw автоматически:
        1.  Разобьет их на чанки [citation:8].
        2.  Сгенерирует эмбеддинги (через OpenAI/text-embedding-3-small, как мы и планировали) [citation:8].
        3.  Сохранит векторы в SQLite.
        4.  **Главное:** Если `sqlite-vec` не загрузится, он упадет в JS-брутфорс (вычисление косинусной близости в памяти), что дает нам **отказоустойчивость "из коробки"** [citation:8].

### 2. Решение Блокера 5 (Графовая БД) через openclaw-mem
Нам нужен граф знаний (Neo4j). Отдельный репозиторий **`openclaw-mem`** создан именно для этого [citation:5].
*   **Как это работает (Senior ML/AI Engineer):** `openclaw-mem` — это "sidecar" для OpenClaw, который умеет:
    *   Извлекать концепты (он называет это `triage` и извлечением задач) [citation:5].
    *   Строить связи между наблюдениями.
    *   Хранить всё в SQLite с FTS5 (полнотекстовый поиск), но в перспективе (ROADMAP) там заложена **графовая память (`graphic-memory-graphrag-lite`)** [citation:5].
*   **Архитектурный сдвиг (Senior Architect):** Мы можем отказаться от идеи поднимать тяжелую Neo4j прямо сейчас. Вместо этого мы интегрируем `openclaw-mem`. Он будет потреблять наши клиппинги, строить локальный граф (пока упрощенный) и давать нам API для поиска. Когда граф станет слишком большим, мы "выгрузим" данные в Neo4j.

### 3. "Мозг" для массового сохранения (Mass Save)
Почему наша кнопка "Save All" глупа? Она просто скрепит DOM. OpenClaw дает ей интеллект.
*   **Интеграция (Senior DevOps Engineer):** Мы разворачиваем OpenClaw. Наш UserScript (который мы сейчас чиним) должен отправлять найденные чаты не только на FastAPI, но и в OpenClaw через его Gateway [citation:4][citation:10].
*   **Протокол (Senior Backend Engineer):** Отправляем JSON с текстом чата. OpenClaw через свой **Pi-embedded** [citation:4] берет на себя:
    *   Тяжелую работу (обход ограничений, выполнение действий).
    *   Использование DeepSeek API (который отлично интегрируется) [citation:3][citation:6] для суммаризации и извлечения сути перед сохранением в память.

### 4. Исправление багов навигации (Неожиданный бонус)
Вы сейчас бьетесь над MutationObserver и перехватом кликов. OpenClaw решает эту проблему архитектурно.
*   **Архитектурная причина (Senior Architect):** Проблема в том, что наш скрипт живет *внутри* SPA и пытается угадать, когда контент поменялся.
*   **Решение с OpenClaw:** OpenClaw работает *вне* браузера. Он управляет браузером через DevTools Protocol или Playwright. Он точно знает, когда навигация завершилась, потому что он сам её инициировал. Это подход уровня "автоматизация", а не "скрептинг".

### 5. Итоговая архитектура (Как мы это соединяем)

Вот как будет выглядеть наша система после интеграции OpenClaw, согласно лучшим практикам из статей [citation:1][citation:4][citation:5]:

1.  **Уровень сбора данных (Client-Side):**
    *   **Компонент:** UserScript (Violentmonkey).
    *   **Задача:** Только клик по кнопке и отправка "сырого" HTML/Markdown на наш внутренний сервер (FastAPI). **Больше никакой логики версионирования и поиска чатов в скрипте.**

2.  **Уровень оркестрации (Server-Side):**
    *   **Компонент:** **OpenClaw (Core + Pi-embedded)** .
    *   **Задача:**
        *   Получает "сырой" чат от FastAPI.
        *   Использует DeepSeek Reasoner для очистки и структурирования [citation:3].
        *   Сохраняет в **Obsidian** (как сейчас).
        *   **НО:** Одновременно отправляет данные в **openclaw-mem** для индексации.

3.  **Уровень памяти (Storage & Retrieval):**
    *   **Компонент:** **openclaw-mem** (SQLite + FTS5 + Вектора) [citation:5][citation:8].
    *   **Задача:**
        *   Хранит эмбеддинги (ChromaDB больше не нужна).
        *   Строит упрощенный граф связей.
        *   Предоставляет API для семантического поиска.

4.  **Уровень поиска (Query):**
    *   **Компонент:** Semantic Search API (может быть оберткой над openclaw-mem).
    *   **Задача:** Получать запрос от пользователя, искать в векторах и графе, возвращать результат.

#### **Вариант 1 (Основной): Полностью локальный Early Bird (Ollama)**

## 🔍 OpenCode vs OpenClaw: В чём разница?

**OpenCode** — это **фреймворк для разработки агентов**, который выполняет задачи локально [citation:6]. Он умеет работать с файлами, запускать команды, писать код. Но у него есть критическая проблема: он отправляет ВЕСЬ контекст проекта при каждом запросе, что сжигает безумное количество токенов [citation:7].

**OpenClaw** — это **оркестратор**, который управляет агентами и их памятью. Он не заменяет OpenCode, а надстраивается над ним [citation:4].

## 🧠 Почему мы не отказались — мы надстроили

В японском техническом анализе [citation:4] чётко показана архитектура, которую мы фактически копируем:

```
■ Энтити: OpenClaw 2号 (指揮官/Оркестратор)
  └ Среда: Внутри Docker-контейнера
  └ Задачи: Полевой командир. Декомпозиция задач, выдача указаний, динамический призыв клонов

■ Энтити: OpenCode (実行部隊/Исполнитель)
  └ Среда: Внутри Docker-контейнера
  └ Задачи: Отряд исполнения. Перевод, кодинг, запуск локальных серверов
```

То есть:
- **OpenClaw** — это генерал, который думает и планирует
- **OpenCode** — это солдаты, которые делают конкретную работу

## 🔧 Что изменилось в нашем плане?

Мы не отказались от OpenCode. Мы **перераспределили роли**:

### Было (ошибочное понимание):
```
OpenCode = умный оркестратор + исполнитель
```

### Стало (правильная архитектура):
```
OpenClaw = оркестратор (думает, планирует, управляет памятью)
OpenCode = исполнитель (пишет код, запускает команды)
```

## 🎯 Почему это важно для нашего проекта?

В Issue #11570 на GitHub [citation:1] пользователь прямо спрашивает: "Можно ли добавить в OpenCode функции OpenClaw — демон, память, автономность?" И ответ сообщества: **OpenCode не должен этим заниматься**. Это разные уровни абстракции.

**OpenCode плох для оркестрации потому что:**
1. Жрёт токены как не в себя (до 50к токенов на простой вопрос) [citation:7]
2. Не имеет встроенной памяти (только руками через плагины) [citation:2]
3. Не умеет в графы знаний (нужен отдельный orchestrator-opencode) [citation:5]

**OpenClaw хорош для оркестрации потому что:**
1. Может сам принимать решения на основе мета-познания [citation:4]
2. Умеет клонировать себя для параллельной обработки [citation:4]
3. Работает с Neo4j для графов знаний "из коробки" [citation:8]

## ТЕКУЩИЕ ПРОБЛЕМЫ (НУЖНО ИСПРАВИТЬ)

### 🐛 Блокер 1: Версионирование не обновляется при навигации
**Описание:** При переходе между чатами через боковую панель, информация о версии не обновляется. Кнопка показывает версию предыдущего чата.

**Воспроизведение:**
1. Открыть чат А → сохранить (становится v1)
2. Перейти в чат Б → кнопка все еще показывает "Save v2" (для чата А)
3. Сохранить чат Б → он сохраняется как v2, хотя должен быть v1

**Причина:** MutationObserver отслеживает изменение URL, но не отслеживает изменение контента в SPA. При переходе по ссылкам в боковой панели URL может не меняться (используется hash или pushState с тем же URL).

### 🐛 Блокер 2: Mass Save сохраняет только один чат
**Описание:** Функция findAllChats() находит только один чат в DOM, хотя в боковой панели их много.

**Воспроизведение:**
1. Нажать красную кнопку "📚 Save All"
2. В диалоге показывает "Found 1 chats"
3. Сохраняется только текущий чат

**Причина:** Селекторы не находят все элементы чатов в боковой панели. Нужно исследовать структуру DOM DeepSeek.

### 🐛 Блокер 3: Нет Preprocessing Agent
**Описание:** Файлы сохраняются, но не обрабатываются — нет эмбеддингов, нет графа знаний, нет поиска.

### 🐛 Блокер 4: Нет векторной БД
**Описание:** SQLite с векторами не настроена, ChromaDB не интегрирована.

### 🐛 Блокер 5: Нет графовой БД
**Описание:** Neo4j не развёрнута и не настроена.

### 🐛 Блокер 6: OpenClaw не развёрнут
**Описание:** Оба экземпляра OpenClaw (Mac и VPS) не установлены и не сконфигурированы.

### 🐛 Блокер 7: Node-RED flows не настроены
**Описание:** Нет маршрутизации данных между UserScript, Mac и VPS.

### Задача 3: Улучшение findAllChats (Senior Backend)

```javascript
function findAllChats() {
    const chats = [];
    const seen = new Set();
    
    // Расширенные селекторы на основе анализа DOM
    const selectors = [
        'a[href*="/chat/"]',
        'a[href*="/c/"]',
        '[role="button"][data-testid*="chat"]',
        '.group\\/conversation-item a',
        '.chat-list-item',
        '[class*="conversation"] a',
        '[class*="ChatHistory"] a',
        '[class*="sidebar"] a[href*="/chat/"]'
    ];
    
    for (const selector of selectors) {
        document.querySelectorAll(selector).forEach(el => {
            const a = el.tagName === 'A' ? el : el.querySelector('a');
            if (!a) return;
            
            const href = a.href;
            const match = href.match(/\/chat\/([^\/]+)/);
            const id = match ? match[1] : null;
            
            if (id && !seen.has(id)) {
                seen.add(id);
                chats.push({
                    id: id,
                    url: href,
                    title: a.textContent?.trim() || el.textContent?.trim() || 'Untitled',
                    element: el
                });
            }
        });
    }
    
    console.log(`Found ${chats.length} unique chats`);
    return chats;
}
```
