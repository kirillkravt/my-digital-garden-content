# Требования к обработке негативных сценариев СБП

## 👤 **Kirill**

Из прошлых переписок по процессу СБП переводов B2C/C2B по взаимодействию Core и Back-office напиши требования к обработке негативных сценариев.
Примерный контекст:
Core выполняет процессинг платежей и выполняет все необходимы проверки для авторизации платежа обращаясь к системам (Эдо для проверки ЭЦП, антифрод, финмониторинг, шлюз СБП) 
Back-office - оффлайн модуль для учета операций для целей будущей сверки с ABS.
В Core - нет базы и все параметры операции живут в только на время прохождения процесса перевода.

Нужно в связке Core - Back-office:
1. Уметь работать с дубликатами операций:
могут приходить дубли (ретраи от систем Шлюз СБП и ТСП) и нужно исключать их обработку если уже есть операция учтенная в BO
2. Уметь "возвращаться" в процесс. Если не получен ответ от какой-то из систем, а после восстановления работы ответ доходит или может быть получен отдельным вызовом этого сервиса для получения статуса, то нужно не обрабатывать новые запросы операций (ретраи), а вернутся к завершению процесса на котором произошел сбой ошибка
3. Уметь "досылать" callbaсk и авизо по первичной операции, а не дублю когда становится известен корректный статус.
4. Уметь получать/передавать гарантированные ответы - предусмотреть логику ретраев при взаимодействии с Шлюзом СБП и ТСП

### Требования к обработке негативных сценариев в процессе СБП (B2C/C2B)  
**Связка Core ↔ Back-office (BO)**  

#### **1. Обработка дубликатов операций**  
- **Идентификация дублей**:  
  - Core должен передавать в BO уникальный идентификатор операции (например, `transaction_id` + `request_id` или хеш ключевых параметров).  
  - BO проверяет наличие операции по этому идентификатору перед учётом.  
- **Механизм отклонения дублей**:  
  - Если BO обнаруживает дубль (статус операции уже учтён), Core получает ответ с текущим статусом из BO и:  
    - Не повторяет процессинг.  
    - Досылает callback/авизо ТСП/Шлюзу СБП на основе данных из BO.  
- **Гарантия идемпотентности**:  
  - Все вызовы BO (на создание/обновление операции) должны быть идемпотентны (повторный запрос с тем же `request_id` не меняет состояние).  

#### **2. Восстановление процесса после сбоев**  
- **Сохранение состояния операции**:  
  - BO хранит промежуточные статусы операций (например, "ожидает ответа от Эдо", "отправлен в антифрод").  
  - Core при ретрае запрашивает у BO текущий статус операции и продолжает с последнего шага.  
- **Обработка "потерянных" ответов**:  
  - Если система (Эдо, шлюз СБП и т.д.) отвечает позже, Core:  
    1. Проверяет статус операции в BO.  
    2. Если операция не завершена — применяет ответ и обновляет статус в BO.  
    3. Если операция уже завершена — игнорирует ответ (логирует инцидент).  
- **Ретри для завершающих действий**:  
  - Для callback/авизо Core повторяет отправку, пока не получит подтверждение от ТСП/Шлюза СБП (с экспоненциальным бекоффом).  

#### **3. Корректная отправка callback/авизо**  
- **Привязка к первоначальной операции**:  
  - Все callback/авизо отправляются только с данными из первоначального запроса (даже если ретрай пришёл с изменёнными параметрами).  
- **Механизм досылки**:  
  - BO хранит историю статусов и исходные параметры операции.  
  - При восстановлении связи Core запрашивает у BO список операций с неуспешными callback/авизо и повторяет отправку.  

#### **4. Гарантированная доставка ответов**  
- **Ретри для внешних систем**:  
  - При взаимодействии с Шлюзом СБП/ТСП Core повторяет запросы при:  
    - Таймаутах.  
    - Ошибках 5xx.  
    - Ошибках сети.  
  - Максимальное число попыток и интервалы (например, 3 попытки с бекоффом 1s, 5s, 10s).  
- **Подтверждение доставки**:  
  - ТСП/Шлюз СБП должны подтверждать получение callback/авизо (HTTP 200 + `acknowledgement_id`).  
  - BO фиксирует факт отправки и подтверждения.  

#### **Дополнительные требования**  
- **Логирование**:  
  - Все этапы (включая ретраи и проверки дублей) должны логироваться в Core и BO для аудита.  
- **Таймауты и мониторинг**:  
  - Настроенные таймауты на ожидание ответов от внешних систем (Эдо, антифрод и т.д.).  
  - Мониторинг "зависших" операций (статус в BO не обновлялся дольше N минут).  

#### **Пример сценариев**  
1. **Дубль операции**:  
   - ТСП отправляет повторный запрос из-за таймаута.  
   - Core проверяет BO, обнаруживает существующую операцию и отправляет текущий статус ТСП без повторного процессинга.  

2. **Сбой при проверке ЭЦП**:  
   - Core не получил ответ от Эдо, операция в BO осталась в статусе "ожидает ЭЦП".  
   - После восстановления связи Core запрашивает статус в Эдо, получает ответ и обновляет BO.  

3. **Пропущенный callback**:  
   - Callback к ТСП не дошёл. BO хранит статус "ожидает подтверждения callback".  
   - Core периодически проверяет такие операции и повторяет отправку.  

**Реализация**:  
- Для BO: API для проверки дублей (`GET /operations/{hash_or_id}`) и обновления статусов (`PATCH /operations/{id}/status`).  
- Для Core: механизм повторных запросов с отслеживанием `request_id` и таймаутами.  
- Общая очередь "на восстановление" для операций с неудачными шагами.

1. **Хранение чувствительных данных**:  
   - Vault используется для секретов (API-ключи, сертификаты, токены СБП, доступы к Эдо).  
   - Core запрашивает секреты динамически (не хранит их в памяти долго).  

2. **Динамические секреты для Шлюза СБП/ТСП**:  
   - Vault генерирует временные токены доступа с TTL (например, 1 час).  
   - Core обновляет их через Vault API перед истечением срока.  

3. **Шифрование данных**:  
   - Vault предоставляет ключи для шифрования PII (персональных данных) перед записью в лог/BO.  
   - Расшифровка только при необходимости (аудит, расследование).  

4. **Ротация ключей**:  
   - Автоматическая смена ключей/сертификатов (например, раз в 30 дней).  
   - Core должен обрабатывать ошибки "недействительный ключ" и запрашивать актуальный.  

5. **Доступы для BO**:  
   - BO имеет отдельный ограниченный доступ в Vault (только чтение секретов для сверки).  

6. **Резервное копирование и DR**:  
   - Настройка Vault Cluster с репликацией для отказоустойчивости.

## 🤖 **DeepSeek**

**6.8.3 Обработка исключений**

**6.8.3.1 Обработка дубликатов операций**
- Система должна обеспечивать однократную обработку каждой уникальной финансовой операции.
- Реализуется механизм идентификации и отклонения повторяющихся запросов на обработку операций.
- Обеспечивается гарантированная идемпотентность при взаимодействии компонентов системы.

**6.8.3.2 Восстановление процесса после сбоев**
- Система должна сохранять промежуточные состояния операций для возможности возобновления обработки с точки прерывания.
- Обеспечивается механизм обработки запоздавших ответов от внешних систем.
- Реализуется возможность повторной отправки исходящих уведомлений до их успешной доставки.

**6.8.3.3 Гарантированная доставка ответов**
- Система обеспечивает повторные попытки отправки запросов к внешним системам при возникновении сбоев связи.
- Реализуется механизм подтверждения успешной доставки исходящих сообщений.
- Обеспечивается отслеживание статуса доставки всех исходящих уведомлений.

**6.8.3.4 Корректная отправка уведомлений**
- Все исходящие уведомления формируются исключительно на основе данных первоначального запроса операции.

## 🤖 **DeepSeek**

### **6.7.5.1 Этап процесса: Инициирование операции**

#### **Цель этапа**
Обработка первоначального запроса от ТСП (Торгово-Сервисного Предприятия) на проведение операции и формирование предварительного ответа.

#### **Взаимодействие с ТСП**

**1. Получение запроса от ТСП**
- ТСП направляет запрос на инициирование операции в Core-СБП
- Параметры запроса:
  - Идентификатор операции (operationId)
  - Данные плательщика и получателя
  - Сумма операции
  - Дополнительные параметры (назначение платежа и т.д.)

**2. Валидация входящих данных**
- Проверка обязательных полей и их формата
- Валидация бизнес-правил:
  - Корректность сумм и валюты
  - Соответствие форматам реквизитов
  - Проверка лимитов операции

**3. Формирование промежуточного ответа**
- При успешной валидации:
  - Core-СБП возвращает статус `processing`
  - ТСП получает подтверждение о принятии операции в обработку
- При ошибках валидации:
  - Немедленный возврат ошибки с соответствующим кодом
  - Описание ошибки в стандартизированном формате

#### **Обработка исключительных ситуаций**

**1. Таймаут соединения с ТСП**
- **Сценарий**: Не получен ответ от ТСП при подтверждении принятия операции
- **Действия**:
  - Повторная отправка ответа через 1 секунду
  - Прогрессивное увеличение интервалов (t = 2^c)
  - Максимум 10 попыток для положительного статуса
- **Результат**:
  - При достижении лимита попыток - фиксация инцидента
  - Операция переходит в статус "требует ручного вмешательства"

**2. Повторный запрос от ТСП**
- **Сценарий**: ТСП отправляет дублирующий запрос с тем же operationId
- **Действия**:
  - Проверка существующей операции в системе
  - Возврат текущего статуса операции (идемпотентность)
  - Отсутствие повторной обработки
- **Результат**: Гарантия однократного выполнения операции

**3. Некорректные данные от ТСП**
- **Сценарий**: Ошибки в формате или содержании запроса
- **Действия**:
  - Немедленный возврат ошибки 400/422
  - Детальное описание проблемы в поле `detail`
  - Фиксация попытки в логах для анализа
- **Результат**: ТСП получает информацию для исправления запроса

#### **Механизмы гарантий**

**1. Идемпотентность**
- Все запросы с одинаковым `operationId` обрабатываются однократно
- Повторные запросы возвращают текущий статус операции
- Гарантия отсутствия дублирования операций

**2. Трассируемость**
- Сквозная идентификация запроса (requestId)
- Логирование всех этапов обработки
- Возможность отслеживания статуса операции

**3. Восстановление при сбоях**
- Сохранение промежуточного состояния операции
- Возможность повторной отправки ответа ТСП
- Механизм ручного вмешательства при критических сбоях

#### **Интеграция с последующими этапами**

После успешного инициирования операции:
- Операция передается на этап авторизации
- ТСП получает уведомление о принятии в обработку
- Запускаются параллельные процессы проверок (ЭДО, Антифрод, Финмониторинг)

#### **Бизнес-логика ответов**

**Успешный сценарий:**
```json
{
  "status": 202,
  "type": "processing",
  "title": "Операция принята в обработку",
  "instance": "req-123456"
}
```

**Ошибочный сценарий:**
```json
{
  "status": 422,
  "type": "validation_error", 
  "title": "Ошибка валидации данных",
  "detail": "Неверный формат номера счета получателя",
  "code": "VAL_001"
}
```

Данный этап обеспечивает надежное взаимодействие с ТСП при старте операции, гарантируя однократность обработки и предоставление четкого статуса операции.

## 🤖 **DeepSeek**

**Да, между обработкой исключений для B2C операций и C2B возвратов есть существенные различия, несмотря на схожесть процессов:**

---

### **1. Различия в бизнес-логике и статусах**

#### **B2C (Платеж клиенту):**
- **Инициатор**: ТСП
- **Критичные статусы**: `PROCESSING` → `COMPLETED`/`REJECTED`
- **Особенности**: 
  - Проверка лимитов на отправку
  - Верификация получателя (физ. лицо)
  - Приоритет - скорость доставки средств

#### **C2B возврат (Возврат платежа):**
- **Инициатор**: ТСП (но по инициативе клиента)
- **Критичные статусы**: `ACCEPTED` → `RETURNED`/`CANCELLED`
- **Особенности**:
  - Привязка к исходной операции C2B
  - Проверка возможности возврата (сроки, остаток)
  - Строгая верификация для исключения мошенничества

---

### **2. Различия в обработке ошибок валидации**

#### **B2C:**
```json
{
  "code": "B2C_LIMIT_EXCEEDED",
  "detail": "Превышен дневной лимит на отправку B2C платежей"
}
```

#### **C2B возврат:**
```json
{
  "code": "REFUND_NOT_ALLOWED", 
  "detail": "Возврат невозможен: исходная операция старше 30 дней"
}
```

---

### **3. Различия в механизмах ретраев**

#### **B2C - приоритет скорости:**
- Таймауты короче
- Меньше попыток ретраев
- Быстрый отказ при ошибках антифрода

#### **C2B возврат - приоритет безопасности:**
- Дополнительные проверки при ретраях
- Обязательная верификация через ЭДО
- Жесткие требования к аудиту

---

### **4. Различия в обработке дубликатов**

#### **B2C:**
- Проверка по `operationId + requestId`
- Защита от повторных списаний

#### **C2B возврат:**
- Дополнительная проверка привязки к исходной операции
- Контроль суммы возврата (не больше исходного платежа)
- Проверка "не возвращено ли уже"

---

### **5. Различия в финальных статусах и уведомлениях**

#### **B2C:**
- Callback с финальным статусом (`COMPLETED`/`REJECTED`)
- CAMT.054 - как обычное платежное поручение

#### **C2B возврат:**
- Callback со статусом возврата (`RETURNED`/`CANCELLED`)  
- CAMT.054 с специальным кодом операции (возврат)
- Уведомление клиента об инициации возврата

---

### **6. Различия в обработке сбоев на этапе финализации**

#### **B2C:**
- При недоступности шлюза СБП - быстрый отказ
- Минимальное время ожидания callback

#### **C2B возврат:**
- Увеличенные таймауты ожидания
- Обязательное подтверждение от НСПК
- Механизм ручного подтверждения при сбоях

---

### **7. Юридические различия**

#### **B2C:**
- Регулирование как перевода физ. лицу
- Требования 115-ФЗ к идентификации

#### **C2B возврат:**
- Регулирование как возврата средств
- Требования к срокам обработки
- Особый учет для налоговой отчетности

---

### **Резюме:**

| Аспект | B2C | C2B возврат |
|--------|-----|-------------|
| **Приоритет** | Скорость | Безопасность |
| **Валидация** | Лимиты отправителя | Привязка к исходной операции |
| **Ретраи** | Быстрые, минимум попыток | Длительные, с доп. проверками |
| **Аудит** | Стандартный | Расширенный |
| **Юридика** | Перевод физ. лицу | Возврат средств |

### 2. Проблема с лишними символами (`&νβσπ;`) при вставке из Word

**Почему это происходит?**

Это классическая проблема кодировки. Символы `&νβσπ;` — это HTML-представление невидимого "узкого неразрывного пробела" (Non-Breaking Space, NBS).

*   **В Word:** Когда вы делаете отступ с помощью табуляции или пробелов, Word иногда заменяет обычные пробелы на NBS, чтобы улучшить форматирование.
*   **При копировании:** Буфер обмена сохраняет эти символы в их HTML-кодировке.
*   **При вставке:** Система, куда вы вставляете текст (часто это веб-редакторы, CMS или, как в нашем случае, чат-интерфейс), пытается отобразить этот HTML-код как обычный текст, и вы видите `&νβσπ;`.

**Как это исправить? (3 надежных способа)**

**Способ 1: Промежуточный буфер — Блокнот (Notepad)**
Это самый простой и надежный метод.
1.  Скопируйте текст из Word.
2.  Вставьте его в **Блокнот** (Notepad) или любой другой простейший текстовый редактор.
3.  Блокнот не поддерживает сложное форматирование и удалит все спецсимволы.
4.  Скопируйте уже "очищенный" текст из Блокнота и вставьте в целевую систему.

**Способ 2: Использовать "Специальную вставку" или "Вставить без форматирования"**
Во многих системах есть такая опция.
*   **В веб-интерфейсах:** Часто можно использовать сочетание клавиш `Ctrl + Shift + V` вместо `Ctrl + V`.
*   **В Word или других редакторах:** После вставки ищите иконку с буквой "А" или подписью "Сохранить только текст".

**Способ 3: Поиск и замена в Word (если проблема постоянная)**
1.  В Word откройте окно "Найти и заменить" (`Ctrl + H`).
2.  В поле **"Найти"** введите (лучше скопируйте отсюда): `^s`
    *   Символ `^s` в Word означает тот самый "узкий пробел".
3.  В поле **"Заменить на"** введите обычный пробел.
4.  Нажмите "Заменить все".

**Рекомендация:** Для постоянной работы используйте **Способ 1 (Блокнот)**. Это займет 5 секунд и гарантированно избавит от проблемы.
