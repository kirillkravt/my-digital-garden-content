# Query-параметры, тело и заголовки API

## 👤 **Kirill**

query параметры в боди или в хэдерах?

---

## 🤖 **DeepSeek**

Отличный вопрос! Это одно из ключевых решений при проектировании API.

**Короткий ответ: Query-параметры передаются в URL, а не в теле запроса (body) и не в заголовках (headers).**

Давайте разберем подробнее, что куда относится.

---

### 1. Query-параметры (Параметры запроса)

*   **Местоположение:** Часть URL (адреса).
*   **Синтаксис:** Начинаются после знака `?`, разделяются амперсандом `&`.
    *   `https://api.example.com/users?**page=2&limit=10&sort=name**`
*   **Назначение:**
    *   **Фильтрация:** `?category=books&author=tolkien`
    *   **Поиск:** `?q=query+string`
    *   **Сортировка:** `?sort=price&order=asc`
    *   **Пагинация:** `?page=5&limit=20`
    *   **Опциональные параметры,** которые изменяют логику "что вернуть".
*   **Особенности:**
    *   Видимы в адресной строке браузера.
    *   Кэшируются браузером и могут сохраняться в истории.
    *   Имеют ограничения по длине (зависит от браузера и сервера).

### 2. Тело запроса (Body)

*   **Местоположение:** Отдельная часть HTTP-запроса, не видимая в URL.
*   **Формат:** Обычно `application/json` или `application/x-www-form-urlencoded`.
*   **Назначение:**
    *   **Передача данных для создания или изменения ресурса.** Например, при отправке формы регистрации или изменении товара.
    *   Используется с методами **POST, PUT, PATCH**.
*   **Пример (JSON):**
    ```json
    {
      "username": "john_doe",
      "email": "john@example.com",
      "password": "securepassword"
    }
    ```

### 3. Заголовки (Headers)

*   **Местоположение:** Мета-информация HTTP-запроса.
*   **Назначение:**
    *   **Управление запросом и передача служебной информации.**
    *   **Аутентификация:** `Authorization: Bearer <token>`
    *   **Определение типа контента:** `Content-Type: application/json`
    *   **Кэширование:** `Cache-Control: no-cache`
    *   **Клиентская информация:** `User-Agent: ...`
*   **Пример:**
    ```
    GET /users/123 HTTP/1.1
    Host: api.example.com
    Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
    Content-Type: application/json
    ```

### Сводная таблица

| Местоположение | Назначение | Типичные HTTP-методы | Пример |
| :--- | :--- | :--- | :--- |
| **Query-параметры** | URL | Фильтрация, поиск, пагинация, сортировка | `GET /users?**active=true**` |
| **Тело запроса (Body)** | Отдельная часть | Передача данных для создания/изменения | `POST /users` **{ "name": "John" }** |
| **Заголовки (Headers)** | Мета-данные | Аутентификация, тип контента, кэширование | `Authorization: Bearer ...` |

---

### Практическое правило (REST API)

*   **Используйте `query`-параметры для `GET`-запросов,** когда вам нужно **отфильтровать, найти или ограничить** набор возвращаемых данных.
*   **Используйте `body` для `POST`, `PUT`, `PATCH`-запросов,** когда вам нужно **отправить данные** на сервер для создания или обновления ресурса.
*   **Используйте `headers` для служебной информации,** такой как **токены доступа, тип передаваемых данных и т.д.**

### Исключения и тонкости

*   **GET-запросы с телом:** Спецификация HTTP не запрещает GET-запросам иметь тело, но это крайне нестандартно и многие библиотеки и серверы могут его игнорировать. **Не делайте так.**
*   **POST для сложных фильтров:** Иногда, если фильтр очень сложный (например, составной логический запрос), его проще передать в теле POST-запроса, даже если операция является по сути "чтением". Это иногда называют "POST по необходимости". Хотя это нарушает строгую идиоматику REST, это практично.

**Вывод:** Query-параметры — это часть URL для модификации запроса на получение данных. Тело запроса — для передачи данных, которые вы хотите сохранить или обновить. Заголовки — для служебной информации о самом запросе.
