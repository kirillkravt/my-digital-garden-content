## 🤖 **DeepSeek**

В процессе обработки C2B-платежей (от бизнеса клиенту) **запрос на общую сумму** и **запрос на проведение единичной операции** можно отличить по следующим ключевым признакам:

---

### **1. Различия в структуре запроса**
| Критерий               | Единичная операция                          | Реестр (общая сумма)                     |
|------------------------|---------------------------------------------|------------------------------------------|
| **Формат тела запроса** | Содержит данные **одной операции** (`operationId`, сумма, реквизиты получателя) | Содержит **массив операций** с агрегацией по получателю/счету |
| **HTTP-метод/эндпоинт** | `POST /v2/operations/{operationId}`         | `POST /v2/batches` (или аналогичный)     |
| **Заголовки**          | `Content-Type: application/json` (стандартный) | Может включать `X-Batch-Processing: true` |

**Пример тела запроса:**  
```json
// Единичная операция
{
  "operationId": "12345",
  "amount": 1000,
  "recipient": "41001123456789"
}

// Реестр
{
  "batchId": "BATCH-001",
  "totalAmount": 5000,
  "operations": [
    {"operationId": "12345", "amount": 1000},
    {"operationId": "67890", "amount": 4000}
  ]
}
```

---

### **2. Различия в логике обработки (на диаграмме)**
На UML-диаграмме это отражено ветвлением (`alt/else`):  
```plantuml
alt#Skyblue Единичный платеж
  API -> Core : POST /v2/operations/{operationId}
  Core -> BO : Запрос на 1 операцию
else Реестр
  API -> Core : POST /v2/batches
  Core -> BO : Массив операций (PUT stage2)
end
```

---

### **3. Бизнес-правила**
| Критерий               | Единичная операция                          | Реестр                     |
|------------------------|---------------------------------------------|----------------------------|
| **Тип счета**          | Может быть любой (включая [ACC_TYPE1])      | Только **счета [ACC_TYPE2]** (номинальные/аггрегирующие) |
| **Лимиты**             | Проверяется каждая операция индивидуально   | Проверяется **общая сумма** реестра |
| **Документооборот**    | Формируется 1 платежное поручение           | Формируется **1 общий документ** (например, camt.054) |

---

### **4. Системные интеграции**
- **Для единичных операций:**  
  Данные сразу передаются в CFT (шаг 1.7 в таблице).  
  ```plantuml
  Payments -> ABS -> CFT : Данные 1 операции
  ```

- **Для реестров:**  
  Сначала формируется реестр в Payments/EDO, затем данные идут в ABS/CFT (шаги 1.8–1.11).  
  ```plantuml
  API -> Payments : Реестр операций
  Payments -> ABS -> CFT : Данные из реестра
  ```

---

### **5. Как определить тип на практике?**
1. **Анализ API-документации**:  
   - Эндпоинты для реестров обычно содержат слова `batch`, `bulk`, `aggregate`.  
   - Пример: `POST /v2/batches` vs `POST /v2/operations`.

2. **Логирование запросов**:  
   - Запросы реестров имеют больший размер тела (из-за массива операций).  
   - В логах Core будет указан тип обработки: `"processingType": "BATCH"`.

3. **Проверка счетов**:  
   - Если операция привязана к **[ACC_TYPE2]** — высокая вероятность агрегации.

4. **Метаданные**:  
   - Поле `X-Request-Scope: SINGLE|BATCH` в заголовках.

---

### **Пример из вашей диаграммы**
В процессе C2B:  
- **Единичные операции** идут по цепочке:  
  `Core → BO → API → Payments → ABS → CFT`.  

- **Реестры** обрабатываются через:  
  `API → Payments → ABS → CFT` (с предварительным формированием документа в EDO).

**Важно:** Реестры используются для оптимизации нагрузки (например, массовые выплаты физлицам), а единичные операции — для срочных/отдельных платежей.
