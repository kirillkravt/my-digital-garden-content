# AWS Data Services и настройка ETL для передачи справочников

## AWS Data Services для работы с данными

AWS предлагает широкий спектр сервисов для работы с данными, включая ETL (Extract, Transform, Load) процессы:

### Основные сервисы
1. **AWS Glue** - полностью управляемый ETL-сервис
   - Автоматическое обнаружение схемы данных
   - Генерация ETL-скриптов
   - Интеграция с другими AWS сервисами

2. **Amazon EMR** (Elastic MapReduce) - для обработки больших объемов данных
   - Поддержка Hadoop, Spark, Hive и других фреймворков

3. **AWS Data Pipeline** - оркестрация данных между сервисами AWS

4. **Amazon Kinesis** - обработка потоковых данных в реальном времени

5. **AWS DMS** (Database Migration Service) - миграция баз данных

6. **Amazon Redshift** - хранилище данных

7. **Amazon Athena** - интерактивный анализ данных в S3

## Настройка ETL для передачи справочников

### Пример архитектуры с AWS Glue
1. **Источник данных** (например, база данных или файлы)
2. **AWS Glue Catalog** - метаданные о данных
3. **AWS Glue ETL Job** - преобразование данных
4. **Целевое хранилище** (S3, Redshift, RDS и т.д.)

### Шаги настройки:
1. **Создайте соединение с источником данных**:
   - В консоли AWS Glue выберите "Connections"
   - Добавьте соединение с вашей БД (JDBC) или файловым хранилищем

2. **Определите каталог данных (Crawler)**:
   ```python
   # Пример скрипта AWS Glue
   import sys
   from awsglue.transforms import *
   from awsglue.utils import getResolvedOptions
   from pyspark.context import SparkContext
   from awsglue.context import GlueContext
   from awsglue.job import Job

   args = getResolvedOptions(sys.argv, ['JOB_NAME'])
   sc = SparkContext()
   glueContext = GlueContext(sc)
   spark = glueContext.spark_session
   job = Job(glueContext)
   job.init(args['JOB_NAME'], args)

   # Источник данных
   datasource = glueContext.create_dynamic_frame.from_catalog(
       database = "your-database",
       table_name = "source_table",
       transformation_ctx = "datasource"
   )

   # Преобразования
   applymapping = ApplyMapping.apply(
       frame = datasource,
       mappings = [("source_column", "string", "target_column", "string")],
       transformation_ctx = "applymapping"
   )

   # Загрузка в целевое хранилище
   glueContext.write_dynamic_frame.from_catalog(
       frame = applymapping,
       database = "target-database",
       table_name = "target_table"
   )

   job.commit()
   ```

3. **Настройте триггеры или расписание**:
   - В AWS Glue можно настроить запуск задания по расписанию (например, ежедневно в 2:00)
   - Или по событию (например, при появлении новых файлов в S3)

4. **Мониторинг**:
   - Используйте CloudWatch для мониторинга выполнения заданий
   - Настройте оповещения о сбоях

## Рекомендации для передачи справочников

1. **Инкрементальная загрузка**:
   - Реализуйте механизм определения измененных записей
   - Используйте временные метки или флаги изменений

2. **Валидация данных**:
   - Добавьте проверки качества данных в ETL-процесс
   - Настройте обработку ошибок

3. **Оптимизация**:
   - Для больших справочников используйте партиционирование
   - Рассмотрите использование колоночных форматов (Parquet, ORC)

4. **Безопасность**:
   - Шифруйте данные при передаче и хранении
   - Настройте соответствующие IAM-роли для доступа

Для конкретной настройки под вашу систему (ФВЫ - возможно, федеральную вычислительную систему) потребуется дополнительная информация о вашей инфраструктуре и требованиях.

## 3 варианта загрузки справочников БИК

### 1. Загрузка через Kafka (событийный подход)
**Описание**: 
- Источник публикует обновления справочника БИК в топик Kafka
- Наша система подписывается на топик и обновляет локальную копию

**Характеристики**:
- Размер справочника: БИК РФ содержит ~20к записей (~2-5 МБ в JSON)
- Передача данных: дельта (только изменения) или полный снэпшот при значительных обновлениях
- Частота: в реальном времени или пакетами (например, раз в час)

**Преимущества**:
- Минимальная задержка в получении обновлений
- Высокая отказоустойчивость (сообщения сохраняются в брокере)
- Масштабируемость

**Недостатки**:
- Сложнее в настройке и поддержке
- Требует инфраструктуры Kafka с обеих сторон

### 2. Доступ к нашей БД (интеграционный подход)
**Архитектура**:
1. Создаем выделенную схему/БД в нашем кластере (например, PostgreSQL или Oracle)
2. Настраиваем ограниченный доступ для системы-источника (только на запись в конкретные таблицы)
3. Источник выполняет UPSERT (вставка+обновление) по расписанию или при изменениях

**Варианты реализации**:
- **ETL-процесс**: источник запускает свой ETL (например, Informatica, Talend) для выгрузки в нашу БД
- **Прямая запись**: приложение источника подключается к нашей БД через JDBC/ODBC
- **API-прокси**: наш сервис принимает данные через REST и записывает в БД

**Характеристики**:
- Размер: можно передавать как дельту, так и полные снэпшоты
- Рекомендуется дельта (например, по полю `last_updated`)

**Преимущества**:
- Простота контроля данных (все в нашей БД)
- Легко делать сверки и аудит

**Недостатки**:
- Риски безопасности (доступ к нашей БД извне)
- Зависимость от доступности нашей БД

### 3. Загрузка файлами (традиционный подход)
**Варианты форматов**:
- CSV/JSON (полные или инкрементальные выгрузки)
- XML (например, стандартные банковские форматы)
- Пакетные файлы в S3/MinIO (например, ежедневные снэпшоты)

**Механизм**:
1. Источник выгружает файлы в согласованную файловую систему/SFTP/S3
2. Наша система забирает файлы по расписанию или через события (S3 Event Notification)
3. ETL-процесс (AWS Glue/Airflow) обрабатывает файлы и загружает в целевую БД

**Характеристики**:
- Размер: обычно полные снэпшоты (5-10 МБ), но можно и дельту
- Частота: от ежедневно до реального времени (микро-пакеты)

**Преимущества**:
- Простота реализации
- Отсутствие прямой связи систем
- Легко делать реплей обработки

**Недостатки**:
- Задержки в получении данных
- Нужно управлять файлами (архивация, версионирование)

## Рекомендации по выбору

1. **Для реального времени** → Kafka (если источник может публиковать в очередь)
2. **Для контролируемой среды** → Доступ к нашей БД (если есть доверие к источнику)
3. **Для простоты** → Файловый обмен (если допустимы задержки)

**Критические вопросы**:
1. Как источник определяет дельту? (по timestamp, версиям, флагам)
2. Требования к RPO/RTO (допустимые потери данных и время восстановления)
3. Необходимость верификации данных перед загрузкой

Для 2-го варианта (доступ к БД) рекомендую архитектуру:
```
[Система-источник] → (JDBC/ODBC) → [Бастион/API Gateway] → [Выделенный PostgreSQL Schema]
                                                           → [Audit Table]
                                                           → [Notification Service (при изменениях)]
```

### **Предложения по интеграции справочников БИК**  

#### **1. Реализация через Kafka (событийная модель)**  
**Суть**: Источник публикует изменения справочника БИК в Kafka, наша система подписывается и обновляет данные в реальном времени.  
**Плюсы**:  
- Минимальная задержка (актуальные данные).  
- Надежность (сообщения сохраняются в брокере).  
**Минусы**:  
- Требуется поддержка Kafka у источника.  
- Сложнее в настройке.  
**Как передаем данные**: Дельта (изменения) или снэпшоты при крупных обновлениях.  

#### **2. Доступ к нашей БД (прямая загрузка)**  
**Суть**: Даем источнику доступ на запись в выделенную схему нашей БД (PostgreSQL/Oracle).  
**Архитектура**:  
- Источник делает **UPSERT** (вставка/обновление) по расписанию или при изменениях.  
- Возможен контроль через API-прокси (без прямого доступа к БД).  
**Плюсы**:  
- Простота контроля (все данные в нашей БД).  
- Легко проверять целостность.  
**Минусы**:  
- Риски безопасности (нужны строгие ограничения доступа).  
- Зависимость от нашей БД.  
**Как передаем данные**: Дельта (по `last_updated`) или полные снэпшоты.  

#### **3. Выгрузка файлами (S3/SFTP)**  
**Суть**: Источник выгружает файлы (CSV/JSON) в S3/SFTP, наша система забирает и обрабатывает их ETL (Glue/Airflow).  
**Плюсы**:  
- Простота реализации.  
- Нет прямой связи между системами.  
**Минусы**:  
- Задержка (не подходит для real-time).  
- Нужно управлять версиями файлов.  
**Как передаем данные**: Обычно полные снэпшоты (ежедневно), но можно и дельту.  

### **Рекомендация**  
- Если нужны **актуальные данные** → **Kafka**.  
- Если важна **простота и контроль** → **Доступ к нашей БД**.  
- Если источник не поддерживает API/очереди → **Файловая выгрузка**.  

**Уточняющие вопросы**:  
1. Как источник определяет изменения (дельта vs полная выгрузка)?  
2. Какие требования к задержке (real-time vs ежедневно)?  
3. Нужна ли верификация перед загрузкой?

## 🤖 **DeepSeek**

### **Процесс получения справочников участников перевода через REST API**  

#### **1. Инициализация подключения**  
- **Аутентификация**:  
  - Процессинговая система отправляет запрос с `client_id` и `client_secret` (или токеном) к API источника.  
  - Получает **access_token** для дальнейших запросов.  

#### **2. Запрос данных**  
- **Получение справочника**:  
  - Процессинг отправляет **GET-запрос** к эндпоинту (например, `/api/v1/banks`).  
  - Возможные параметры:  
    - `last_update` – если нужна только дельта (изменения после указанной даты).  
    - `limit/offset` – для постраничной загрузки.  

#### **3. Обработка ответа**  
- API возвращает данные в **JSON/XML** (например, список БИК, названий банков, статусов).  
- Пример ответа:  
  ```json
  {
    "banks": [
      {"bic": "044525999", "name": "Сбербанк", "status": "ACTIVE"},
      {"bic": "044525123", "name": "ВТБ", "status": "ACTIVE"}
    ]
  }
  ```

#### **4. Сохранение в процессинговой системе**  
- **Валидация**: Проверка на дубли, корректность форматов.  
- **Запись в БД**:  
  - Обновление существующих записей.  
  - Добавление новых (например, через `INSERT ON CONFLICT UPDATE` в PostgreSQL).  

#### **5. Периодичность обновления**  
- **По расписанию**: Например, раз в час/день.  
- **По вебхуку**: Если источник поддерживает уведомления (отправляет запрос при изменениях).  

#### **6. Обработка ошибок**  
- **Повторные запросы**: При статусах `5xx` или таймаутах.  
- **Логирование**: Фиксация ошибок для анализа.  

### **Схема процесса**  
```
[Процессинг] → (GET /api/v1/banks) → [Система-источник]  
                     ↑  
[Access Token]       ↓  
                     [JSON-ответ] → [Парсинг] → [Сохранение в БД]  
```

### **Плюсы подхода**  
- **Гибкость**: Можно запрашивать дельту или полные данные.  
- **Масштабируемость**: Подходит для больших справочников (если есть пагинация).  
- **Стандартизация**: REST API – распространенный формат.  

### **Что уточнить у источника**  
1. Лимиты запросов (rate limiting).  
2. Максимальный размер ответа (если справочник большой).  
3. Метод определения изменений (дата модификации, версия, вебхуки).
