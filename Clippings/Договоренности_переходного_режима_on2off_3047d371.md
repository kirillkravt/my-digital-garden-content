Для переходного режима on2off используется следующая логика обработки операций B2C и C2B:

Предусловие:
Core получил запрос на выполнение операции
Выполнил проверку режима = on2off 

Логика для B2C:
Установить таймер 20 сек
По таймеру отправить ответ в ТСП c ошибкой 500

и так далее до выявления в проверке Core факта смены режима от ABS (отдельное сообщение is_online или is_offline)
Если от ABS прише is_offline, то Core:
Начинает авторизовывать операции через BO
Если пришел is_online, то авторизация через ABS

Логика для С2B аналогичная

### Договоренности по реализации переходного режима (On2Off)

#### 1. Общие положения
В переходном режиме `on2off` Core выступает в роли буфера, управляя очередностью запросов от внешних систем (ТСП, Шлюз СБП) до момента фиксации актуального статуса от ABS.

#### 2. Логика обработки операций B2C (ТСП -> Core -> ABS)

1.  **Инициация:** При получении запроса от ТСП в режиме `on2off`, Core не отправляет его в ABS, а ставит в ожидание.
2.  **Таймаут и ответ:** Core устанавливает таймер на **20 секунд**.
    *   По истечении 20 секунд Core **обязан** вернуть ТСП HTTP-ответ с кодом ошибки **500**.
3.  **Повторный запрос:** ТСП, получив ошибку 500, **обязуется** повторить запрос (механизм retry).
4.  **Цикл:** Core повторяет шаги 1-3 для каждого нового запроса от ТСП, продолжая удерживать операцию.
5.  **Условие выхода (смена статуса):**
    *   Цикл повторяется до тех пор, пока Core не получит от ABS явное указание о смене режима (событие `is_online` или `is_offline`).
    *   **Если получен статус `is_offline`:** Core с этого момента начинает авторизовывать (маршрутизировать) все новые операции напрямую в **BO**, минуя ABS.
    *   **Если получен статус `is_online`:** Core с этого момента начинает авторизовывать все новые операции напрямую в **ABS**.

#### 3. Логика обработки операций C2B (Шлюз СБП -> Core -> ABS)

1.  **Применимость:** Логика полностью аналогична логике для B2C.
2.  **Ключевое отличие:**
    *   Ответ с ошибкой **500** Core направляет не в ТСП, а в **Шлюз СБП** (который также реализует механизм повторных запросов).
3.  **Условия выхода (смена статуса):** Аналогичны пункту 5 блока B2C. После получения статуса `is_offline` авторизация операций C2B также переводится на **BO**, после `is_online` — на **ABS**.

**2. Обработка B2C (ТСП)**

1.  Core ставит запрос на таймер 20 сек.
2.  По таймеру -> ответ в ТСП 500.

6.  Получен is_offline -> новые операции авторизуем через BO.
7.  Получен is_online -> новые операции авторизуем через ABS.

**3. Обработка C2B (Шлюз СБП)**

Логика полностью аналогична B2C.

**Отличие:** ответ 500 уходит не в ТСП, а в Шлюз СБП. Шлюз СБП делает повторный запрос.

**Решение по доработкам Core (C2B):**

1.  **Триггер:** Core получил команду на смену режима в переходный (on2off).

2.  **Маршрутизация:**
    *   Все последующие запросы C2B Core направляет на обработку в **BO**.

3.  **Двойной удар (Double-flow):**
    *   BO выполняет свои процессы.
    *   Параллельно Core отправляет операцию в **ABS** для выполнения проводки.
    *   Важно: запрос в ABS идет с заполненным полем **48 (Тип операции C2B)**.

4.  **Значение поля 48:**
    *   Если режим **переходный (on2off)** -> передаем значение `C2BQRD_OFLN`.
    *   Если режим **онлайн (online)** -> передаем значение `C2BQRD_ACCP`.

### Функциональное требование: Обработка C2B в переходном режиме (on2off)

**Модуль:** Core (обработка входящих запросов C2B)

**Описание изменения:**
Изменить логику маршрутизации и формирования запросов в ABS при получении команд смены режима.

**Детали реализации:**

1.  **Условие срабатывания:**
    *   Core получил команду на смену режима работы в **переходный (on2off)**.

2.  **Маршрутизация запросов C2B:**
    *   Начиная с момента перехода в режим `on2off`, все **новые** входящие запросы C2B должны направляться на обработку в **BO** (бэк-офис).

3.  **Двойная отправка в ABS:**
    *   Помимо отправки запроса в BO, Core **обязательно** дублирует операцию в **ABS** для выполнения проводки.
    *   Соединение с ABS и таймауты должны обрабатываться согласно стандартным настройкам Core (не блокируя основной поток ответа в Шлюз СБП).

4.  **Формирование поля 48 (Тип операции):**
    *   При отправке запроса в ABS значение поля **48** должно динамически определяться в зависимости от **текущего режима работы** Core на момент обработки операции:

| Режим Core | Значение поля 48 |
|---|---|
| Онлайн (online) | `C2BQRD` |
| Переходный (on2off) | `C2BQRD_OFLN` |

5.  **Важно:**
    *   При возврате Core в режим **online** значение поля 48 должно снова стать `C2BQRD` (без суффикса).
    *   Ответ об успешности/ошибке проводки в ABS **не влияет** на ответ, который Core возвращает в Шлюз СБП (ответ формируется по результатам обработки в BO).

### Функциональное требование: Обработка B2C в переходном режиме (on2off) — Исходный вариант

**Модуль:** Core (обработка входящих запросов B2C от ТСП)

**Описание изменения:**
Реализовать логику "удержания" операций B2C на Core при получении команды перехода в режим on2off до момента фиксации актуального статуса от ABS.

**Детали реализации:**

1.  **Условие срабатывания:**
    *   Core получил команду на смену режима работы в **переходный (on2off)**.
    *   Core получил входящий запрос B2C от ТСП.

2.  **Логика обработки запроса (Циклический таймаут):**

    *   **Шаг 1. Таймер:** Core не отправляет запрос в ABS, а устанавливает таймер ожидания на **20 секунд**.
    *   **Шаг 2. Ответ в ТСП:** По истечении 20 секунд Core **немедленно** возвращает в ТСП HTTP-ответ с кодом ошибки **500 Internal Server Error**.
    *   **Шаг 3. Ожидание ретрая:** Core переходит в режим ожидания повторного запроса от ТСП по данной операции.
    *   **Шаг 4. Повтор:** При получении повторного запроса от ТСП Core повторяет **Шаг 1** (вновь ставит операцию на таймер 20 сек).
    *   **Шаг 5. Цикл:** Шаги 1-4 повторяются циклически для каждого нового/повторного запроса от ТСП.

3.  **Условие выхода из цикла (смена режима):**

    *   Core продолжает описанный цикл до тех пор, пока от ABS не поступит явное событие об изменении статуса (`is_online` или `is_offline`).
    *   Цикл применяется **только** к операциям, поступившим в моменте, пока Core еще не знает актуальный статус.

4.  **Действия после получения статуса от ABS:**

    *   **Если получен статус `is_offline`:**
        *   Начиная с этого момента все **новые** входящие запросы B2C Core направляет на авторизацию напрямую в **BO**.
    *   **Если получен статус `is_online`:**
        *   Начиная с этого момента все **новые** входящие запросы B2C Core направляет на авторизацию напрямую в **ABS**.
    *   Важно: операции, которые в данный момент находятся в цикле (ждут на таймере), должны быть обработаны согласно новому статусу при получении их повторного запроса.

5.  **Требования к ТСП (подтверждение):**
    *   ТСП обязуется реализовать логику автоматического повторного запроса (retry) при получении ошибки 500 от Core.
