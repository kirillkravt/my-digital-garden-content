**3. Требования к отчету Cash_bal1**

**3.1. Назначение:**  
Общий балансовый отчет по устройствам без разбивки по кассетам.

**3.2. Требуемые изменения:**

1. **Добавить колонку:** Тип устройства (TSO / Combi / Recycle / CashOut).  
2. **Добавить колонку:** Дата и время крайней инкассации (в формате "дд.мм.гггг чч:мм:сс").  
3. **Добавить возможность сортировки** по типам устройств (4 типа).  
4. **Добавить возможность фильтрации** по региональному признаку УС.

**3.3. Формат выгрузки:**  
Excel-файл, содержащий колонки:

- Терминал ID
- Адрес
- Тип устройства
- Количество купюр
- Сумма денежных средств
- Дата, время формирования отчета
- Дата крайней инкассации
- Регион (опционально, если требуется)

---

**4. Требования к отчету Cash_bal2**

**4.1. Назначение:**  
Балансовый отчет по устройствам с разбивкой по кассетам.

**4.2. Требуемые изменения:**

1. **Добавить колонку:** Тип устройства (TSO / Combi / Recycle / CashOut).  
2. **Добавить колонку:** Дата и время крайней инкассации (в формате "дд.мм.гггг чч:мм:сс").  
3. **Добавить информацию по кассетам выдачи:** количество загруженных купюр и сумма при инкассации.  
4. **Добавить данные по депозитным (Cash In) кассетам с разбивкой по номиналам:**  
   - Количество купюр каждого номинала  
   - Сумма по каждому номиналу  
5. **Добавить данные по Reject-кассетам:**  
   - Общее количество листов  
   - Общая сумма в кассете  
6. **Добавить возможность сортировки** по типам устройств.  
7. **Добавить возможность фильтрации** по региональному признаку УС.

**4.3. Формат выгрузки:**  
Excel-файл с детализацией по кассетам, включая:

- Терминал ID
- Адрес
- Тип устройства
- Номер кассеты
- Тип кассеты (выдача, депозит, реджект)
- Номинал (для депозитных кассет)
- Количество купюр
- Сумма
- Дата, время формирования отчета
- Дата крайней инкассации
- Регион (опционально)

---

**5. Уточнения для реализации**

- **Региональный признак:** должен быть включен в оба отчета во избежание ручного поиска устройств среди 1400+ УС.  
- **Депозитные кассеты:** данные выводятся суммарно, если нет возможности разбивки по номиналам (уточнить у разработки).  
- **Дата инкассации:** используется дата открытия цикла инкассации.  

---

**6. Ограничения**

- Отчеты должны работать для всех типов УС (АТМ, ТСО, Ресайклер и т.д.).  
- Данные по депозитным кассетам могут быть доступны только для закрытых циклов (требуется уточнение).  
- В случае технических ограничений по выводу депозитных данных в реальном времени — использовать модель отчетов Jasper Reports (по закрытым циклам).  

---

**7. Технические рекомендации**

- Использовать LUNO для определения типа устройства и региональной принадлежности.  
- При отсутствии данных по депозитным кассетам в открытых циклах — перевести отчет Cash_bal2 на данные закрытых циклов.  
- Обеспечить возможность экспорта в Excel с настраиваемыми периодами.

# Требования к доработке модуля шифрования (Encryptor)

**Дата составления:** 13.01.2026  
**Документ:** Постановка_Encryptor_Требования_v1.0  
**Автор:** [Имя аналитика]  

---

## 1. Краткое описание задачи
Доработка системы мониторинга и управления банкоматами для корректного выявления и обработки ситуаций, связанных с проблемами ключей шифрования (MAC, TMK, сессионные ключи).

---

## 2. Действующие лица
- **Исполнитель:** А Н, Е С, Ш Н  
- **Заказчик:** М Банк (И М, А З)  

---

## 3. Извлечённые требования от Заказчика

### 3.1. Основные сценарии обработки ошибок ключей:

#### **Сценарий 1: Неуспешная проверка MAC на статусных сообщениях (Solicited Status Messages)**
- **Триггер:** Получение статусного сообщения от банкомата с некорректным MAC.
- **Действие системы:**
  1. Выставить ошибку/предупреждение **Encryptor** по устройству.
  2. Отправить команду закрытия (OOS) на банкомат.

#### **Сценарий 2: Неуспешная смена сеансовых ключей по команде из гибких сценариев**
- **Триггер:** Неудачная попытка смены ключей (DEV, MAC, TMK) в статусе OOS.
- **Действие системы:**
  1. Выставить ошибку/предупреждение **Encryptor** по устройству.
  2. Запретить автоматическое открытие банкомата (флаг запрета в InService).

#### **Сценарий 3: Несколько неудачных проверок MAC на финансовых запросах**
- **Триггер:** Серия неудачных проверок MAC (пороговое значение настраиваемо).
- **Действие системы:**
  1. Выставить ошибку/предупреждение **Encryptor**.
  2. Отправить команду закрытия (OOS) на банкомат.

---

### 3.2. Уточнения и уступки (согласовано с Заказчиком):

1. **Автоматическая смена MAC-ключа при ошибке** — **НЕ требуется**.
2. **Количество попыток перед закрытием:** 2 попытки (первая + контрольная).
3. **Ошибка должна учитываться в обоих случаях:**
   - MAC не прошёл проверку на хосте.
   - Банкомат прислал реджект о неуспешной проверке MAC.

---

### 3.3. Требования к мониторингу и интерфейсу:

1. **Статус ошибки:** Должен выставляться признак/ошибка **Encryptor**.
2. **Фильтр в GUI:** Устройства с проблемой ключей должны попадать в существующий фильтр **“Модуль шифрования”** (или аналогичный).
3. **Визуализация:** Статус должен отображаться:
   - На главном экране мониторинга в детализации ошибок/предупреждений.
   - На вкладке “Основные” в состоянии устройств.

---

## 4. Технические уточнения для Исполнителя

### 4.1. Что должно быть реализовано:

| №  | Компонент                         | Описание                                                                 |
|----|-----------------------------------|--------------------------------------------------------------------------|
| 1  | Проверка MAC на статусных сообщениях | Для всех сообщений пуллинга (Solicited Status Messages).                 |
| 2  | Счётчик неудачных проверок MAC    | Настраиваемое количество попыток (по умолчанию: 2).                      |
| 3  | Команда закрытия банкомата        | Отправка команды OOS при превышении порога ошибок.                       |
| 4  | Флаг запрета открытия             | Установка флага при неудачной смене ключей в OOS.                        |
| 5  | Выставление статуса Encryptor     | Единый статус для всех сценариев проблем с ключами.                      |
| 6  | Интеграция с фильтром GUI         | Включение в фильтр “Модуль шифрования”.                                  |

### 4.2. Что НЕ требуется:
- Автоматическая смена MAC-ключей при ошибке.
- Отдельная логика для TMK vs. сессионных ключей (общий статус Encryptor).

---

## 5. Ограничения и допущения

1. **Тестирование:** Из-за сложности тестирования на реальных устройствах возможны корректировки по ходу реализации.
2. **Обратная совместимость:** Изменения не должны ломать существующие сценарии работы с ключами.
3. **Производительность:** Добавление проверок не должно существенно влиять на производительность системы.

---

## 6. Выходные артефакты

2. Механизм подсчёта и реакции на ошибки MAC.
3. Новый/обновлённый статус Encryptor в БД и GUI.
4. Обновлённая документация (при необходимости).

## 🤖 **DeepSeek**

Как опытный бизнес-аналитик, я оцениваю этот документ **как хорошую основу, но недостаточно полную и чёткую для передачи в разработку без дополнительных уточнений.**

Документ хорошо структурирует историю обсуждений, но **не формализует требования в виде однозначных, тестируемых условий.**

Вот чего критически не хватает:

### 1. Отсутствуют нефункциональные требования (NFR):
*   **Производительность:** Насколько быстро система должна реагировать на ошибку MAC? (Например: "Команда закрытия (OOS) должна быть отправлена на устройство в течение 3 секунд после фиксации критического количества ошибок").
*   **Надёжность:** Где и как хранить счётчик неудачных попыток? Что происходит при перезапуске сервиса? Счётчик должен быть устойчив к рестартам.
*   **Настраиваемость:** Конкретный путь или параметр в БД для порогового значения (п.2 в 4.1). Например: `atm.encryptor.mac_failure_threshold`. Нужно ли настраивать это значение индивидуально для устройств или глобально?

### 2. Нет чётких критериев завершения (Definition of Done) и тест-кейсов:
*   **DoD:** Как разработчик поймёт, что задача выполнена?
    *   Код написан, прошел ревью и мерджен в ветку разработки?
    *   **Протестировано на стенде?** Каким именно образом? (Это главный вопрос, так как в логах упоминается сложность тестирования на реальных устройствах).
    *   Документация (например, Swagger/комментарии к API) обновлена?
*   **Тестовые сценарии:** Их нужно описать в виде таблицы. Например:

| №  | Действие (Стимул)                                    | Ожидаемый результат (Реакция системы)                                                                                       | Критерий успеха                                                                               |
|----|-------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| T1 | На пуллинг-сообщение приходит некорректный MAC (1 раз) | Статус Encryptor **НЕ** выставляется. Банкомат остается в работе.                                                          | В логах видна ошибка MAC, но команда OOS не отправлена.                                      |
| T2 | На пуллинг-сообщение приходит некорректный MAC **2 раза подряд** (порог=2) | 1. Статус `encryptor_error` выставляется в БД для PID. <br> 2. В GUI устройство попадает в фильтр "Модуль шифрования". <br> 3. На устройство отправлена команда OOS. | В БД присутствует запись об ошибке. В логах видна отправка команды `SetOOS`. GUI отображает устройство в фильтре. |
| T3 | Из гибкого сценария приходит команда на смену ключей, которая завершается ошибкой | 1. Статус `encryptor_error` выставляется. <br> 2. Выставляется флаг `open_prohibited = true`. <br> 3. Автоматические команды на открытие (InService) игнорируются. | Флаг запрета открытия проверяется при попытке перевода в InService.                          |

### 3. Не хватает деталей по интеграции и данным:
*   **Структура статуса "Encryptor":** Какой именно атрибут/поле/флаг в БД будет изменяться? Нужно ли новое поле или использовать существующее (например, `device_state`)? Какое значение он будет принимать (например, `KEY_ERROR`)?
*   **Механизм "флага запрета открытия":** Это поле в таблице устройств? Или логика строится на наличии статуса `encryptor_error`? Нужно явно описать.
*   **Логирование:** Требуется ли записывать каждую неудачную проверку MAC в отдельный лог для аудита? Указать уровень логирования (INFO, WARN, ERROR).

### 4. Открытые вопросы для Заказчика (уточнить до передачи в работу):
*   **Сценарий восстановления:** Как оператор должен исправить ситуацию? Через интерфейс мониторинга должна быть доступна **ручная команда "Повторить обмен ключами"** или "Сбросить статус ошибки Encryptor"?
*   **Уведомления:** Нужно ли интегрировать новый статус в систему алертинга (например, отправка уведомления в чат-бот оперблока при срабатывании)?
*   **Историчность:** Нужно ли хранить историю выставления/снятия статуса `encryptor_error` для отчётности?
