### **Сводка по задаче (Executive Summary)**

**Задача:** Модификация Back-Office и Web-интерфейса (SVWI) для отображения операций, проведенных без авторизации через UPI (прямое подключение к платежным системам).

**Ключевые изменения:**
1.  **Back-End:** Изменение источника данных в процедуре `api_web_gate.get_auth_hold_status` с таблицы `sv_fin_tab` на `upi_fin_tab`.
2.  **Front-End (SVWI):** Расширение функционала раздела "Холдирование" для отображения операций без авторизации с цветовой индикацией и корректным заполнением полей.

**Бизнес-цель:** Предоставить операторам полную видимость всех транзакций, включая те, что прошли в обход стандартного процесса авторизации через Front-end, для улучшения обслуживания клиентов и мониторинга.

---

### **1. Требования к Back-Office (База данных, API)**

#### **1.1. Изменение источника данных**
*   **Требование:** Процедура `api_web_gate.get_auth_hold_status` должна быть модифицирована для работы с новой таблицей `upi_fin_tab`.
*   **Обоснование:** Источник данных для операций без авторизации был изменен на системном уровне.
*   **Критерий приемки:** Запросы из SVWI на получение статуса холдирования корректно обращаются к `upi_fin_tab` и возвращают данные в ожидаемом формате.

#### **1.2. Логика выборки операций без авторизации**
*   **Требование:** При выборке данных необходимо фильтровать записи, где поле `fe_utrnno` равно `NULL`.
*   **Обоснование:** Это индикатор того, что операция прошла без участия Front-end.
*   **Детализация по МПС:**
    *   **VISA/BЕЛКАРТ:** `Visa_draft_tab.fe_utrnno IS NULL`
    *   **MasterCard:** `mc_fin_tab.fe_utrnno IS NULL`
*   **Дополнительный фильтр:** Выбирать данные только по собственным картам банка.
*   **Критерий приемки:** В результирующую выборку попадают только транзакции, удовлетворяющие условиям выше.

#### **1.3. Обеспечение целостности данных**
*   **Требование:** Необходимо обеспечить корректное соединение (JOIN) таблиц `upi_fin_tab`, `Visa_fin_tab`, `Visa_draft_tab` и `mc_fin_tab` для получения полного набора данных по всем МПС.
*   **Критерий приемки:** Данные по всем типам карт (VISA, БЕЛКАРТ, MasterCard) отображаются корректно и без дублирования.

### **2. Требования к Web-интерфейсу (SVWI)**

#### **2.1. Местоположение и доступ**
*   **Требование:** Отображение операций без авторизации должно быть реализовано в существующем разделе Web-интерфейса: **"Процессинговая система -> Обслуживание клиентов -> Холдирование"**.
*   **Критерий приемки:** Новые данные интегрированы в существующую таблицу на указанной странице.

#### **2.2. Цветовая индикация (UI-требование)**
*   **Требование:** Реализовать цветовую индикацию строк таблицы в зависимости от статуса операции без авторизации.
*   **Спецификация цветов:**

    *   **Серый цвет строки:** Статус операции = `"OFF-Line Not_proc"`.
*   **Критерий приемки:** Операции без авторизации визуально отличаются по цвету от обычных операций, цвета соответствуют спецификации.

1.  **Производительность:** Изменения не должны привести к значительной деградации производительности раздела "Холдирование". Время отклика должно остаться в пределах текущих SLA.
2.  **Безопасность:** Изменения не должны расширять круг лиц, имеющих доступ к данным. Доступ к операциям без авторизации должны иметь те же роли, что и доступ к обычным операциям в данном разделе.
3.  **Совместимость:** Изменения в API (`get_auth_hold_status`) должны быть обратно совместимыми, чтобы не сломать существующих клиентов, которые могут использовать этот метод.

### **Пакет требований: Отображение операций без авторизации**

**1. Цель (Goal)**

**Повышение эффективности сервисного обслуживания клиентов и полноты финансового мониторинга за счет обеспечения полной видимости всех типов транзакций в системе холдирования.**

*   **Проблема:** В текущий момент операторы и специалисты службы поддержки в Web-интерфейсе (SVWI) не видят операции, проведенные через прямое подключение к платежным системам (UPI) без авторизации через стандартный Front-end. Это создает «слепую зону»:
    *   Клиенты могут обращаться по операциям, которые оператор не может найти в системе.
    *   Невозможно провести полный мониторинг и анализ всех финансовых потоков.
    *   Возрастает время на обработку запросов и риск ошибок.

*   **Решение:** Интегрировать данные об операциях без авторизации из нового источника (`upi_fin_tab`) в существующий интерфейс раздела «Холдирование».

*   **Ожидаемый результат:** Операторы получают единую, полную картину по всем операциям (как с авторизацией, так и без), что позволяет оперативно и точно обрабатывать запросы клиентов, проводить расследования и управлять рисками.

---

**2. Бизнес-требование (Business Requirement)**

**BR-001: Обеспечение отображения операций, инициированных без авторизации через Front-end, в разделе «Холдирование» Web-интерфейса (SVWI) для их полного контроля и обслуживания.**

**Описание:** Бизнес-процесс обслуживания клиентов и мониторинга транзакций требует, чтобы в интерфейсе оператора отображались **все** операции, вне зависимости от способа их проведения (через стандартную авторизацию или прямое подключение UPI). Отсутствие данных об операциях без авторизации приводит к неполному обслуживанию, ошибкам и неудовлетворенности клиентов.

**Обоснование:** Для выполнения обязательств перед клиентами и обеспечения качества сервиса банк должен иметь возможность видеть и обрабатывать 100% транзакций по картам. Данное требование направлено на устранение существующего разрыва в данных.

**Критерии успеха:**
*   **Качественные:**
    *   Сокращение количества обращений клиентов, которые оператор не может идентифицировать в системе.
    *   Повышение скорости и точности обработки запросов, связанных с операциями без авторизации.
    *   Устранение «слепой зоны» в мониторинге операций для снижения финансовых и операционных рисков.
*   **Количественные (если применимо и измеримо):**
    *   Снижение времени на обработку одного запроса, связанного с поиском транзакции, на X%.
    *   Доведение процента успешного поиска операций по обращениям клиентов до 100%.

**Связанные заинтересованные стороны:**

*   **Пользователи:** Операторы контакт-центра, специалисты по мониторингу и расследованию инцидентов.

## 🤖 **DeepSeek**

Отличный и очень важный технический вопрос. Необходимость `JOIN` таблиц продиктована **архитектурой данных в Back-Office** и стремлением к **полноте и точности информации**.

Вот ключевые причины, почему без `JOIN` не обойтись:

### 1. Разделение данных по МПС (Платежным системам)

База данных спроектирована таким образом, что транзакции по разным платежным системам хранятся в **разных физических таблицах**. Это стандартный подход для изоляции данных и упрощения управления.

*   **`mc_fin_tab`** — для операций по картам **Mastercard**.
*   **`visa_fin_tab`** и **`visa_draft_tab`** — для операций по картам **VISA** и **БЕЛКАРТ**.

Новая таблица **`upi_fin_tab`**, скорее всего, является **общей служебной таблицей** или таблицей-агрегатором, которая содержит ссылки на транзакции во всех этих специализированных таблицах, но не обязательно содержит все их детали.

**Задача:** Показать в интерфейсе единый список операций, собранный из этих разных источников.

**Решение:** `JOIN` между `upi_fin_tab` и специализированными таблицами (`mc_fin_tab`, `visa_fin_tab` и т.д.) по ключевым полям (например, `utrnno`).

---

### 2. Неполнота данных в одной таблице

Представьте, что `upi_fin_tab` хранит только общую информацию о транзакции (например, сумму, дату, статус, ссылку на исходную запись), но **не хранит специфичные для МПС данные**.

*   Поле **`Тип терминала`** (`P0023`) находится *только* в таблице `mc_fin_tab`.
*   Какие-то специфичные поля для VISA (например, определенные коды ответов) могут находиться *только* в `visa_fin_tab`.

**Задача:** Заполнить в интерфейсе все 19 полей, включая те, которых нет в `upi_fin_tab`.

**Решение:** Чтобы получить поле `P0023` для операции MasterCard, необходимо присоединить (`JOIN`) таблицу `mc_fin_tab` к `upi_fin_tab` по общему ключу (например, `utrnno` или `internal_id`). Аналогично для данных VISA.

---

### 3. Определение типа карты

В техническом задании указано: "Берутся данные только по собственным картам банка". Но также нужно отобразить в колонке **"Тип"**, с картой какой платежной системы была совершена операция (VISA, MC, БЕЛКАРТ).

Сама по себе таблица `upi_fin_tab` может и не содержать явного поля `card_type`. Этот признак может определяться тем, в какой именно из таблиц (`mc_fin_tab`, `visa_fin_tab`) найдена соответствующая детальная запись.

**Задача:** Определить и отобразить тип карты.

**Решение:** Использовать `OUTER JOIN` ко всем таблицам МПС и анализ того, какая из присоединенных таблиц вернула не `NULL` значение.
*   Если `mc_fin_tab.utrnno IS NOT NULL` -> Тип = 'MasterCard'
*   Если `visa_fin_tab.utrnno IS NOT NULL` -> Тип = 'VISA'

---

### Как это может выглядеть в коде (упрощенно):

```sql
SELECT
    -- Общие поля из upi_fin_tab
    u.utrnno AS UTRN,
    u.trndate AS "Выполнено",
    u.amount AS "Сумма операции",
    
    -- Поле, специфичное для MasterCard, из mc_fin_tab
    m.p0023 AS terminal_code,
    
    -- Определение типа карты на основе того, из какой таблицы пришли данные
    CASE
        WHEN m.utrnno IS NOT NULL THEN 'MasterCard'
        WHEN v.utrnno IS NOT NULL THEN 'VISA'
        ELSE 'Unknown'
    END AS "Тип"
    
FROM upi_fin_tab u

-- LEFT JOIN означает: "возьми все записи из основной таблицы 'u', 
-- и если есть соответствие в таблице 'm', то подставь данные оттуда. 
-- Если нет - верни NULL для полей таблицы 'm'".
LEFT JOIN mc_fin_tab m ON u.utrnno = m.utrnno AND m.fe_utrnno IS NULL
LEFT JOIN visa_fin_tab v ON u.utrnno = v.utrnno AND v.fe_utrnno IS NULL

WHERE u.fe_utrnno IS NULL -- Основной критерий: операция без авторизации
```

### Резюме для команды разработки:

**`JOIN` таблиц необходим, потому что:**
1.  **Данные физически разнесены** по разным таблицам в зависимости от МПС.
2.  **`upi_fin_tab` likely acts as a metadata table** и не содержит всех необходимых для отображения деталей.
3.  **Цель — создать единое представление** (VIEW) из этих распределенных данных для конечного пользователя (оператора в SVWI).
4.  **Без `JOIN` мы получим неполные или некорректные данные**, что сделает фичу бесполезной.

---
