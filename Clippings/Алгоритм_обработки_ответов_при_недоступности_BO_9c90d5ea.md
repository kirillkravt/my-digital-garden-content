# Алгоритм обработки ответов при недоступности BO

## 👤 **Kirill**

Есть схема взаимодействия Core и BO при B2C/C2B переводах. Core - процессинг платежей выполняет авторизацию. BO - бэкофис, учитывает операции, которые послужат основанием для сверки с АБС. Ответ Core должен отправлять клиенту ТСП. Как бизнес-аналитик опиши алгоритм по предоставлению ответов клиенту если BO не доступен (сетевая недоступность). Что должен сделать процессинг чтобы обеспечить корректное информирование всех участников и т.д.

---

## 🤖 **DeepSeek**

### **Алгоритм обработки ответов клиенту при недоступности BO в B2C/C2B переводах**  

#### **1. Определение проблемы**  
При выполнении перевода:  
- **Core (процессинг)** успешно авторизует платеж.  
- **BO (бэк-офис)** недоступен (сетевая ошибка, таймаут и т. д.), поэтому не может учесть операцию для сверки с АБС.  

Необходимо обеспечить:  
✅ Корректный ответ клиенту (ТСП)  
✅ Учет операции в Core, даже если BO временно не работает  
✅ Последующую синхронизацию данных с BO  

---  

#### **2. Алгоритм действий процессинга (Core)**  

| **Шаг** | **Действие** | **Описание** |  
|---------|-------------|-------------|  
| **1** | Проверить доступность BO | Если BO не отвечает (таймаут, 5xx ошибка), перейти в режим "деградации". |  
| **2** | Зафиксировать операцию в Core | Платеж сохраняется в **локальном журнале Core** с меткой **"BO недоступен"**. |  
| **3** | Отправить клиенту (ТСП) успешный ответ | Клиент получает **успешный статус** (например, `200 OK`), так как авторизация прошла. **Важно:** клиент не должен знать о проблемах BO. |  
| **4** | Поставить операцию в очередь на повторную отправку | Запустить механизм **ретраев** (например, экспоненциальные задержки: 1 сек, 5 сек, 30 сек, 5 мин). |  
| **5** | При восстановлении BO отправить данные | Как только BO доступен, Core отправляет накопленные операции. |  
| **6** | Логировать ошибки, если BO долго недоступен | Если BO не работает > N минут (например, 30 мин), уведомить поддержку. |  

---  

#### **3. Дополнительные механизмы обеспечения надежности**  

🔹 **Ретраи с экспоненциальной задержкой** – избегаем лавинообразного роста запросов.  
🔹 **Фоллбек-хранилище** – если очередь переполнена, записывать операции в резервное хранилище (например, Kafka, файловый лог).  
🔹 **Мониторинг и алерты** – при длительном простое BO (например, > 10 мин) уведомлять DevOps.  
🔹 **Компенсационные транзакции** – если BO так и не принял операцию, Core должен уметь откатывать платеж (если это допустимо бизнес-логикой).  

---  

#### **4. Варианты ответов клиенту**  

| **Сценарий** | **Ответ Core клиенту** | **Дальнейшие действия** |  
|-------------|----------------------|-----------------------|  
| BO доступен | `200 OK` (успех) | BO учитывает операцию. |  
| BO недоступен | `200 OK` (успех) | Core сохраняет операцию локально, ретраит позже. |  
| Ошибка авторизации (недостаточно средств и т. д.) | `4xx/5xx` (ошибка) | Клиент получает ошибку, операция не проводится. |  

---  

#### **5. Восстановление после сбоя**  

Когда BO снова доступен:  
1. Core отправляет накопленные операции.  
2. BO проверяет дубли (идемпотентность по `operation_id`).  
3. Если операция уже учтена – игнорировать.  
4. Если нет – принять и синхронизировать с АБС.  

---  

### **Итог**  
✅ Клиент всегда получает **четкий ответ** (успех/ошибка) без зависимости от BO.  
✅ Операции не теряются, даже если BO временно недоступен.  
✅ После восстановления BO данные синхронизируются.  
✅ Система устойчива к сбоям.  

Этот подход соответствует **принципам отказоустойчивости** и **согласованности данных** в распределенных системах.

### **Механизм ручного дозапроса callback’ов**  

Если система отправителя использует **fire-and-forget**, но нам важно гарантированно получить все callback’и, можно реализовать **ручной дозапрос**. Вот как это может работать:  

---

### **1. API для дозапроса (Pull-модель)**  
**Вариант 1: Запрос по ID операции**  
- **Эндпоинт**: `GET /api/callbacks/{operation_id}`  
- **Логика**:  
  - Если callback не пришёл, наша система делает запрос с `operation_id`.  
  - Сервер возвращает последний статус (если callback уже был отправлен) или ошибку `404 Not Found` (если его нет).  

**Вариант 2: Список недопоставленных callback’ов**  
- **Эндпоинт**: `GET /api/callbacks/failed?date=YYYY-MM-DD`  
- **Логика**:  
  - Запрашиваем все callback’и, которые не получили подтверждения (`ACK`) за указанную дату.  
  - Сервер возвращает массив `{operation_id, status, timestamp}`.  

---

### **2. Веб-интерфейс для ручной выгрузки**  
- **Где**: Админка или бэк-офис система отправителя.  
- **Что можно сделать**:  
  - Фильтр по дате/статусу.  
  - Выгрузка в `CSV/JSON` для анализа.  
  - Возможность переотправить выбранные callback’и кнопкой.  

---

### **3. Условия работы механизма**  
- **Хранение истории**:  
  - Отправитель должен хранить callback’и **минимум N дней** (например, 7–30).  
  - Желательно — с меткой `delivered: true/false`.  
- **Идемпотентность**:  
  - Если callback переотправлен, наша система должна корректно обработать дубль (например, по `operation_id`).  

---

### **4. Альтернативы, если API для дозапроса нет**  
- **Периодическая синхронизация**:  
  - Раз в час/день запрашиваем **все свежие операции** через отдельное API.  
- **Резервный канал доставки**:  
  - Например, дублирование в **S3-хранилище** или **email с JSON-вложением**.
