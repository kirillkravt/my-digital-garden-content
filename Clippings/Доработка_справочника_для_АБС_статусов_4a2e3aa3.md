## 🤖 **DeepSeek**

**Пагинация** — это способ организации контента (текста, данных, элементов интерфейса) по отдельным страницам (или блокам) с целью удобного отображения и навигации.  

### **Где применяется?**  
1. **Веб-сайты и приложения**  
   - Разбивка длинных статей, товаров в интернет-магазинах или списков пользователей на страницы (например, «1 2 3 … 10» внизу экрана).  
   - Пример: Google выдает результаты поиска постранично.  

2. **Базы данных и программирование**  
   - При запросах к БД пагинация позволяет загружать данные частями (например, «Показать 10 записей из 100»).  
   - SQL-пример: `LIMIT 10 OFFSET 20` (пропустить 20 записей, вывести следующие 10).  

3. **Документы и книги**  
   - Нумерация страниц в PDF, Word или печатных изданиях.  

### **Зачем нужна?**  
- Уменьшает нагрузку на систему (не загружать все данные сразу).  
- Улучшает UX: пользователь не теряется в огромном списке.  
- Позволяет быстро переходить к нужному блоку информации.  

**Синонимы:** постраничная навигация, разбиение на страницы.

**Требования к доработкам (раздел 2.2 документа)**  

### **1. Интеграция с существующими системами**  
**Цель:** Обеспечить передачу данных из внешних систем для контроля мошеннических операций по заданным правилам.  

**Ключевые задачи:**  
- **Настройка интерфейсов** для подключения новых источников данных (например, СДБО, АБС, платежные шлюзы).  
- **Форматы данных:** Поддержка JSON для REST API и RabbitMQ (очереди `OPERATIONS_SV_QUEUE`).  
- **Параметры передачи:**  
  - Обязательные поля: `ucid`, `accountNumber`, `operationType`, `amount`, `timestamp`, `payer`, `recipient`.  
  - Опциональные: `mccCode`, `locationName`, `cardTail` (для карточных операций).  
- **Идентификация транзакций:**  
  - Единый `guid` для сопоставления запроса и ответа.  
  - Тип сообщения `1120` (Authorization Advice) для запросов, `1130` (Authorization Advice Response) для ответов.  

**Требования к реакциям (дополнение к 2.3):**  
- **Гибкость правил:**  
  - Возможность настройки блокирующих/неблокирующих сценариев (например, только уведомление без алерта).  
- **Действия при срабатывании:**  
  - Приостановка операции (код `SUSPEND`).  
  - Уведомление внешних систем (коды `APPROVE`/`DECLINE`).  
  - Блокировка ЛК в СДБО (через REST API).  

**Примеры интеграций:**  
- **RabbitMQ:** Настройка очереди `OPERATIONS_SV_QUEUE` для входящих транзакций.  
- **REST API:**  
  - СДБО → Антифрод: Проверка операций.  
  - Антифрод → СДБО: Ответ с решением (`SCOR_SUSPECT_FRAUD`, `BLACK_LIST` и др.).  

**Примечание:** Для реализации необходимо согласовать форматы запросов/ответов (см. разделы 2.1.3 и 2.1.5) и обеспечить обработку кодов стандартных ответов (раздел 3).

### **Дополнение к требованиям по валютам и курсам**  

**Требование:**  
Обеспечить корректную обработку транзакций в разных валютах путем интеграции с **справочником курсов валют** от банка.  

#### **1. Передача курсов валют**  
- **Источник данных:**  
  - **API банка** (REST/JSON) с актуальными курсами (рекомендуемый вариант).  
  - **Файловый обмен** (CSV/XML) с периодичностью обновления (если API недоступен).  
- **Обязательные поля:**  
  - `currency_code` (код валюты, например, `USD`, `EUR`).  
  - `rate_to_rub` (курс к рублю).  
  - `last_updated` (метка времени обновления).  

#### **2. Конвертация сумм**  
- **Правила проверок** (например, лимиты в рублях) должны учитывать:  
  - Автоматический **пересчет суммы операции** в рубли по курсу на момент транзакции (`timestamp`).  
  - Округление до 2 знаков после запятой (для соответствия полю `amount`).  

#### **3. Обработка ошибок**  
- **Коды ответов для отсутствующих курсов:**  
  - `CURRENCY_RATE_UNAVAILABLE` — если курс не найден для `currency`.  
  - `CURRENCY_INVALID` — если валюта недопустима (нет в справочнике).  

#### **4. Пример параметров в запросе**  
```json
{
  "amount": 100,
  "currency": "USD",
  "timestamp": 1726217425000,
  "exchange_rate": 92.45  // Опционально, если передается извне
}
```

#### **5. Интеграция с существующими правилами**  
- Для правил с рублевыми лимитами (например, «>330 000 руб./день»):  
  - Добавить **конвертацию в рубли** перед проверкой.  
  - Указать в документации, что лимиты **всегда в RUB**.  

---  
**Почему это важно?**  
- **Пример:** Клиент переводит 5000 USD. При курсе 92 RUB/USD система должна проверить эквивалент 460 000 RUB против лимита в 330 000 RUB.  
- **Риски без доработки:** Ложные срабатывания/пропуски фрода из-за неучтенных курсовых разниц.
