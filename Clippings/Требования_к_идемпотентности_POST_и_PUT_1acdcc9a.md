## 🤖 **DeepSeek**

На основе истории переписки, вот требования к идемпотентности методов на стороне Core для **POST** и **PUT**:

## POST - **НЕ идемпотентный**

**Требования:**
- Каждый повторный идентичный запрос создает **новый ресурс**
- Сервер должен генерировать новый ID для каждого POST запроса
- Повторение запроса приводит к созданию дубликатов
- **Обязательная проверка на дубли** на стороне Core для предотвращения нежелательного повторного создания

**Пример:** Создание заказа - повторный запрос создает новый заказ с новым ID.

## PUT - **Идемпотентный**

**Требования:**
- Многократное повторение идентичного запроса дает **одинаковый результат**
- PUT должен **полностью заменять** ресурс
- При повторном запросе с теми же данными состояние системы не меняется
- Сервер возвращает тот же результат для повторных идентичных запросов

**Пример:** Обновление данных пользователя - повторный запрос с теми же данными не меняет состояние.

---

## Ключевые принципы:

1. **POST** - создает новые сущности, требует защиты от дублей
2. **PUT** - обновляет/заменяет существующие сущности, безопасен для повтора
3. Идемпотентность должна обеспечиваться **на уровне бизнес-логики Core**
4. Все внешние вызовы должны учитывать эти свойства при повторных запросах

# Описание процесса "Смена режима" (Change Mode)

## Предусловие
- Заведены вручную счета и остатки в BO

## Процесс выполнения

### 1.1 Проверка возможности проведения операции СБП
- **Payer → Core**: Request POST
- **Core → Payer**: Ответ на POST запрос

---

## Основной процесс смены режима

### Вариант A: Запрос на изменение режима Online
**1.2** ABS → Core: Request (Kafka online) с параметром is_online = "Y"
**1.3** Core → ABS: Ответ о принятии запроса

### Вариант B: Запрос на изменение режима Offline
**1.4** ABS → Core: Request (Kafka offline) с массивом счетов и остатков

**1.5** Core → Core: Обработка запроса
- Изменение статуса обработки баланса счета в Кэше Core на "PENDING" (по каждому счету отдельно)

**1.6** Core → Core: Формирование запроса в BO (XP Clearing_in) по каждому счету отдельно

**1.7** Core → BO: Запрос на обновление счета и остатков "Set account balance"

---

### Группа обработки в BO

#### Сценарий успешного обновления:
**1.8** BO → Core: HTTP код 2xx
**1.9** Core → Core: Изменение статуса баланса счета в Кэше на "Offline"

#### Сценарий неуспешной записи:
**1.10** BO → Core: HTTP код 4xx
**1.11** Core → ABS: Response Kafka о невозможности проведения авторизации в Core
**1.12** ABS → Core: ABS повторяет запрос до получения положительного ответа Offline или Online

**1.13** Core → ABS: Подтверждение изменения режима на "Offline"

---

## Выполнение операции

**1.14** Payer → Core: Request PUT на выполнение операции

**1.15** Core → Core: 
- Core ставит обработку операции на "паузу"
- Проверка режима Core из Кэша
- Если статус "Pending", начинается опрос кэша каждые 100мс для получения положительного статуса

---

## Особенности процесса

- Операции, которые завершатся по таймауту во время взаимодействия с BO, будут повторно отправляться со стороны ТСП
- Повторные запросы будут обработаны, так как в одной из попыток BO гарантированно запишет балансы
- Обеспечивается идемпотентность обработки повторных запросов

# Требования к идемпотентности методов

## POST методы - **НЕ идемпотентные по умолчанию**

### Проблема:
- Многократный вызов POST с одним ID возвращает разные `externalId`
- Каждый вызов инициирует новую операцию СБП

### Требования:
- **Ключ идемпотентности**: параметр `ID` (uuid) в теле запроса
- Запросы с одинаковым ID должны обрабатываться как повтор первого запроса
- **Не должно создаваться новых операций** при повторных вызовах

### Логика обработки:
1. Проверить наличие предыдущего ответа для ТСП с таким же ID
2. Если был **положительный ответ** → вернуть тот же ответ
3. Если был **отрицательный ответ или его не было** → проверить ответ от Шлюза СБП
4. Если от Шлюза был **положительный ответ** → выполнить шаги 3-5 (антифрод, финмон, ответ ТСП)
5. Если от Шлюза **отрицательный ответ или его не было** → выполнить все шаги заново

---

## PUT методы - **Идемпотентные**

### Проблема:
- Шлюз СБП отклоняет повторные запросы с ошибкой "повтор идентификатора"
- Некорректная работа систем клиента при повторных запросах

### Требования:
- **Ключ идемпотентности**: параметр `ID` (uuid) в теле запроса
- **Ключ для операций СБП**: `ips_27_operation_id` + `ips_105_clearing_date`
- Повторные запросы должны получать **такой же ответ** как на первый запрос

### Логика обработки:
- Если запрос с таким ID **уже обработан со статусом 200** → вернуть положительный ответ (200) **без инициации нового процесса**
- Если запрос с таким ID **со статусом ≠ 200** → инициировать процесс обработки

### Особый случай:
- **Ручная повторная выгрузка** с признаком `rpt_flag = Y`
- Проводка прокидывается в АБС, но авизо (`camt.054`) формируется только если не было отправлено в первоначальном процессе

---

## Общие принципы:
- **Положительные ответы**: HTTP 200, 201, 202
- **Отрицательные ответы**: все остальные HTTP коды
- При одновременных запросах с одинаковым ID ответ должен направляться на все инициированные запросы

# Функциональные требования к идемпотентности методов Core

## 1. Требования к POST методам

### 1.1. Общие требования
**FR-POST-001:** Система Core должна обеспечивать обработку повторных POST-запросов как идемпотентных операций

**FR-POST-002:** Ключом идемпотентности для POST-запросов должен выступать параметр `ID` (uuid) из тела запроса

### 1.2. Логика обработки повторных запросов
**FR-POST-010:** При получении POST-запроса система должна проверять наличие предыдущего ответа для ТСП с таким же ID

**FR-POST-011:** Если для данного ID существует предыдущий положительный ответ (HTTP 200, 201, 202) → система должна вернуть тот же ответ без выполнения бизнес-логики

**FR-POST-012:** Если предыдущий ответ был отрицательным или отсутствует → система должна проверить наличие ответа от Шлюза СБП для данного ID

**FR-POST-013:** Если от Шлюза СБП был получен положительный ответ → выполнить только шаги 3-5 (антифрод, финмон, ответ ТСП) без повторного проксирования в Шлюз

**FR-POST-014:** Если от Шлюза СБП ответ отрицательный или отсутствует → выполнить полную обработку запроса (шаги 1-5)

### 1.3. Обработка конкурентных запросов
**FR-POST-020:** При одновременной обработке нескольких запросов с одинаковым ID система должна гарантировать отправку сформированного ответа на все инициированные запросы

---

## 2. Требования к PUT методам

### 2.1. Общие требования
**FR-PUT-001:** Система Core должна обеспечивать идемпотентную обработку PUT-запросов

**FR-PUT-002:** Ключом идемпотентности для PUT-запросов должен выступать параметр `ID` (uuid) из тела запроса

**FR-PUT-003:** Для операций СБП дополнительным ключом должен выступать связка `ips_27_operation_id` + `ips_105_clearing_date`

### 2.2. Логика обработки операций СБП
**FR-PUT-010:** При получении PUT-запроса система должна проверять наличие уже обработанного запроса с таким же `ips_27_operation_id` и `ips_105_clearing_date`

**FR-PUT-011:** Если запрос с такими параметрами уже обработан со статусом 200 → вернуть положительный ответ (200) без инициации нового процесса обработки

**FR-PUT-012:** Если запрос с такими параметрами существует но имеет статус ≠ 200 → инициировать процесс обработки заново

### 2.3. Обработка ручной повторной выгрузки
**FR-PUT-020:** Система должна поддерживать специальный режим обработки для ручной повторной выгрузки с признаком `rpt_flag = Y`

**FR-PUT-021:** В режиме `rpt_flag = Y` система должна гарантировать прокидку проводки в АБС

**FR-PUT-022:** В режиме `rpt_flag = Y` система должна предотвращать дублирование авизо (`camt.054`) - формировать его только если не было отправлено в первоначальном процессе

### 2.4. Логика проксирования PUT-запросов
**FR-PUT-030:** При получении повторного PUT-запроса система должна проверять наличие предыдущего ответа для ТСП с таким же ID

**FR-PUT-031:** Если существует предыдущий положительный ответ → вернуть тот же ответ повторно в сторону ТСП

**FR-PUT-032:** Если предыдущий ответ отрицательный или отсутствует → выполнить полную обработку запроса (шаги 1-3)

---

## 3. Общие системные требования

### 3.1. Хранение состояния
**FR-COMMON-001:** Система должна хранить историю обработки запросов с ключами идемпотентности и результатами обработки

**FR-COMMON-002:** Время хранения состояния обработки должно покрывать длительность операционного дня

### 3.2. Классификация ответов
**FR-COMMON-010:** Положительными ответами считать HTTP коды: 200, 201, 202

**FR-COMMON-011:** Отрицательными ответами считать все остальные HTTP коды

### 3.3. Производительность
**FR-COMMON-020:** Механизм проверки идемпотентности не должен существенно влиять на производительность обработки запросов

**FR-COMMON-021:** Система должна обеспечивать атомарность операций проверки и обновления состояния идемпотентности
